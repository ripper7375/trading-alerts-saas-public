### What happens to a manifest

1. **Endpoint:** key, contract, slot not more than 10 minutes ahead; queue `cycle-manifest` on `market-data-sync` with `{ manifest, receivedAt }`.
2. **Processor** (after every row job queued earlier): insert the PENDING row `ON CONFLICT DO NOTHING` on `(symbol, slot)`; a row that is no longer PENDING is returned untouched.
3. **Check:** `market_data_v6` rows of each timeframe between `oldest_bar_ts` and `newest_bar_ts` must be at least `bar_count - quarantined_rows`; `indicator_statistics` rows captured at the slot must be at least `statistics_count`.
4. **Decision:** all landed → READY. Bars missing → look again in 5 s (a delayed job of the same name), and INCOMPLETE once 120 s have passed since arrival. Only statistics missing → look again, then READY after 30 s **with `STATISTICS_SHORTFALL` recorded** (decision 3). A manifest for a slot older than an hour → INCOMPLETE without reading the data.
5. **READY:** `ready_at = max(now, slot)`, status from `cycleStatus` (FRESH up to 2 minutes after the slot, 4 minutes when `attempts > 1`), the digest, then the `cycle-ready` job, then the conditional `PENDING → READY` update.

## 6. Decisions needed from Davin

None blocks part 5. Three, in order of weight:

1. **Make the landed check prove "this cycle's rows", not only "rows exist".** As built, it counts rows in the shared table over `[oldest_bar_ts, newest_bar_ts]`. Consecutive slots overlap by 287 bars, so an older copy of a row satisfies it even when this cycle's upsert of that row failed and is still waiting to be retried. For the closed bars that rarely matters (they do not change), but the **newest row** changes every cycle. Cheap fix: also require, per timeframe, that the row at `newest_bar_ts` has `cycle_id` at or above the manifest's `collection_cycle_id` (one more small query and a decision input, plus tests and mutants). The collector stamps every promoted row's `cycle_id` with its collection cycle (`promote_cycle`, `export_collector_validator_v2.py:1245`), and the manifest's `collection_cycle_id` is that same number (`backfill_worker_api_gateway_v5.py:743`), so the comparison is available now. **Recommend adding it**, in part 5 or as a small part 4b, before the first real cycle.
2. **A new direct dependency in `railway-gateway`: `ajv` 8.18.0** (pinned exactly; it is already in the lockfile through other packages). The contract is a JSON Schema and Python's validator is what the sender is held to, so Ajv gives the same verdicts (96-case corpus). Confirm; `security-overrides.md` concerns only `overrides`, which are untouched.
3. **The statistics policy.** Bars gate readiness; statistics get 30 s of grace and the cycle then goes READY with `STATISTICS_SHORTFALL` recorded. The alternative, never READY without statistics, lets a statistics outage block every cycle and every sensor. **Recommend keeping it as built**, with part 5 deciding STALE from the shortfall (§7 item 6).

## 7. Problems and surprises the next session must know

1. **Bull adds concurrency across named handlers.** One `process(name, 1, fn)` starts one loop, but a second named handler starts a second loop on the same queue, and the manifest would then run alongside a row. Read in `node_modules/bull/lib/queue.js` (`while (concurrency--)`, and `handlers[job.name] || handlers['*']`). Hence the single `'*'` handler. `market-data.processor.spec.ts` checks exactly one registration and the two Bull lines, so a Bull upgrade that changes them fails there with the reason.
2. **Every queue must be overridden in every e2e spec.** The un-mocked `cycle-ready` queue made the four existing e2e specs pass but leave an open Redis handle. One line was added to each; the new e2e gives `market-data-sync` its own mock so it can assert what the worker registered.
3. **Idempotency is three layers, each tested:** the PENDING insert is `ON CONFLICT DO NOTHING`; a row that is not PENDING returns before anything else; the ready job id is keyed by the slot and the READY update is conditional. The announcement goes **before** the READY update, so a failure between them is retried and announces again under the same job id (Bull ignores it). The other order could mark a cycle READY and never announce it, silently.
4. **Step 3's consumer must not assume the row is already READY when it picks up a `cycle-ready` job**: the job exists for a moment before the update commits (and for as long as it takes to retry if that update fails). The job's payload carries `readyAt`, `dataStatus`, `attempts` and the digest so it can proceed without waiting, or it should retry.
5. **The digest's canonical form is defined by TypeScript's number formatting** (`2650` where Python prints `2650.0`). Anything that recomputes it later, for the replay, must produce the same text; the known-answer test uses non-integer prices for that reason. The form is `spine/1\n{"M5":[[ts,o,h,l,c,v]...],"M15":[...]}`, bars oldest first, indicator columns excluded on purpose.
6. **Part 5 must not read READY as "statistics are all there".** A cycle can be READY with `check_detail.reason = 'STATISTICS_SHORTFALL'`. "Missing statistics → STALE" needs part 5 to check that.
7. **No watchdog for a stuck PENDING row.** A manifest job that fails all 3 attempts (a database outage longer than the backoff) leaves its row PENDING for good. Part 5 reads only READY rows, which makes it harmless; it is not cleaned up.
8. **`cycle-ready` jobs pile up in Redis until step 3** (about 288 a day, small payloads). They never complete, so `removeOnComplete` never trims them.
9. **Time to ready still includes the sender's 386 serial row requests** (part 3, §7 item 1). The 2-minute deadline may be tight; part 10's measurement settles it, and the thresholds in `manifest-thresholds.ts` are starting values.
10. **Deploy order matters and is Davin's** (§8). A gateway deployed before the migration answers 200 and then fails the job on a missing table; the sender has stamped the manifest delivered, so it is lost.
