**When the export runs.** `OnTimer` exports at second 59 of every minute (`InpExportSecond = 59`, `TimeLocal`); at the minute that ends an M5 bar the forming bar is one second from closing, at the other minutes it is up to four minutes old. **Which export the collector pairs with slot T, and so how old the forming bar is when a cycle reads it, is the step 2 newest-row question, which stays unverified** (`measure-cycles.js` prints the ages that settle it).

**What follows from it, and what does not.**

- **ADR-083's premise is confirmed by the source.** The decision says the band columns are populated on exactly `T_EDT` rows ending at the forming bar. Rows 4 and 6 are why: the bands are drawn through `rates_total - 1`, and the containment count includes it. So `t_edt_open_bar_rows = 1` is right and **no MINOR change is needed on this ground**. It holds while `InpExtendLinesToCurrent` is `true` (the default in all seven); with `false` the bands stop at `rightmost_bar`. The `.set` values deployed on terminals A and B are not in the repository: check that input on the VPS (**your production check, section 7, item 2**).
- **The plan's two possible outcomes** were "the fit includes the forming bar: certification states that look-ahead is limited to its close" or "`t_edt_open_bar_rows` becomes 0". **The first is the case.** What certification should say, in words you can change: the SSA trend, the crossings, the containment sample and the extended statistics read the bar still forming at the export, with its close as of the last tick before it; the Model A and B window includes it only when the newest used cluster has a crossing there; and the trend stored for an older bar is the one computed when it was the live bar, while the line, the bands and the statistics are refit over the whole window at every export (ADR-020).
- **Not shown by a read:** how much the forming bar moves a fit. That needs a point-in-time value compared with the same bar one cycle later (B4). Also not traced: the collector's validator (`export_collector_validator_v2.py`) and the point-in-time table.

## 8. Problems and surprises the next session must know

1. **The index-use test could not be made to fail here.** The part 4 note said it fails on a table that has held rows. On PostgreSQL 18.0 it passed on an empty table, on a table analysed with 26,000 rows and on the same table after `DELETE`, and in the full run of the five gated specs. So the rewrite is **deterministic by construction, not a reproduced-then-fixed bug**: it proves the index exists on `cycle_slot` alone, and, in a transaction that is always rolled back, drops the unique index (`(symbol, cycle_slot)`, which version 18 can also scan), switches sequential scans off and asks for the plan of the writer's own `DELETE`: the only way left to find those rows is the index under test, whatever the statistics say. It runs with 0 and with 2,000 rows and leaves the table, its indexes and its statistics as they were (a test says so).
2. **`evaluated_at` is when the worker STARTED the job, not when it finished.** `CycleReadyProcessor.handle` takes `nowSec` once at the start and passes it on as `evaluatedAt`; the schema comment says "when the cycle was evaluated". The database therefore never holds a completion time. The kit's "signal to done" is the start delay plus the job's wall time (`--jobs` or `--redis`) or, failing that, the MCDs' summed times, and the report says which. I changed no production file; if you want the true end in the table, that is a column in a later migration.
3. **Every cycle is a fresh Python process, so MCD0 pays a one-time cost:** the lazy build of the schema validator (`mcd_common/envelope.py` `_validator`), about 0.19 s on this machine against 6 to 27 ms for MCD1 to MCD3; run twice in one process MCD0 takes 4 ms. It is far inside the 1 s budget but it will always show in MCD0's row (runbook §4.2).
4. **Part 6's "five gateway specs need the whole checkout" is now six**: `measure-sensors-real.spec.ts` reads the Python sources, the registries and the standard to pin the kit's constants. A copy of `railway-gateway/` alone fails them; the Railway build runs no tests.
5. **The mutation harness.** Its first version died at the first mutant: the Jest output holds characters Windows' default code page cannot decode, and Python's `subprocess` (text mode) lost them in a reader thread. It runs with `encoding="utf-8", errors="replace"` now. The first full run was also too slow (14 s a mutant, 447 mutants), so it was stopped (the source was restored from its copy and its SHA-256 checked) and rerun on four copies of the package in parallel. Recorded in `environment-gotchas.md`.
6. **Tool traps met:** a recursive `grep` over the whole repository from the Bash tool ran past two minutes (`node_modules`): use the Grep tool or name the folders; the PowerShell tool refused a command that held `Remove-Item` because it took `D:\SaaS` (the path up to the space) for a system path: delete in a separate command that names the folder; the Bash tool's working directory moved again after a `cd` (use a subshell).
7. **What was not measured:** anything against production, staging, a real Redis, the Railway image or the VPS; PostgreSQL 18.0 here against Railway's version; Python 3.11.9 here against the image's; the compressed bundle's real size per cycle (the runbook says how to measure it live); how often MCD0 flags a timeframe on live cycles (3 of 3 fixtures flag both).
