# B1 evidence: latest bar per index, four statements measured on a scratch PostgreSQL

**Order:** [adhoc-currency-snapshot-latest-per-index](../migration-orders/adhoc-currency-snapshot-latest-per-index.migration-order.md) (Unit 2, B1 of the PostgreSQL/cache quick-win study) · **Date:** 2026-10-20 · **Executor:** Claude Code · **Nothing here touched production or any real database.**

## What was measured, and where

- **Scratch server:** PostgreSQL **18.1** (the binaries on this machine), `initdb --locale=C`, defaults except `fsync=off`, `synchronous_commit=off`, `full_page_writes=off`, `max_wal_size=4GB`; `shared_buffers` 128MB, JIT on, 2 parallel workers per gather. **Production is 17.11** (Davin, 2026-10-20). Docker is not installed, so a matching 17 server was not available.
- **Does the version gap matter?** The one 18 feature that could change a plan here is btree skip scan, which applies when a query filters a LATER index column without the leading one. None of the four statements does (S1 has no filter, S2 and S3 filter the LEADING column). The planner's cost model may still differ between 17 and 18, so treat the plans as strong evidence, not proof, for 17.
- **Table:** Prisma's own DDL (`prisma migrate diff --from-empty --to-schema prisma/market-data/schema.prisma --script`), the `currency_gold_indices` table and its three indexes: the primary key, `UNIQUE (index_name, bar_time)` and `(index_name, bar_time DESC)`, the same three Davin confirmed on production.
- **Data (synthetic, `gen.sql`):** nine listed indices, one M5 bar per index every 300 s, consecutive days of 288 bars; rows inserted in time order across indices (the engine's arrival order), so the heap is not in index order. XAUX's session opens 60 s after the others. CHFX is stale (its newest bar is 40 days older). `ZZ1X` is an UNLISTED index name with one row.

| Volume             | Days | Rows      | Heap pages | Index bytes |
| ------------------ | ---- | --------- | ---------- | ----------- |
| V0                 | 5    | 11,809    | 204        | 2.0 MB      |
| V1 (about 1 year)  | 260  | 662,401   | 11,421     | 108 MB      |
| V2 (about 3 years) | 780  | 2,010,241 | 34,660     | 332 MB      |

- **Method:** after `VACUUM (ANALYZE)`, per statement and volume: `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` five times (median), a text plan once, and one end-to-end `psql` run to a file for rows and bytes returned (`bench.cjs`). Primary metric: **shared buffers touched (hit + read)**, which does not depend on what was cached.
- **Equality:** every candidate is compared, by an md5 of its rows, with an independent reference (the row at each index's `max(bar_time)`, no `DISTINCT ON`, no `LIMIT`). S0 is compared after the application's own de-duplication (first row of each `index_name` run in S0's order).

## The four statements

- **S0, what Prisma 7.9.1 sends today** (checked with the study's offline probe on this checkout): `SELECT "id", <5 columns> FROM "currency_gold_indices" ORDER BY "index_name" ASC, "bar_time" DESC OFFSET 0`. All rows cross the driver; the application keeps the first of each index.
- **S1:** `SELECT DISTINCT ON ("index_name") <5 columns> ... ORDER BY "index_name" ASC, "bar_time" DESC`.
- **S2:** `unnest(ARRAY[<the nine ALL_INDEX_NAMES>]) CROSS JOIN LATERAL (... WHERE "index_name" = n."index_name" ORDER BY "bar_time" DESC LIMIT 1)`.
- **S3:** a recursive CTE that finds each distinct `index_name` by repeated "next name above this one" seeks, then the same `LATERAL ... LIMIT 1` (full text in `bench.cjs`).

## What the plans show

- **S1 does the same server work as S0.** At V2 its plan is `Unique` over an `Index Scan` of `currency_gold_indices_index_name_bar_time_idx` with `Index Searches: 1` and **324,117 buffers read**, the whole index plus a heap visit per row: `DISTINCT ON` walks the ordered rows and drops duplicates, it does not jump from group to group. It saves the transfer (10 rows instead of 2,010,241, 394 bytes instead of 146 MB) and nothing else: 3.5 s of database time per call at V2, growing with history.
- **S3 touches about one index entry per group.** At V2: `Index Searches: 10` for the "next name" seeks on the unique index, then `Index Searches: 10` for the newest bar of each group (a backward scan of the unique index, `LIMIT 1`), **96 buffers, 0.62 ms**, and the figure is flat from V1 to V2 (it depends on the number of groups, not the history).
- **S2 is as fast but wrong by design for this order:** it returned 9 rows where the reference has 10, because `ZZ1X` is not in the list. The Advisor's Q2 settled that an unlisted name must not be dropped.

## Robustness checks of S3 (scratch only)

- Empty table: 0 rows. One index with two bars: its newest bar. An index name outside the nine: returned.
- A V1 table loaded with NO `VACUUM` (visibility map empty, `0 of 11,421` pages all-visible): 131 buffers, 0.79 ms, so S3 does not depend on a freshly vacuumed table.

## Decision (order rule D5)

1. Equality with the reference: S0, S1, S3 pass; **S2 fails at all three volumes** (drops `ZZ1X`) and is rejected.
2. Lowest median buffers at V2 among the passing statements: **S3, 96 against 324,118** (S1 and S0).
3. The "within 2x, take the simpler" tie-break does not apply (the gap is more than three thousand times).
4. Rule (d), "stop if the best still reads more than 25% of the table's pages at V2": S3 reads 0.3%. It does not fire.

**Chosen: S3.** It has no bind parameter (no array binding through the driver adapter to prove), it preserves dynamic name discovery, and it needs no schema or index change.

## What this does NOT show

- **Production plans, timings or load.** The statements ran on a scratch 18.1 server (production is 17.11) with synthetic data, a `C` collation (production's is unknown; `ORDER BY` and `>` in S3 use the column's own collation, and so does the index), default memory settings and no concurrent traffic. The server milliseconds are not production latencies.
- Real data distribution, table bloat, autovacuum timing, the network round trip, or the number of groups growing beyond nine.
- Anything about statement (2) of the helper (the sparkline read, bounded to one session) or the other helpers (B2, B3).

## Reproduce

`gen.sql` (`psql -v ndays=260 -f gen.sql` on a database that has `cgi-ddl.sql` applied) and `bench.cjs` (`node bench.cjs <port> <db,db,db> <outDir>`; it calls `C:/Program Files/PostgreSQL/18/bin/psql.exe`). Start the scratch server with `Start-Process -WindowStyle Hidden` as the environment gotchas say.
