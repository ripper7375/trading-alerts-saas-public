### Findings that change the work

- **S0. The riskiest assumption holds (spike, read-only).** The existing fixtures are trimmed per MCD. I merged them into **one shared per-cycle bundle** per slot (403 KB for v1, 671 KB for v4: up to 1,133 M5 and 378 M15 bars) and ran all four evaluators on it, MCD3 reading the MCD1 and MCD2 envelopes just produced: **8 of 8 stored envelopes reproduced byte for byte** (v1 and v4, MCD0 to MCD3). Evaluation took 2.6 to 24 ms per MCD; a cold Python start with the kit and four evaluators imported took 92 ms; two runs were byte-identical; each envelope is about 1,000 to 1,600 characters. With `retuning = True` the kit already makes all four CAUTIONARY (`RETUNING`; MCD3 also carries `UPSTREAM_CAUTIONARY:MCD1` and `:MCD2`). Script: session scratchpad, `spike_union_bundle.py`. This is evidence for the shared-bundle design and for the 30 s cycle budget (section 11.2 of the standard); it is not evidence about database latency.
- **S1. Language gap: the evaluators are Python, the worker's home is a Node-only image.** ADR-016 says "Railway", not which language. Options: (a) **keep Python as the only implementation and run it from the gateway as a per-cycle subprocess** (recommended: the standard says the evaluator, parameters and registry are copied into the worker "unchanged", section 11.1; no second implementation to keep equal); (b) port the kit and four evaluators to TypeScript (about 1,165 + 2,300 lines and about 690 tests to re-express; byte-identical canonical JSON needs decimal half-up arithmetic; every MCD from MCD4 on would be written twice; I estimate six to eight sessions, unmeasured); (c) a separate Python Railway service that consumes the Bull queue (needs a Bull-compatible consumer in Python, a new service and new secrets). Option (a) needs Python 3.11 and PyYAML in the Railway image: **that is a change to the production build, so it is a Phase B step, verified first on a throwaway Railway service** (B0). Q2.
- **S2. "Replaying a stored cycle gives identical readings" cannot hold unless the inputs are stored.** The worker reads channel columns (`*_ssa`, `*_uoedt`, `*_loedt`, `*_base_fl`) from `market_data_v6`, and a later cycle refits them over the whole window (ADR-020; waiting-on, look-ahead item). A cycle's inputs cannot be rebuilt from the tables a week later. Step 2's decision 8 left "freeze per cycle" to step 3. Recommended: store the exact canonical bundle per cycle, compressed, in its own table with a retention you set, and store its SHA-256 on every `mcd_outputs` row. The bundle is small because the loader selects only the columns the evaluators read (fixtures: 2 to 30 columns per bar); measured JSON 0.4 to 0.7 MB per cycle on the fixtures; compressed size and a year's storage are **unmeasured**. Q4.
- **S3. On every real fixture MCD0 flags both timeframes** (3 of 3 slots: v1 `MCD0_M5_M15_DEFECT`, v3 and v4 the same). With ADR-018 applied, every channel MCD is then CAUTIONARY with `MCD0_DEFECT_M5` and `MCD0_DEFECT_M15` on those slots. The per-MCD fixtures hold the evaluators' own output, before inheritance, so the worker needs its own cycle-level expected outputs. This is what walkthrough Part 0 item 3 predicted, and what the five-day shadow review is for. Section 2.4 of the architecture lists MCD0 as the gate; ADR-061 would halve the risk on most setups if the rate stays this high.
- **S4. A queue backlog and an eager consumer.** `cycle-ready` jobs have piled up since the gateway shipped (nothing consumes them; `removeOnComplete` never applies to a job that never runs). A consumer that starts at deploy would evaluate days-old slots against refit columns and write them as if live. The worker must treat a job older than a bound (starting value 10 minutes, the ADR-012 STALE window) as skipped and recorded, and registering the consumer must be impossible while the module is disabled (a test pins that). Q11.
- **S5. The bundle keys `config_hash` and `channel_mode` by source; `market_cycles` keys them by timeframe then source.** Two timeframes using the same source with different tunings cannot both be in one `CycleInputs`. The seeded setting (M5 `best_fit_a`, M15 `non_b`) cannot collide, but the setting allows it. Recommended: the loader refuses that case (the reading becomes INVALID with `SANITY_FAILED`, logged), instead of changing the kit. Q13.
- **S6. "Flag off until all nine items pass" against "every MCD built so far starts shadow running in step 3".** Items 7 to 9 (dispatch matrix, synthesis rows, statistics measured) cannot be done before shadow. Read as: shadow needs items 1 to 6, live needs all nine. Q7.
- **S7. The newest-row question (stub or closing bar) is still open** and decides whether the last closed bar's values in a bundle are final. Stored bundles (S2) make the sensors immune for replay; the live check is B1. The worker never writes `market_cycles`: I read "live shadow writes on `market_cycles`" in your prompt as shadow writes to `mcd_outputs` for real `market_cycles` rows.

### Part 3: the cycle inputs loader (TypeScript, `railway-gateway/src/sensors/inputs/`)

- **Files:** `bundle-types.ts` (the `CycleInputs` JSON form), `inputs-source.ts` (**one interface, two sources**), `fixture-inputs.source.ts`, `database-inputs.source.ts`, a new channel-column bar query beside (not inside) `closed-bars-query.ts`, `statistics-fields.ts` (the live-bar field removal list, pinned to the kit's), `stats-slot.ts`, plus specs.
