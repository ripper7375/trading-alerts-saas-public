## 5. How it works (for the approval)

**One request.** For a JSON-schema request to a model that enforces schemas and caches only behind a breakpoint, with a chart, the adapter sends (this is the real output of `buildRequestBody`, text shortened):

```json
{
  "model": "vendor-a/model-one",
  "messages": [
    { "role": "system", "content": [ { "type": "text", "text": "<RULES>", "cache_control": { "type": "ephemeral" } } ] },
    { "role": "user", "content": [
        { "type": "text", "text": "<CYCLE BLOCK>", "cache_control": { "type": "ephemeral" } },
        { "type": "image_url", "image_url": { "url": "https://…/m5.png" } },
        { "type": "text", "text": "<USER PART>" } ] }
  ],
  "temperature": 0.2,
  "max_tokens": 1500,
  "response_format": { "type": "json_schema", "json_schema": { "name": "report1", "strict": true, "schema": { … } } },
  "provider": { "data_collection": "deny", "require_parameters": true },
  "usage": { "include": true }
}
```

with `Authorization: Bearer <key>`, `Content-Type` and `Accept` as the only headers, `redirect: "error"`, `cache: "no-store"`. For a model that does not enforce schemas the format is `{ "type": "json_object" }` and the result says `response_mode: "JSON_OBJECT"` (the validator is the caller's either way; a provider can ignore a schema). A message that is all text with no breakpoint to mark is sent as one string, with its parts joined with nothing between them, the way part 2 reads a prompt.

**What is refused before anything is sent** (a failure with a code and `attempts: 0`): no messages or a malformed one, an empty text, an image that is not https or a base64 PNG/JPEG/WebP/GIF, an output limit above the model's, a temperature outside 0 to 2, a wait of zero or more than ten minutes, a schema without a plain name, an image for a model without vision (`VISION_UNSUPPORTED`), and a prompt estimate over the model's window once its own margin is added (`CONTEXT_TOO_LARGE`). That last check is how a fallback with a smaller window is skipped.

**Waits and retries (decision D23).** One attempt waits 25 s for the primary model and 20 s for the fallback (the Understand call keeps its one second). One immediate retry for HTTP 429, HTTP 5xx, a timeout or a network error; none for any other 4xx, a body that is not a completion, a body that is too large (1 MiB; 64 KiB for Understand), or a request aborted by the caller's own signal (the request deadline of part 7). An error carried inside a 200 is read by its number only.

| Failure                                                                       | Code                                                                                          | Retried                             | Asks the fallback                   |
| ----------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | ----------------------------------- | ----------------------------------- |
| HTTP 429, 500, 502, 503, 504                                                  | `HTTP_<n>`                                                                                    | once                                | yes                                 |
| other HTTP 4xx (400, 401, 402, 403, 404, 408, 413, 422)                       | `HTTP_<n>`                                                                                    | no                                  | yes                                 |
| attempt timed out                                                             | `TIMEOUT`                                                                                     | once                                | yes                                 |
| `fetch` threw (network, a refused redirect)                                   | `UNREACHABLE`                                                                                 | once                                | yes                                 |
| not JSON, no choices, no text, text that carries the key, a 200 with an error | `BAD_RESPONSE` or `HTTP_<n>`                                                                  | no (429 and 5xx inside a 200: once) | yes                                 |
| body over the limit                                                           | `RESPONSE_TOO_LARGE`                                                                          | no                                  | yes                                 |
| the caller's deadline passed                                                  | `ABORTED`                                                                                     | no                                  | **no**                              |
| not configured, URL refused, request refused                                  | `NOT_CONFIGURED`, `URL_REFUSED`, `REQUEST_INVALID`, `VISION_UNSUPPORTED`, `CONTEXT_TOO_LARGE` | nothing sent                        | the fallback port checks for itself |

**Cost.** (1) The provider reports `usage.cost`: that figure times a million, rounded to the nearest whole micro-dollar, no flag. (2) It does not, or sends something that cannot be a cost (not a number, negative, over $100 for one call), and the registry has a dated price and both token counts: price times tokens in exact integer arithmetic, `COST_ESTIMATED`; cached input is priced as ordinary input, so the estimate is never below the truth. (3) Neither: `null` and `COST_ESTIMATED`, and the caller must not treat the call as free. A token count that is not a whole number of at least zero is null; more cached tokens than prompt tokens is null.

**The fallback.** Primary fails: the fallback is asked once, with `max_output_tokens` cut to what it can write. Both fail: the outcome lists both, with the last code, and part 7 sends the board-only fixed answer. The fallback is not asked when none is named or it is switched off, when it is the same vendor as the primary (a second lock behind the registry's), or when the deadline has passed. Switching off the default promotes the fallback model to ask alone; switching off both leaves nobody (`NO_MODEL`).

**The registry's rules, by name** (each is damaged on purpose by a test): an unknown field or value, a slug that is not `vendor/model`, a duplicate slug, a `:free` variant (those hosts may keep prompts), a price without its date or a date without a price, one price without the other, more than six decimals, an impossible calendar date, a window that is too small for the budget and the output together, a language that is not one of the 19, a `passed` model with no run, no verification date or no dated price, an unverified row that claims anything, and a launch pair that is two defaults, two fallbacks, one without the other, not `passed`, without the answer role, or from one vendor.

## 6. Decisions and readings of mine

D1, D5 and D25 are built as ordered. These are the places where the order, the plan or the documents were silent or could be read two ways. The first two are what you have to do; the rest stand unless you object.

1. **Run the smoke script (yours; runbook S1).** Step A is free and needs no key: `node scripts/reply/gateway-smoke.js --list-models` reads OpenRouter's public list and prints, for each of the six rows, the live slug, context, price per million tokens, image input and structured outputs next to the registry's. A slug it cannot find is one of my guesses to correct. Step B spends money: with the key set and the monthly cap set in the OpenRouter dashboard (D5), `node scripts/reply/gateway-smoke.js --call --cap-usd 1` (add `--probe-cache`) makes up to three tiny calls per model through the real adapter (a JSON object, a strict schema, a one-pixel image; seven with the cache probe) and prints the registry fields it would propose. Each call is about 50 tokens in and out, so the whole run costs cents; the script stops when the money spent reaches `--cap-usd` (default 1, at most 10: D25's whole initial evaluation is $5 to $10). **It writes nothing.** The verified fields go into `config/ai-models.ts` by a person with the dates they were read (`verified_at`, `priced_at`), and the checker then holds each row to them.
2. **Naming the launch pair belongs to S2, not S1.** The order says the pair "will be named after S1". The registry's checker refuses a `launch_role` on a model that is not `passed`, and refuses `passed` without an evaluation run, because ADR-055 says both models pass the suite. So S1 fills in the verified fields of the candidates and lets you choose which two to evaluate; part 10's recorded run (S2) is what sets `status: 'passed'` and the two `launch_role` fields, in two rows. Parts 4 to 9 are built and tested on fixture models and need no pair. If you want a pair named earlier, the rule to change is `registry.ts` (the `passed` requirements), and that is your call.
3. **The waits.** The order's "25s / 20s" is read as the primary model's wait and the fallback's (decision D23: "per-call timeouts of 25 s and 20 s"), and the Understand call keeps ADR-098 D4's one second and one retry. With a retry the primary alone can take 50 s; the request deadline of part 7 (55 s, aborting through the signal the adapter honours) is what bounds the whole request.
4. **Two environment names, one new.** `OPENROUTER_API_KEY` is the key and `INTAKE_UNDERSTAND_API_KEY` its alias (D5); the canonical name wins when both are set, and an empty or blank one counts as unset. I added `OPENROUTER_BASE_URL`, with `INTAKE_UNDERSTAND_BASE_URL` as its alias, because the answer path needs the same override the Understand call already had (a proxy, or a local fake). `INTAKE_UNDERSTAND_MODEL` still names the Understand model. All are read from an env object the caller passes in: the gateway reads no `process.env`, and none is set anywhere or in `.env.example`.
5. **What an unverified row is.** The order wants every model a `candidate`. I added a field the order did not name, `verified_at` (null until S1), and made the checker hold a row without it to the safe side: no vision, no JSON-schema mode, no caching, no price, no language, no run, a window of at most 32,768 tokens and an output of at most 2,048, so the prompt always fits, the reply is always checked by our validator and no chart goes to a model that may not read one. The slugs (`google/gemini-3.6-flash`, `deepseek/deepseek-v4-flash`, `z-ai/glm-5.2`, `moonshotai/kimi-k3`, `openai/gpt-5.6-terra`, `anthropic/claude-sonnet-5`) are `vendor/model` guesses from file D's display names. A `:free` slug is refused by the checker: those hosts may keep prompts (ADR-077).
6. **Roles and tier access are copied, not decided.** The two 1.0x models (Gemini 3.6 Flash, DeepSeek V4 Flash) may be named for the Understand call as well as the answer, the other four only for the answer, because the Understand call has a one-second budget. The role is not enforced at run time (the environment names the Understand model); it is a declaration the picker and the fallback read. `tier_access` copies the picker's `proOnly`: the default is open to Free, the rest are Pro only. Both are yours to change, in one file (D22 sets the entitlement table in part 6).
7. **"Another provider" is another vendor.** ADR-055 says the fallback comes from another provider. I read that as the model's maker (the slug's prefix: `google`, `deepseek`, ...), which is what makes the pair independent of one company's outage, and not as the host OpenRouter routes to. Which hosts may serve a model is a separate matter (ADR-077; `provider_only`, and `data_collection: "deny"` on every call).
8. **Cost.** The provider's reported cost is rounded to the nearest whole micro-dollar (not up); an estimate is computed from the dated price on integers; a "reported" cost over $100 for one call is not believed. The unit is read as US dollars. OpenRouter's documentation calls the field "credits" and its support page says credits are dollar-denominated; S1 confirms it against the dashboard.
9. **The fallback is asked after any failure except the request's own deadline.** That includes a 401 or 402 (the same account will probably fail again, but the second call costs nothing and the fixed answer waits for it either way). Each model is asked at most once per request, so a prompt that is too large for the fallback's window is refused by the fallback itself with nothing sent, and shows in the attempts.
10. **The validator is the caller's.** The gateway sends `json_schema` where the model enforces it and `json_object` otherwise, and reports which (`response_mode`); a reply that is not valid is the orchestrator's regeneration (decision D11), not a reason to switch models. So "json_object plus a validator" is the mode choice here and the schema check in parts 5 and 7.
11. **`provider.require_parameters` is sent only with a JSON-schema request**, so a host that would ignore the schema is not used. The Understand call does not send it (its request is unchanged from step 6 apart from the usage block).
12. **No back-off.** A retry is immediate: the Understand call has no second to spare and OpenRouter routes the retry itself.
13. **The key has a static guard.** The word `Authorization` or `Bearer` may appear in exactly one file of `lib/reply` (`gateway/openrouter.ts`), and a test reads every file for it. The same test lets only that file use `fetch`, a timer or the clock.
14. **An empty key is "not configured"**, not a `Bearer ` header (found in my own review, section 8).
15. **Added to the plan's file list:** `messages.ts` (part 2's assembled prompt to the adapter's messages: the seam `ChartInput.ref` was documented as the gateway's job).

## 8. Problems and surprises

1. **OpenRouter's documentation differs from the order in three places** (I read the provider-routing, usage-accounting, structured-outputs and prompt-caching pages on 2026-10-14 while the mutation run was going). (a) `usage: { include: true }` is deprecated "and has no effect": full usage details come with every response. (b) `cost` is documented in "credits" (support says credits are dollar-denominated). (c) GPT-5.6's optional explicit caching uses `prompt_cache_breakpoint`, not `cache_control`; its automatic caching, like DeepSeek's, Moonshot's, Z.AI's, OpenAI's and Gemini 2.5's, needs no marker, and `cache_control: { "type": "ephemeral" }` is the form for Anthropic Claude, explicit Gemini and Qwen. Also: `provider.only` takes provider SLUGS (`google-vertex`), not display names; the registry's comment now says so. Confirmed as I had written them: `provider.data_collection` (`allow` default, `deny`), `provider.require_parameters`, `response_format: { type: "json_schema", json_schema: { name, strict, schema } }`, and `usage.prompt_tokens_details.cached_tokens`. The documentation says strict mode "may restrict which JSON Schema features you can use, and enforcement varies by provider": whether `report1-1.schema.json` (with its length limits and patterns) passes a provider's strict mode is open (section 9).
2. **The tests found three defects in my code, all fixed:** `isIsoDate` judged `0001-01-01` by the wrong year (`Date.UTC` reads 0 to 99 as 1900 to 1999; now `setUTCFullYear`); `--call --json` printed a progress line before the JSON, so it was not one document; and my first fake service reported 2,048 cached tokens out of a 50-token prompt, which the adapter rightly read as unknown, so the cache probe said "no caching" for a model that caches (the fake was wrong, the adapter was right).
3. **My own review found one more:** a configuration with an empty key string would have been sent as a `Bearer ` header and made every response look like it contained the key. It is now `NOT_CONFIGURED` with nothing sent (four tests).
4. **The first mutation run was in the main tree and I stopped it half way.** `Stop-Process` on a command-line pattern also matched the Bash tool's own shells, and one source file (`usage.ts`) was left mutated. I had copied every source file and its checksum first; the file was restored from the copy and all ten files were compared byte for byte before anything else ran. The run was then redone in six scratch copies of the tree (a standing fact in `environment-gotchas.md`).
5. **`python` is still a dead alias here**, so part 1's Python-backed parity cases (6) skip silently in a targeted run, as in part 2. Nothing in this part needs Python.
