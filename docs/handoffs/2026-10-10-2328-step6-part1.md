The ten readings:

1. **The contract above** is my reading of §4.9, D9 and F10 and F11. The fields most likely to change when parts 4 and 5 meet real data: `data.last_price` (D8), the `events` item fields, and the chunk fields (part 6 settles the corpus front matter). Any change is a recorded amendment; nothing reads the packet before step 7.
2. **The SYN reading's zones keep the stored hash even when there are none.** The worker stores a real `zones_sha256` for an empty list (checked on goldens 02 and 14) and a `zones_reason` (`NO_ZONE_SOURCES`, `NOT_DIRECTIONAL`); the packet carries both, and the reason is set exactly when there are no zones. My first draft said "null when empty" and the golden data corrected it.
3. **The packet has a `trace` of its own, and the route's trace adds to it.** Everything in the packet's trace is derived from the packet, so it cannot drift; the request id, the stage times and `packet_sha256` (D9 e) belong to the route's trace, because a hash cannot be a field of the thing it hashes. `packetSha256(packet)` hashes the whole packet, trace included.
4. **The hash is async and platform-made**: SHA-256 by Web Crypto (`globalThis.crypto.subtle`, available in Node, browsers and the edge runtime), over the TypeScript canonical text, so `canonical.ts` imports nothing and a client component may import the barrel. It is **not comparable with a hash Python makes of the same document** (`json.dumps` writes `1e-05` where JavaScript writes `0.00001`); the sensors' own `envelope_sha256` is carried verbatim and never recomputed here.
5. **Rule D1's open corners.** English text from a non-English interface is answered in `en-US` and Portuguese in `pt` (the first locale of that language in the list); an instant prompt is answered in the interface locale; an interface value that is not a locale falls back to `en-US`.
6. **The roster's `owned_terms` is the level names a sensor reports** (UOEDT, baseline, LOEDT), the only terms the registries give; the glossary of part 3 adds the others and names an owner for each. `flag` is the committed configuration (all `off`); what is live at run time is the flag on the stored rows. `on_board` means "not a gate".
7. **Ten refusal codes**: the five gate codes in the order the gate decides them (NOT_SIGNED_IN, TIER_REQUIRED, THREAD_INVALID, PROFILE_NOT_SET, QUOTA_INSUFFICIENT), FEATURE_UNAVAILABLE, QUESTION_EMPTY and QUESTION_TOO_LONG at the door, UNDERSTANDING_FAILED (the new row D4 asks for), OUT_OF_SCOPE. HTTP statuses are left to part 5's route layer, as `lib/engine4/server/errors.ts` does for Engine 4; the reply text comes from part 3's registry.
8. **Starting limits**, one constant each: question 500 characters (A5), English 1,000, a chunk's text 4,000, 4 chunks, 8 expansions, 50 events, 15 board lines; the JSON Schemas carry the same numbers and a test ties them.
9. **`INTAKE_VERSION = 1.0.0` and `ROUTING_VERSION = routing-v1`** (the matrix of part 4 will carry that id).
10. **The importer allow-list in `boundaries.test.ts` is empty on purpose** (section 4b). It is friction for parts 5 and 10, which must add their routes and components to it; it is what stops a flag-gated feature from reaching a client bundle by accident.

## 7. Problems and surprises

- **Tests are never type-checked here.** The root tsconfig excludes `__tests__`: `tsc --noEmit --listFilesOnly` lists 3,190 files and not one test (Engine 4's included), and Jest's SWC does not check types. A temporary tsconfig showed four real errors in my tests (an unused import, a field missing from a helper type, an unsafe cast, a possibly undefined index), fixed. The step 5 part 6 note in `environment-gotchas.md` says the opposite; I corrected it and added the recipe.
- **The first suite run found a real validator defect**: a missing field was reported twice (`REQUIRED`, then a wrong-value issue on the same path), and a key whose value is `undefined` counted as present. Fixed in `check.ts` (`Issues.add` reports a missing path once; `exactObject` treats `undefined` as missing) with direct tests.
- **The mutation check's first tool cost 10.5 s a mutant** (978 would be 3 hours). A harness of four scratch copies with direct `node jest` calls and two test tiers brought it to about 15 minutes a pass; the recipe is in `environment-gotchas.md`. Two of the first pass's 136 survivors were killed only by a suite outside the first tier, which is why survivors get a second, wider run.
- **Three small code changes came from the check**, none of behaviour a caller would see: two redundant length limits removed (the slot and the build id are already bounded by their patterns), the trace comparison now uses `canonicalJson` instead of a helper of its own, and the "SYN not running while its reading is given" rule now fires for `NOT_RUNNING` only (an invalid state is reported once, as that).
- **Beyond the order's file list**: `lib/intake/check.ts` (the toolkit the packet, refusal and roster validators share, so it is not written three times); `knowledge-service/config/registry-codes.json` (the plan's part 1 text says `build_roster.py` writes it; the order's list left it out; it creates the top-level `knowledge-service/` folder that part 6 will fill); the test helpers and five suites the order did not name (`check`, `engine4-parity`, `schema-parity`, `packet-edges`, `roster-edges`); and `packetSha256`, which the plan's "`packet_sha256`" asks for and which keeps part 5 from hashing a part of the packet by mistake.
- Two known traps met again and avoided: Bash collapses `\\n` (a patch of the harness was rewritten with the Edit tool) and `Path.write_text` writes CRLF on Windows (a list the harness read had `\r` in it).
