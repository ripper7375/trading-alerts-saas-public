## 6. Decisions for Davin (readings of mine where the plan was silent)

I built each as the default and will change any of them on your word.

1. **Which sensors have a line: the configuration's live sensors plus any sensor that has a live row for the cycle.** A sensor the roster marks `live` and that has no live row is listed ABSENT (D7). A sensor with a live row but marked `shadow` or `off` in the committed configuration still has its line, because the row proves it ran live at that slot and a warning from it must not vanish a minute after a configuration change. A gate (MCD0) has a row and never a line; a row of a sensor the roster does not know is reported (`SENSOR_UNKNOWN`) and given no line. With the committed configuration (every flag `off`) and no live row the board is empty and the packet says `SENSORS_NOT_LIVE`.
2. **The synthesis is shown only from a LIVE row of the trader type, and only if a sensor is live.** A `shadow` reading never reaches the board; with no live sensor the SYN line says "not running" whatever the table holds (it has nothing it could have read). The DATA price comes from that live row (D8); with no live synthesis the DATA line says "last price unavailable".
3. **The board is checked line by line against the envelopes, not trusted.** A row whose envelope text does not hash to its stored hash, is of another sensor or cycle, has a state the sensor does not have, or says something the packet validator would refuse is **listed ABSENT with a problem** (`ROW_UNREADABLE`), never shown as what it claims. Two live rows for one sensor and cycle (the unique key forbids it) are both distrusted. The synthesis and its zones are all or nothing: the `entry_zones` rows must equal the stored zones document.
4. **The line count.** "Live sensors plus two" counts the SYN line and the DATA line; the header is a line of its own. The words for an empty board are on the SYN line, so the rule holds there too.
5. **A primary sensor that is INVALID or STALE is given in full** (its envelope says why it is unavailable); an ABSENT one cannot be (there is nothing to give), and the route notes `PRIMARY_UNAVAILABLE:MCD1`.
6. **D2 (b) as written makes the trend sensors warnings in the counter-trend readings.** A sensor whose LONG or SHORT is the opposite of the synthesis's is a warning. In a snapback (`R2_EXHAUSTION_SNAPBACK`: goldens 02, 06, 07, 08) the synthesis is by construction against the trend the sensors report, so those sensors are warnings, and in golden 10 (a range edge) the same happens; Direction then gives the **whole board** in full: Day Trader golden 08; Scalper goldens 06, 08, 10, 12 and 16 (16 has a single live sensor). The review file lists these cycles under each trader type. I built the rule as written (nothing is lost, only tokens). If you would rather exempt a sensor that is the premise of a counter-trend reading, that is a `routing-v2` change in `warnings.ts`, in the Python tool and in the matrix notes.
7. **Explain.** One sensor owner gives that sensor. Several owners (the level names, `trend`, `channel`: all three channel sensors) give the primary sensor and the sensor that reads **only** the timeframe the question names; the sensor that reads both (MCD3) is never "the sensor of the timeframe". Terms owned by the synthesis or a knowledge domain give no sensor. No term spotted gives the always set (note `NO_TERM`). Explain looks in domain D1 only, as 4.5 says, even when a sensor owns the term.
8. **Exit and targets.** A sensor is added if any of its levels is **strictly** beyond the entry on the target side. The entry is the first zone's reference price, or the close of the stored reading when there are no zones; the side is above for a LONG and below for a SHORT; a synthesis with no direction adds nothing (note `NO_TARGET_SIDE`). An INVALID or STALE sensor has no levels to count.
9. **Entry timing** adds the `source_sensors` of the stored zones (all zones of the reading), not only the first zone's.
10. **The instant prompts** add the sensors whose `uses_channel` includes the label's timeframe: M5 gives MCD2 and MCD3, M15 gives MCD1 and MCD3. D10 (b) is therefore read from the roster, not named.
11. **The gateway.** If it cannot be asked the status is UNKNOWN (`GATEWAY_UNREACHABLE` in the flags and the problems) and the slot comes from the newest `READY` row of `market_cycles`, so the board is still shown; Section 5 gets no direction from UNKNOWN. A gateway that answers with no cycle gives no slot and no readings.
12. **Events.** Upcoming means the newest observation of a release is not before the clock. The News intent gets every upcoming release of the next **7 days**, the others the HIGH-impact releases of the next **24 hours**, at most 50, soonest first. `OK` up to 45 minutes of calendar age, `LATE` after (the age of the newest observation of the whole table, as Engine 4 reads it), `UNAVAILABLE` for an empty table or a failed read, never "no news". `tier1` is true for an id of Engine 4's list, which ships empty (D13). The 7 days and the 50 are mine.
13. **The 800-token cap is checked with three characters to a token.** A board of 15 sensors, each with the longest state code and the longest summary of the signed-off cycles, fits; every real board of the stored worlds is under half the cap.
14. **The matrix owns the knowledge.** Each row names its domains in the order D1 to D5 and whether the D2 playbooks are searched for the sensors of M\*. Part 6 reads them from the file.
15. **Three existing regexes of `packet.ts` are now exported** (`REASON`, `STATE_CODE`, `RULE_ID`): the facts use the packet's own rules, not copies. No other change to part 1's files except the barrel and `INTAKE_VERSION`.
16. **The profile reader is a projection built field by field**; a stored profile that no longer passes its own validator is `PROFILE_UNREADABLE`, not "not set".
