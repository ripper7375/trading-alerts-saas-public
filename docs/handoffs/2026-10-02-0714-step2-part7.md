## 1. Done in this session (one line each)

- **Renderer worker** (`mtf_render_upload_worker.py`, rewritten): driven by the cycle, not the clock. It polls `xauusd.db` (read-only) for the newest validated M5 cycle and renders when `cycle_time` is newer than the last one it rendered; with none recorded (a restart) it renders the newest validated slot once.
- **Active indicator per timeframe, at the slot:** the worker asks `GET /api/v1/cycles/current?slot=S` for the setting AT the slot it renders; every way that can fail (not configured, unreachable, timeout, non-200, not the contract, a timeframe with no setting, an unknown indicator, an answer for another slot or from a gateway that ignores `?slot=`) falls back to `RENDER_OVERLAYS` and is stamped `overlay-source: default`.
- **The stamp, twice:** in the image title (cycle slot with unix and UTC, last closed bar, indicators, variant, render time, the forming-bar notice, and the newest M5 candle actually drawn) and in R2 object metadata (`cycle-slot`, `last-closed-bar`, `overlay`, `variant`, `rendered-at`, plus `overlay-m15` and `overlay-source`). New pure module `mtf_render/stamp.py` is the one definition.
- **The picture is drawn AS OF the slot** (`as_of_slot`): no bar opened after the slot is read, so a row a later cycle has written cannot get into an image that says it is for slot S.
- **The last good image is kept:** both variants are rendered into a temporary folder and every file is checked to be a complete PNG; only then is anything uploaded. A failed render, a missing or truncated file, a failed upload, a bug while choosing overlays: the objects in R2 stay as they were, the slot is retried after `RENDER_RETRY_SEC`. A prune failure after a good upload no longer fails the slot (found and fixed this session).
- **Gateway, additive:** `GET /api/v1/cycles/current?slot=S` (strict: digits, a 5-minute boundary, not more than 600 s ahead of the gateway clock) resolves the settings at S and says so with `basis: REQUESTED_SLOT`; without the parameter nothing changes.
- **Monolith:** `ChartStamp`, `parseChartStamp`, `chartMatchesCycle(stamp, cycleSlot)` (`NO_CHART_STAMP`, `CHART_SLOT_MISMATCH: ...`), `chartStampHeaders` in `lib/storage/chart-keys.ts`; `getChartStamp(variant)` (HeadObject, `null` for no object or no usable stamp, an error for anything else) in `lib/storage/r2.ts`; `/api/chart/download` puts the stamp on its 307 as `X-Chart-Slot`, `X-Chart-Last-Closed-Bar`, `X-Chart-Overlay`, `X-Chart-Variant`, `X-Chart-Rendered-At` (and two extras). It still serves an image with no stamp or an unreadable stamp; entitlement and error handling are exactly as before.
- **Parity pinned in tests:** metadata keys, slot length, variants and sources (Python `stamp.py` against `chart-keys.ts`), and the object key (worker `KEY_PREFIX` and `OUT_STEM`, and its `Metadata` argument, against `chartObjectKey()`, as well as the existing renderer check).

### How the stamp stays true

`slot` is `collection_cycles.cycle_time` of the validated M5 cycle the image was drawn from; the collector promotes a cycle's rows into `market_data` before it marks the cycle validated, so a validated slot's data is in place. `last-closed-bar` is always `slot - 300` (rule 2: a bar is closed when open time + 300 <= slot). The read is capped at the slot, so the picture cannot contain a later cycle's row. The same stamp object builds the title and the metadata, and the renderer refuses a stamp whose variant is not the picture's. On the monolith side `parseChartStamp` accepts only what is consistent: a missing or malformed field, a slot off the boundary, a last closed bar that is not `slot - 300`, or a variant that is not the object's own all mean "no stamp", never a guess.

## 7. Problems and surprises the next session must know

1. **The renderer and the gateway disagree about "now" by about a minute** (the VPS validates S, the gateway READY-s S later). Hence `?slot=`. Anything else that must act on "the setting at the cycle I am working on" from the VPS side has the same issue.
2. **The renderer is slot-driven, so a restart renders the newest validated slot once** (its memory of the last slot is in process, on purpose). The same slot is therefore re-uploaded after a restart; harmless, and the stamp is the same.
3. **The pair can be briefly mixed if the second PUT fails** (overlay new, standard old). Each object still carries its own true stamp, so a consumer comparing slots sees it. A PUT is atomic, so no object is ever half-written.
4. **`RENDER_INTERVAL_SEC` is retired** and silently ignored if still set; `RENDER_POLL_SEC` (10) and `RENDER_RETRY_SEC` (30) replace it. The renderer needs `API_GATEWAY_URL` and `BACKFILL_API_KEY` (the push worker's values) in its NSSM environment, or it runs on `RENDER_OVERLAYS` and stamps `default`.
5. **`nssm set ... AppEnvironmentExtra` replaces the whole value**; add the two new variables together with the R2 and `MTF_DB_PATH` ones already there.
6. **The `X-Chart-*` headers are on the redirect.** A browser script following the redirect cannot read them; they are for downloads, curl and tools. Code that needs the stamp (the prompt builder) calls `getChartStamp(variant)` itself (one HEAD request, no image bytes).
7. **A HEAD request is added to every download.** If it fails the download still works and logs a warning; signing happens first, so a missing R2 configuration is still the signing call's 503.
8. **Mutation harnesses must run detached** (a tool timeout would kill one mid-mutant and leave a mutated source); recorded in `environment-gotchas.md`.
9. **No UI text was added** (no `.tsx` markup changed), so the i18n coverage rules do not apply.
