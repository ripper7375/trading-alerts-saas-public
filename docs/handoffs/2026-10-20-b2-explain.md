# B2 evidence: latest bar per requested index, four statements measured on a scratch PostgreSQL

**Order:** [adhoc-pro-session-bars-latest-per-index](../migration-orders/adhoc-pro-session-bars-latest-per-index.migration-order.md) (Unit 3, B2 of the PostgreSQL/cache quick-win study) · **Date:** 2026-10-20 · **Executor:** Claude Code · **Nothing here touched production or any real database.** Method, data and caveats are those of [B1's evidence](./2026-10-20-b1-explain.md); only what differs is described here.

## What was measured, and where

- **Scratch server:** PostgreSQL **18.1** (the binaries on this machine), `initdb --locale=C`, defaults except `fsync=off`, `synchronous_commit=off`, `full_page_writes=off`, `max_wal_size=4GB`; `shared_buffers` 128MB, JIT on, 2 parallel workers per gather. **Production is 17.11**; Docker is not installed. None of the statements filters a later index column without the leading one (the only case where 18's btree skip scan applies), so the plans should match 17's; not proven.
- **Table and data:** exactly B1's: Prisma's own DDL (`cgi-ddl.sql`, the `currency_gold_indices` table with its primary key, `UNIQUE (index_name, bar_time)` and `(index_name, bar_time DESC)`) and B1's synthetic generator (`gen.sql`), both in `2026-10-20-b1-explain/`. V0 11,809 rows, V1 662,401, V2 2,010,241; nine listed indices (CHFX stale by 40 days, XAUX's session opening 60 s later) and the unlisted single-row `ZZ1X`.
- **The caller's filters (the difference from B1):** the helper receives the names it must find.
  - **FX8:** the eight FX indices the chart and screener send (`USDX EURX GBPX JPYX AUDX CADX CHFX NZDX`); `XAUX` and `ZZ1X` are in the table but not requested.
  - **ONE:** the single name the detail route sends (`EURX`).
  - **MIXED:** a hostile request: a repeated name, a name with no rows, an unlisted name that is in the table: `EURX EURX NOPE ZZ1X USDX`.
- **Method:** as in B1: after `VACUUM (ANALYZE)`, `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` five times per statement, volume and filter (median), one text plan, one end-to-end `psql` run for rows and bytes. Primary metric: **shared buffers touched (hit + read)**. Equality: an md5 of each candidate's rows against an independent reference (the row at each requested index's `max(bar_time)`), in `index_name` order; S0 is compared after the application's own de-duplication.

## The four statements (for a request of names `N`)

- **S0, what Prisma 7.9.1 sends today for statement (1)** (the study's offline probe, case `pro-session-latest-distinct-ordered`): `SELECT "id", "index_name", "session_open_bar_time" FROM "currency_gold_indices" WHERE "index_name" IN (N) ORDER BY "index_name" ASC, "bar_time" DESC OFFSET 0`. Every historical row of the requested indices crosses the driver.
- **S1:** `SELECT DISTINCT ON ("index_name") ... WHERE "index_name" = ANY(N) ORDER BY "index_name" ASC, "bar_time" DESC`.
- **S2:** `(SELECT DISTINCT n FROM unnest(N::text[]) AS u(n)) AS names CROSS JOIN LATERAL (SELECT ... WHERE "index_name" = names.n ORDER BY "bar_time" DESC LIMIT 1) ... ORDER BY "index_name" ASC`.
- **S3:** B1's recursive walk over the distinct names, restricted to `N` (`"index_name" > previous AND "index_name" = ANY(N)`), then the same `LATERAL ... LIMIT 1`.

## What the plans show

- **S1 does the same server work as S0 here too.** For the eight FX names at V2 both touch **287,918 buffers** (about 8.3 times the table's heap pages: an ordered index scan with a heap visit per row) and take about 3 s; `DISTINCT ON` saves the transfer (8 rows instead of 1,785,600 and 89 MB) and nothing else. For one name at V2 both read the whole index range of that name (35,526 and 35,529 buffers).
- **S2 and S3 cost a handful of seeks and do not grow with the history.** At V2: S2 **35** buffers (FX8), **7** (ONE), **18** (MIXED); S3 69, 12 and 32. The plan of S2 at V2 (FX8): a `HashAggregate` over the unnest (the distinct names), then a nested loop whose inner side is `Limit` over `Index Scan Backward using currency_gold_indices_index_name_bar_time_key` with `Index Searches: 8`, `Buffers: shared hit=35`, **0.29 ms**.
- **Every statement equals the reference for every filter at every volume**, including the hostile mix: the repeated name gives one row, the absent name gives none, the unlisted-but-requested `ZZ1X` is returned, and the unrequested `XAUX` stays out. In B2 S2 is exact because the names are the caller's own filter (in B1 the same shape had to be rejected for dropping names the caller never listed).

## Decision (order rule D4)

1. Equality with the reference: all four pass for all filters and volumes.
2. Lowest median buffers at V2: **S2** for all three filters (35 / 7 / 18 against S3's 69 / 12 / 32).
3. S2 and S3 are within 2x of each other (1.97x, 1.71x and 1.78x at V2), so the order's tie-break applies and prefers S2 for its structural simplicity (no recursion for an explicit input array). It would have won without the tie-break.
4. Rule "stop if the best still reads more than 25% of the table's pages at V2": S2 reads 0.1% (FX8). It does not fire.

**Chosen: S2.** The requested names are bound as one `text[]` parameter; the gated spec proved that the driver adapter binds it (so Prisma's `Prisma.join` fallback was not needed).

## What this does NOT show

The same limits as B1: no production plans, timings or load; PostgreSQL 18.1 against production's 17.11; a `C` collation; synthetic rows in time order; default memory settings; no concurrent traffic; no autovacuum bloat or network round trip. The server milliseconds are not production latencies. Nothing here is about statement (2) of the helper (the bars from each session open, bounded to one session), the corridor or preference reads.
