## 6. Decisions needed from Davin, with the options seen

None blocks part 6. Decisions 1 and 2 are about what a replay says; 3 to 6 are small and can wait.

1. **The verdicts: four you named, and two more.** Your order named four findings (verified, tampered bundle, version mismatch, logic divergence). Built: those four, plus **`STORED_READING_CORRUPT`** (a stored row whose `envelope_json` does not hash to its own `envelope_sha256`, or whose envelope names another MCD, slot or evaluator version than its columns: without it a row edited in the database would be reported as an evaluator defect, which sends the investigation the wrong way) and **`NOT_REPLAYABLE`** with a cause (nothing stored, the bundle was deleted by the 90-day retention while the readings stay, no readings, readings made under different RETUNING enforcement, the engine's configuration unreadable, the runner gave no result). Options: **keep (recommended)**; or fold `STORED_READING_CORRUPT` into `TAMPERED_BUNDLE` (one word fewer, a wrong name for what it is).
2. **A replay never runs Python on inputs it cannot vouch for.** A tampered bundle (the unzipped text does not hash to `inputs_sha256`; or the encoding, the unzip, the recorded length, the JSON, the slot or symbol inside it, or a reading's `inputs_sha256` disagree) ends the replay before the runner starts: the verdict needs no run, and a run would only show what the tampered bytes produce. Options: **keep (recommended)**; or run it anyway and print the difference (about 1 s more per cycle, and a risk that someone reads that difference as an evaluator finding).
3. **How the stored text is sent back.** The replay parses the stored text and sends it as the runner's request (`JSON.parse`, then the runner bridge's `JSON.stringify`), the same path a live bundle takes. For any text the worker stores this is a fixed point (JavaScript wrote the numbers the text came from: shown on the three stored bundles, with the hash equal whether the file is sent raw or through JavaScript, and on a bundle with `1e-07`, `1e+21`, a 16-digit integer, a denormal and a long decimal), and the replay still compares the runner's returned bundle hash with the stored `inputs_sha256`, so a case where it is not shows up as `LOGIC_DIVERGENCE` with "the canonical form of a bundle changed". The one text it cannot reproduce is one containing an integral float such as `5.0`, which only a sender other than the worker's JavaScript can write. Options: **keep (recommended; no change to the accepted part 4 file `python-runner.ts`)**; or add an optional `bundleText` to `RunnerRequest` that is spliced raw into the request, which removes even that case (a small edit to `python-runner.ts` and its spec).
4. **Flags come from the stored rows.** The committed `worker_config.yaml` has every MCD `off`, so a replay under it would run nothing. The replay writes a temporary configuration (outside the repo, deleted after) in which every engine MCD is `off` except those with a stored reading, which get the flag stored on the row. No Python change. A flag set the engine would refuse today (a checklist that changed since) is reported as `NOT_REPLAYABLE (RUNNER_FAILED)` with the runner's words, never as a verdict about the cycle. Options: **keep**; or a `--flags` option on `mcd_worker.cli` (a change to the accepted part 1 Python and its mutation tool).
5. **A fixture cannot be checked as text.** The three `mcd_worker/fixtures/*.bundle.json` files are not the canonical text the runner hashes (their SHA-256 is not `inputs_sha256`; measured), so a fixture's only inputs check is the hash the runner computes from the parsed file against the `inputs_sha256` in `.cycle.json`; a changed file and a changed canonical form both give `TAMPERED_BUNDLE (REPLAYED_HASH_DIFFERS)`, and the finding says they cannot be told apart. The stored database form has no such limit. Options: **keep**; or store `<slot>.bundle.canonical.json` beside each fixture (generated files, `.prettierignore` entries).
