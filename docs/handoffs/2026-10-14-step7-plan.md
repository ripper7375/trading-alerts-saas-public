## 4. Design in one picture

**Three homes.** (1) `lib/reply/`: the pure core of Section 5 and its ports (contracts, gate, context, gateway, checks, Report 1, metering arithmetic, orchestrator), with `read/` and `server/` imported by path, never through a barrel, the way `lib/intake/` is organised. (2) `lib/platform/`: the chapter 7 stores that touch the database (entitlements, the quota ledger, `request_traces`, chat threads and messages, retention). (3) Data files in `config/`: `config/ai-models.ts` (the registry, as the architecture names it), `config/entitlements.ts`, `config/reply/` (caps, prompts, wording lists, schemas, demo recordings). UI in `components/chat/` beside the existing `chat-panel.tsx` and `chat-sidebar.tsx`.

```
browser: Panel B composer  |  Panel C badge press  |  Panel A thread click
  -> POST /api/chat/message { client_request_id, thread_id?, TYPED{question} | INSTANT{intent} }   (NDJSON: stages, then one result)
     flag REPLY_ENABLED -> session -> tier (entitlement table) -> thread (owner) -> profile -> quota FLOOR
  -> runIntake (step 6, unchanged contract)       Understand now goes through the gateway and is metered
  -> ANSWER GATE (5.3)   data status decides what may be said; a chart is kept only if its cycle matches
  -> SHAPE   report1.v1 | answer.v1 | no model (REPORT_2 opens the modal; STALE gives a fixed text)
  -> ASSEMBLE (5.4, 5.5)  segments: static rules | cycle block | chart | user part; caps; cut order
  -> RESERVE the worst case in the ledger        cannot be covered -> refusal, the model is never called
  -> MODEL  (the fallback model on failure)       JSON schema where the model supports it
  -> CHECK  schema -> numbers -> wording          ONE regeneration, shared; then flag; wording twice -> fixed answer
  -> COMPOSE direction from SYN, values filled by id, data stamp, disclaimer, "what changed"
  -> SETTLE actual cost (units) -> WRITE message(s) + request_traces row -> final event
```

**Ports, as in step 6, so every edge is a thing a test replaces and counts.** `ModelPort` (the gateway; a fixture model for tests), `DayBarsPort`, `ChartPort`, `LedgerPort`, `ThreadStorePort`, `TraceWriterPort`, `ClockPort`, plus the step 6 ports (`UnderstandPort`, `SnapshotPort`, `KnowledgePort`). Each has a fake and a real adapter that is off by default. Every port **fails closed**: a ledger that cannot be reached refuses the request (never lets it through free), a trace that cannot be written fails the request after settlement is rolled back or marked, and a model port that throws is a fallback, then a fixed answer.

**One value dictionary, three users.** `buildValueDictionary(packet, dayBars)` returns every addressable value as `{ id, value, kind: PRICE | DISTANCE | PCT | RATIO | TIME | COUNT, tolerance }` (`MCD2.baseline`, `Z1.invalidation`, `DAY.high`, `LAST_PRICE`, distances from the last price to each level and zone, profile values, event times, statistics with their n). The **prompt** shows the model ids beside values, the **resolver** fills `{id}` placeholders, and the **number check** uses the same map as its context set. One source cannot drift from itself. Single OHLC bar values are left out, as §5.8 says.

**Direction is never the model's.** The schema has no direction field; the server copies bias, trend relation, rule id and archetype from the SYN reading; a golden test per scenario holds the structured direction equal to the synthesis, and a per-locale direction-word guard stops a headline from naming the opposite side (part 4).

**The prompt prefix is byte-identical across users.** Static rules, then the cycle block (board, SYN line, OHLC) for one trader type and one cycle, then the chart, then the user's part (readings, knowledge, profile, events, history, question). No clock, no request id and no user data above the user part; the trace records `cycle_block_sha256` and a test builds the prefix for two users and compares bytes. Whether the provider then caches is a registry flag (`prompt_caching`: `NONE`, `AUTO` or `EXPLICIT` with breakpoints) and a measurement, not an assumption.

**Metering is exact and two-phase.** Cost is stored as an integer in micro-dollars from the gateway's reported cost (never a float); units are derived (D2). Reserve before the call: the worst case of the Understand call, the answer call with maximum output and, if the balance allows, one regeneration (if it does not, regeneration is switched off and the numbers are flagged instead). Settle after: actual cost, release of the difference. A request id is the primary key of the reservation, so a double-click or a client retry cannot charge twice, and this uses the database's key, not the fail-open Redis guard of `lib/idempotency`.

**Time budget (§5.11) with a deadline.** Per stage targets as in §5.11 (Report 1 end to end ≤ 15 s at p90; short answers ≤ 8 s); every call has a timeout; the request has a deadline set from `maxDuration` (D23); on expiry the board-only fixed answer is sent and the reservation is settled for what was spent.

**Off by default, nothing deployed.** New: `REPLY_ENABLED` (exactly `true`), optional `REPLY_ALLOWED_USER_IDS` (D21), `OPENROUTER_API_KEY` (D5), optional `REPLY_DISABLED_MODELS` (a no-deploy kill switch). Unchanged and still off: `INTAKE_ENABLED`, `INTAKE_INSTANT_PROMPTS_ENABLED`, `ENGINE4_REPORT2_ENABLED`. Two migration FILES, neither applied (D3, D17), join the four unapplied ones of steps 2 to 5.
