### Two findings that can change the work

1. **The newest row at slot time may not be the new-bar stub.**
   - The exporters trigger at second 59 of each minute (`InpExportSecond = 59` in
     `mq5/ohlcvexportlightweight_v2_29.mq5:35,110`; same pattern in the centroid indicators).
   - The collector's guard comment (`export_collector_validator_v2.py:75-81`) treats a lag of about 300 s on M5
     as normal (worst legitimate lag 495 s).
   - Together these suggest that at slot 20:55 the newest row is the 20:50 bar, exported about a second before it
     closed, not the 20:55 stub that ADR-011 and §1.5 describe.
   - The only real sample (the 18 Sep example cycle in `davintrade-stack-d-and-e/engine-1-5-new/`) ends with the
     20:55 stub, so the evidence conflicts. A real cycle settles it. Part 3's manifest records each export's
     `Export Time` and newest bar for that purpose.
   - It touches rule 2 (a "closed" bar may be about 1 s short), rule 3 (the labelled price) and "replay returns
     the same closed bars".
2. **The indicators' own fits include the still-open bar.**
   - In `mq5/2EDTCentroidRegressionCherryPickA_v2_29.mq5:1997-2004` the SSA input vector runs to
     `rates_total - 1`. Only that one of seven centroid files was read.
   - This is the open "forming bar inside the statistics fit windows" item in `waiting-on.md`.
   - The §1.8 item "no still-open bar downstream" can therefore be shown on the read path only.

A scan of the `.ex5` binaries for frozen-mode strings was tried and is **not** evidence: the files are
compressed and the scan found nothing even for "Statistic".

### Part 1: slot, closed-bar rule, market hours, data-status function

- **Goal:** one pure, tested implementation of rules 1, 2 and 7.
- **Files (new):** `railway-gateway/src/cycle/slot.ts`, `market-hours.ts`, `data-status.ts`, `thresholds.ts`.
  - `slot.ts`: slot of a timestamp, "closed bar" (open + period ≤ slot), last-collected slot per timeframe
    (M15 refreshes at :00 :15 :30 :45).
  - `market-hours.ts`: TypeScript port of `is_market_open_xauusd` (with its DST rule), with parity cases against
    the Python function.
  - `data-status.ts`: FRESH, DELAYED, STALE, MARKET CLOSED from (now, slot, cycle row, market hours).
  - `thresholds.ts`: ADR-012 starting values in one place (ready ≤ 2 min, ≤ 4 min with retries, STALE after
    10 min), so confirming them later is a one-line change plus a new ADR.
- **Tests (new):** `test/cycle-slot.spec.ts`, `test/data-status.spec.ts`, `test/market-hours.spec.ts`.
- **Depends on:** nothing. **Migration:** none. **Deploy effect:** none (not wired in).
- **Open point for the part:** where the monolith gets the same status function (a copy pinned by a sync test,
  as the Prisma mirrors are, or a workspace package). Decide in the part, not now.

### Part 3: sender side, newest bars first plus the cycle manifest (VPS Python)

- **Goal:** ADR-013 and the sender half of ADR-009.
- **Files:**
  - Edit `C/backfill_worker_api_gateway_v5.py` in place (the name stays, so the NSSM service config does not
    change).
  - Edit `C/export_collector_validator_v2.py`: stamp export time and validated time on `collection_cycles`,
    using the existing `migrate_*` pattern; and `C/sqlite_schema_v6_xauusd.sql`.
  - New `C/gateway_contract_cycle_manifest.schema.json`.
- **Behaviour:**
  - The priority set is the newest 288 M5 and 96 M15 closed bars plus each timeframe's newest row (386 rows,
    inside the 500-row budget). The 288 comes from rule 4 and the §2 channel window of `min(T_EDT − 1, 288)`
    closed bars (ADR-083). It is to be confirmed against the MCD0 to MCD3 manifests when the part is built.
  - After the priority set the backlog drains oldest-first with the remaining budget, which keeps the "SQLite
    stops growing" guarantee of the current design.
  - The manifest (slot, collection cycle ids, bar counts, newest bar times, export times, terminal,
    `config_hash` per source, mode, remaining backlog) is sent only after the priority set is acknowledged.
  - A 404 or 5xx on the manifest means retry. It never quarantines and never stamps `synced_at`.
  - Single-row requests stay; throughput is measured alongside (ADR-013).
- **Tests (new):** `C/test_push_priority_order.py`, `C/test_cycle_manifest.py`, plus the existing Stack C tests
  re-run.
- **Depends on:** nothing to build; part 4 consumes the contract. **Deploy effect:** VPS files only, by Davin.

### Part 4: gateway manifest endpoint, landed-check, `market_cycles`, ready job

- **Goal:** the gateway half of ADR-009.
- **Behaviour:**
  - `POST /api/v1/cycle-manifest` with the existing API-key guard and a DTO validated against the part 3
    schema.
  - The manifest is processed in the same single-concurrency queue as the rows, so rows queued before it have
    landed by construction.
  - The processor compares counts and newest-bar times, writes one `market_cycles` row per slot (FRESH or
    DELAYED, with timings) and enqueues the `cycle-ready` job with id `XAUUSD_<slot>` once.
  - A duplicate manifest creates no second row and no second job.
  - The consumer of the job is build step 3.
- **Files:** `railway-gateway/src/gateway/*`, `src/worker/*`, DTO and contract wiring.
- **Tests (new):** manifest e2e spec, manifest processor spec, DTO-versus-schema contract spec.
- **Depends on:** parts 1, 2, 3 (contract). **Deploy effect:** the gateway auto-deploys from `main`, so apply the
  part 2 migration first. The endpoint is additive and the row contract is untouched.
