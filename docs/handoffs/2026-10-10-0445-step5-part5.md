## 6. Decisions for Davin (readings of mine where the order or the architecture was silent)

Built as the default unless you say otherwise.

1. **The CURRENT profile cascades on deleting the account; the two audit tables do not.** The order says `user_id` is a nullable FK with `ON DELETE SET NULL` and the plan said "no CASCADE anywhere". For `user_trade_preferences` that would leave a row full of a person's equity and limits with no owner and no hash. I made it `user_id NOT NULL UNIQUE ... ON DELETE CASCADE` (personal data goes with the account, architecture 6.11 "personal data is deleted"). If you prefer the literal reading, the alternative is nullable plus a cleanup job; a test fails if anything cascades into an audit table.
2. **Where the migration is.** The order said `prisma/non-market-data/migrations/`; that folder does not exist. Every migration lives in `prisma/migrations/` (one history for both schemas, `database-traps.md`), the plan said "after the newest one", so it is `20261010000000_add_engine4_tables` there. Live code wins (non-negotiable 7).
3. **The profile figures are TEXT, not NUMERIC.** The engine returns canonical decimal text (`types.ts`: "as stored, so a snapshot is JSON-safe and byte-stable"); a `NUMERIC(p,s)` rounds silently and Prisma's `Decimal` would hand back an object. The CHECKs cast the text, each one guarded by the decimal-text rule so a bad text fails its own rule only. The text must be canonical (no sign, no leading zero, no trailing zero), so the database refuses `1.50`.
4. **The counter-trend cap (at most 2.5 for Trend Countering) is also a database rule.** The order lists risk, leverage, RRR and the 1:5 ceiling; the cap is part of `validateProfile`, and the corpus needs the two to agree.
5. **Saving the profile the trader already has writes nothing.** A snapshot is a change; "confirmed again" is not stored (the consent record has its own time). The first save writes the first snapshot.
6. **The key.** A missing `ENGINE4_AUDIT_HMAC_KEY` stops every write; it must be at least 32 characters; `ENGINE4_AUDIT_HMAC_KEY_VERSION` is a whole number from 1 to 999999999, default 1. **Only `NODE_ENV=test` falls back to a public key** (the order said "fallback static test key for tests"): a published key anywhere else would make every hash guessable, so it is an error instead. The HMAC message is the user id's UTF-8 bytes with nothing added. To rotate: set a new key and a higher version; old rows keep their hash and version; recognising an old hash needs the old key, which the operator keeps (`verifyUserHash` answers `OTHER_KEY_VERSION` rather than guess).
7. **The trigger lets `user_id` go from a value to NULL when nothing else changes**, whoever does it (a hand-written `UPDATE ... SET user_id = NULL` is the same act as the foreign key's; it loses nothing the hash does not keep). Consequence: **a `User.id` cannot be changed while audit rows name it** (`ON UPDATE CASCADE` would have to rewrite them); ids are cuids and never change.
8. **What the consent record stores.** The whole `ValidatedSetup` as the exact text that was hashed (`setup_json`), its SHA-256, and a JSONB copy; the database re-derives the hash and checks that the copy is the same document (the pattern of `synthesis_readings`). The columns a reader filters on (`cycle_slot`, `side`, `zone_id`) must equal the setup's own values (three CHECKs). Beside them: `symbol`, the synthesis rule id and version (not in `ValidatedSetup`, so the caller passes them), the profile snapshot (a foreign key, `RESTRICT`), the `badge` (not in `ValidatedSetup`), the versions of Engine 4, `symbol_specs` (taken from `setup.versions.specs`, null when there were no broker figures), the template and the disclaimer, the language, and `recorded_at` (set by the database). The inputs, outputs, overrides and warnings of 6.11 are inside the stored setup, not repeated as columns.
9. **What `recordConsent` refuses** (as results): a setup not pinned to a cycle (or whose slot does not fit a 32-bit column, which holds until 2038), an Accept of a setup that failed its checks (a Modify or Decline of one IS recorded: the trader did look at it), a profile snapshot that is not the trader's, one that is not the profile the setup was validated against (all eight figures compared), and any empty name or version. The snapshot check is one extra read before the insert.
10. **`ENGINE4_VERSION = '1.0.0'`**, in `lib/engine4/version.ts` and the barrel. Change it whenever a change alters the figures or the verdict for the same inputs; the shape of a `ValidatedSetup` has its own id. The string is mine; say if you want another scheme.
11. **Narrow client interfaces.** The stores take the delegates they use as small interfaces (the real generated client fits with no cast; a test passes its own), like the readers of part 3, and are imported by path. The guard allows `crypto` and `@/lib/db/prisma` in `store/` only. Additive changes to earlier parts: the barrel, the guard test and the barrel test.
12. **Files beyond the plan's list:** `version.ts`, `store-fake.ts`, `store-guard.test.ts` (reads the stores' source: only `create` on the audit delegates, no update, delete or raw SQL), `migration-sync.test.ts`, and edits to `database-traps.md` and `environment-gotchas.md`.

## 7. Problems and surprises

1. **`ON DELETE RESTRICT` raises 23001, `NO ACTION` raises 23503.** My first spec expected 23503 for the snapshot foreign key; the key did refuse (the constraint name was right), the code was not. Recorded in `database-traps.md`.
2. **`TRUNCATE` of the history table alone is refused by PostgreSQL itself (0A000) before any trigger runs,** because the other two tables point at it. The `*_no_truncate` triggers are the wall for `TRUNCATE ... CASCADE` and multi-table truncates, so the spec tests each trigger with the other switched off.
