## 7. Problems and surprises the next session must know

1. **Prisma's `migrate diff` cannot see CHECK constraints.** With all three present it reports an empty migration, so a measured column added to the model without being added to `state_statistics_n_gate` would pass the drift check and let a number through below n = 30. Two tests in `schema-sync.spec.ts` compare the CHECKs with the model (every nullable `Float` is gated and nothing else; every `String[]` column is covered). Whoever adds a metric column must edit the CHECK in the migration too.
2. **Prisma makes `String[]` columns nullable** (`TEXT[] DEFAULT ARRAY[]::TEXT[]`, no `NOT NULL`), and a `NOT NULL` added by hand shows as drift. Hence the third CHECK.
3. **The long unique key needs an explicit name.** Prisma's default name for `(mcd_id, evaluator_version_series, config_hash_key, state_code, horizon_hours)` would pass Postgres's 63-byte identifier limit, so the model says `map: "state_statistics_series_key"`. The upsert `where` key in the generated client is still the long field-name form (used in the gated spec).
4. **`retuning_enforced` is not stored** (it was in what the runner hands over; you named only observed and applied). It is recoverable: when `observed` is false the switch has no effect, and when it is true `enforced = applied`.
5. **`inputs_sha256` is NULL on `mcd_outputs` only for a bundle that cannot be written as JSON** (part 1, section 7 item 4), and such a bundle has no canonical text, so `market_cycle_inputs` gets no row for it.
6. **Real server, not the embedded engine.** Step 2 verified on Prisma's embedded Postgres (PGlite) because Docker is not running. This time a real PostgreSQL 18.0 server ran from the installed binaries. The version differs from production's Railway Postgres (not known to me); everything used (CHECK, `TEXT[]`, JSONB, BYTEA, partial-free btree indexes) is old. The final check on production's own server remains yours, as for every migration.
7. **Two tool traps, now in `environment-gotchas.md`:** starting the cluster with `pg_ctl start` inside a tool call hangs the call (the server inherits the pipe) and, when the call is stopped, the postmaster's children die with `0xC0000142`; detach it with `Start-Process`. And a `cd` in one Bash call moved the session's working directory three times; use absolute paths. Also my Bash heredoc rejected TypeScript with backticks and quotes (the known trap): nothing was written, the Edit tool was used instead.
8. **The `railway-gateway` Prisma client in `node_modules` and both root clients were regenerated** (`npx prisma generate`, `npm run type-check`); `node_modules` is not tracked. `next-env.d.ts` was not touched (no build was run).
9. **The gateway auto-deploys from `main`.** Its schema now carries the three models; nothing queries them, so a deploy before the migration is applied is harmless. A deploy of part 4's code with the worker enabled before the migration is applied would not be (section 8, rollout).
10. **Part 1 and part 2 are both uncommitted**, with the other files already in the tree (`davintrade-recent-works/stack-d.md`, two earlier hand-offs). Commit by explicit path, never `git add -A`.
