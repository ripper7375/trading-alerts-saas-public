## 6. Decisions for Davin (readings of mine where the order or the plan was silent)

I built each as the default and will change any of them on your word.

1. **The 19 locales are the app's, not the order's list.** Section "READ THIS FIRST". `en-GB` and `pt` were added, `ms` and `ru` were not.
2. **The recorded run is a stand-in, announced as one.** The order allowed a deterministic fixture without a key; I made it impossible to mistake for a measurement: the manifest says `STAND_IN`, the gate prints it, a test fails the day someone relabels it, `--require-live-run` refuses it. Its answers are the hand labels (the same ones the router is judged on), so the intent and M\* figures of the TypeScript half are 100% **because of that**, not because a model is good; they would catch a router, scope, glossary or normaliser regression, and nothing else.
3. **Recall@4 is "at least one expected chunk in the first four hits"** (the order's definition), over the first four `chunks` and not the expansions. The mean share of the expected chunks found (0.464) is printed as information. Because a complete answer sometimes needs a chunk its intent cannot reach, a question is not failed for that alone.
4. **Bars as built:** intent match and M\* match each at least 90% in every locale (the order says "Intent & M\* match": I applied it to each, which is stricter than "both right" at once); every locale within 5 points of English on intent, M\* and recall (an epsilon so that exactly 5.0 passes); stand-aside and opposing sensors in M\* in 100%; out of scope refused as `OUT_OF_SCOPE` in 100%; **in-scope questions refused at most 5% (D15 c, proposed, a starting value)**; recall@4 at least 0.80 in every locale. The adversarial cases are judged apart, all 13 must pass.
5. **The label schema has more fields than the order's six:** `slice` (core or noisy), `trader_type` (the primary sensor, so M\*, depends on it), `expected_warnings` (what "stand-aside and opposing sensors present 100%" is measured against, labelled by hand and not derived from the router), `expected_symbols` and `expected_timeframes` (what a perfect reader returns; a live run reports them), `label_note` (why, for your reading).
6. **You approve the English base only.** The hash in `approval.json` is the canonical JSON of `base.en-US.json`. The translations are DRAFT and wait for native readers; the run is tied to their hashes, so a change to one needs a new run, not a new signature.
7. **The run files hold the retrieval request of every question** (`replay.retrieval`: intent, English pivot, M\*, state codes, routing version). The image build cannot run the TypeScript router, so the Python half must be handed what the pipeline asked; `labelled-gate.test.ts` re-derives it on every run and fails if the file is not what the pipeline does today, which is what makes it trustworthy. The cost: a change to the router, the matrix, the glossary, the normaliser, the scope check or the prompt means making the run again (`--stand-in --write`, or `--live --write`, which calls the model again).
8. **The fingerprint check is split by what each half can see.** Both check the glossary, the English base, each locale file (by canonical hash) and that the manifest hashes to its fingerprint; only the TypeScript half sees the prompt version and the prompt text. The Docker build therefore does not fail on a prompt change; the monolith's test run does.
9. **"2day" is a known gap, not fixed here** (section 4d). Should the scope check read it as today? Your call; a fix is one rule in `scope.ts` and a changed ledger test.
10. **The Dockerfile's replay step uses `--require-approved`**, so the labelled set needs its own signature before the image builds, in addition to D3 to D5.
11. **No `--require-live-run` in the Dockerfile** (so the image can build before there is a key); the runbook (part 10) should add it once a live run is committed.
