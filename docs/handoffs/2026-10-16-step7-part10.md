## 5. How it works (for the approval)

**A cell.** `runCellFull(scenario, key)` builds the orchestrator's world for the scenario (the golden cycle, the trader type, the locale, the data status and retuning flag, the condition: a model that is down, a quota that cannot cover the worst case, a knowledge index that is down, a late calendar, a chart of another cycle), runs one request through `runReply`, captures every call the answer model received, and records: what the pipeline answered with (outcome, fixed reason, refusal, notes, whether a direction is stated and is the synthesis reading's, the calendar's status), how many model requests went out, the calls in order with their tokens, cost and host, the units charged and the time, and **what the checks found** (`judgeReplies` over the captured replies).

**What a run keeps and what a replay recomputes.** A run keeps every call's text, so the replay can judge them again with no model: it rebuilds the world of each cell (the packet, the value dictionary), runs the same validation, number check, wording check, decision and composition the answer step runs, and compares with the recorded judgement. The outcome, the refusal and the notes are facts of the pipeline run; they are held by the scenario tests (the whole set runs through the orchestrator in the gate test and in `eval-run.js --check`).

**The gate.** For each registry row with status `passed`: it names a run; the run is on disk and well formed; it is a LIVE run (a stand-in is "not evidence"); it is of this model; its fingerprint is the CURRENT one (model and host, prompt, wording lists, caps, scenarios and their worlds); the bars recomputed from its CELLS (not the summary the file carries) all hold; and `languages_ok` lists all 19 locales, each within 5 points. Any problem is a named code and a sentence.

**Why only scenarios in all 19 locales are scored.** The bar compares each locale with English on the same questions. A scenario run in English alone would lower English's score and nobody else's.

**What is staged and what is real.** Real: the intake path, the gate, the answer gate, the context assembler (its caps, its cut order, its chart rule), the checks, the composer, the quota meter, the ledger's rules (over its model), the stores' validation. Staged: the clock, the Understand answer (and its reported cost of 300 micro-dollars), the market database (a seeded day of bars moved to end at the cycle's price), the chart in storage (the matching one by default, another cycle's or none for the scenarios that say so) and the answer model.

## 6. Decisions and readings of mine

1. **34 scenarios, not "about 24 to 30".** The count the order and §7.7 give is a floor; the extra are the second trader type's cells (a scenario is a cycle; each runs for both trader types), the two split rows (row 1 refuses a direction and still answers Explain; row 6 has "one model down" and "both down"), the DELAYED overlay and the demo. `golden-tool.js` holds 24 as the minimum. If you want fewer, `D01b`, `D06b` and `O01` are the three to drop; M01 is needed by the demo.
2. **The cost of a live run is larger than D25's figure.** The plan said about 570 calls per model per pass (30 scenarios x 19); the set is 680 cells a pass, **634 written by the model under test** (the staged failures replay from scripts and cost nothing), so two passes are about 1,270 calls per model. `eval-run.js --estimate --model` prices it from the registry once S1 has written a price; **you set the cap** (`--cap-usd`, required, at most 50). Passes can be 1 for a first look (`--passes 1`), and `--scenarios`/`--locales` run a part; a part does not pass the gate.
3. **A language's score counts only the scenarios the model writes in all 19 locales** (the 16 cycles x 2 trader types, DELAYED and the demo: 34 runs per locale). The degraded scenarios that call the model (row 2, row 3, row 4, row 5, row 8, row 9, the Explain answer) run in English only and count in the other bars, not in the language comparison.
4. **The stand-in's replies are language-neutral except two things.** The rationale and risk lines are `MCD2 · MCD2_UP_IN_CORRIDOR` (a stand-in does not pretend to translate a sensor); the headline ("Price near {LAST_PRICE}, inside the day range ...") and the invalidation line are written in the 17 languages, **my drafts, read by nobody**. They are why the Free recording reads thin.
5. **The Free recording is one turn, an M5 instant prompt, and a trader sees nothing until it is approved AND live.** One turn because an instant prompt has no question text to translate (the user bubble is the dictionary's own "Inspect the M5 chart"); a conversation would need 17 translated questions of mine. And **the order says "store approved demo scenario replies"**: nothing in this part can be approved by me, and a recording of placeholder sentences must not reach a trader whoever signs it, so the rule has two parts (`shownToTraders`: `approval.json` APPROVED and `source.kind === 'LIVE'`). The path to a visible demo is S2 (a live run), `record-demo.js record --run <live run>`, S5 (read in 19 languages) and your signature. If you want the stand-in shown to Free users in the meantime, that is one boolean in `demo-source.ts`; I recommend against it.
6. **Rows 9 and 10 of §7.6 are Engine 4's.** D09 holds the reply path's half (the calendar block says it is late and shows its age); D10 holds that the chat only opens the modal (the outcome is the Trade Setup action; the offer check that refuses stale specs is Engine 4's `checkOffer`, held by its approved worked examples 08 and 09). I did not duplicate Engine 4's logic into the reply suite.
7. **"Quota exhausted" is a small positive allowance** (30,000 units: it cannot cover the worst case, so the refusal carries the balance); an unset allowance refuses everything with no balance (part 7's own test). The scenario's expectation is `QUOTA_INSUFFICIENT` with the balance shown.
8. **The refusal code is `QUOTA_INSUFFICIENT`**, the name the intake contract has; my first draft of the scenario said `QUOTA_EXHAUSTED` and the first run showed me the real name.
9. **A typed cell's units hold a fixed 300 micro-dollars for a fake Understand call.** Only instant prompts are clean measures of cost; the real Understand cost is in S8's traces (runbook S3 says so).
10. **The harness is test support and the scripts import it.** `scripts/reply/eval-run.js` loads `__tests__/lib/reply/eval/helpers/harness.ts` through `tsx` so the live run exercises the same orchestrator world as the gate test. The alternative (moving the world into `lib/`) would put test doubles into the production tree.
11. **`golden-tool.js`, not `golden.py`.** The order allows "or Node equivalent"; the `wording-tool.js` and `prompts-tool.js` pattern is Node and a Jest test can run it with no Python.
12. **Rolling back is a redeploy.** The plan said "rollback is a flag, not a deploy". True of the code and the data (nothing is reverted, no migration), but a Vercel environment variable applies to the next deployment, so "unset `REPLY_ENABLED`" is a redeploy of the same commit (a few minutes; I have not timed one). The runbook says so in its rollback table. Nothing in the repository switches the chat off faster.
13. **S8 leaves `INTAKE_INSTANT_PROMPTS_ENABLED` unset** (the order's S9 lists it with `REPLY_ENABLED`; its S8 is the allow-list). It is a global switch of the chart badges and not part of the allow-list: on for the staging week, every Pro trader's badge would post to a route that refuses them. It goes on at S9.
