## 6. Decisions for Davin (readings of mine where the plan or the order was silent)

I built each as the default and will change any of them on your word.

1. **A refusal is `success:false` with an `intake-refusal/1`, and its status says whose to fix.** The body is `{ success: false, error: { code, message }, refusal, trace }` and the chat shows `refusal.reply`. Statuses: 401 not signed in, 403 tier, **422** the thread, an empty or over-long question and **a question that is out of scope**, 409 profile not set, **429** quota, 503 the feature (a port failed) and a failed understanding, 404 the flag, 400, 413 and 415 for a body that cannot be read. Out of scope is a refusal and not a 200 so that every answer without a packet looks the same to the client; if you would rather a client see 200 for it, it is one line in `server/errors.ts`.
2. **The interface language is the server's language cookie** (`getServerLanguage`, the resolution the pages already use), read once and only when something needs it; a value that is not one of the 19 becomes `en-US`. **A body never names a language, a user, a tier, a symbol or an intent**: each reader builds a new object from named keys, and tests send forged ones.
3. **The body is read after the flag, the session and the tier**, at most 8 KiB. A refusal at any of the three never reads it (tested with a body that would be 415, 413 and 400).
4. **The instant route has one lock, `INTAKE_ENABLED`.** `INTAKE_INSTANT_PROMPTS_ENABLED` is the UI's flag (`isInstantPromptsEnabled` in `server/access.ts`, for part 10); making it a second lock on the route would make the route and the button disagree.
5. **The Understand adapter (D4 A): OpenRouter through `fetch`, no SDK.** The model is named by `INTAKE_UNDERSTAND_MODEL` (**no default**, so no model id in the code can go stale), the key by `INTAKE_UNDERSTAND_API_KEY`, the base URL by `INTAKE_UNDERSTAND_BASE_URL` (default `https://openrouter.ai/api/v1`; https, or http on this machine). It asks for a JSON object at temperature 0, `max_tokens` 700 and `provider.data_collection: "deny"` (ADR-077); **whether the provider keeps that promise is for the part 9 run and the privacy notice, not shown here**. Not configured: a typed question gets `UNDERSTANDING_FAILED` (a retry cannot help; `FEATURE_UNAVAILABLE` would be truer, and is a one-line change); an instant prompt needs no model and works.
6. **The contract the knowledge service must implement (part 6).** `POST {KNOWLEDGE_SERVICE_URL}/search`, header `x-knowledge-service-key`, body `{ schema: "knowledge-search/1", intent, question_en, m_star, state_codes, routing_version }`, answer 200 with `{ status: "OK" | "EMPTY" | "UNAVAILABLE", index_build_id, chunks, expansions }` (exactly the packet's `knowledge` section; anything more is refused whole). **The service reads the domains and the D2 scoping of each intent from `dispatch-matrix.v1.json`**, not from the request (part 4's reading 14); `state_codes` are those of the sensors in M\*, in M\*'s order. I did not send the synthesis rule id; if the D3 chunks want it, it is one field. A 503 from the service is an UNAVAILABLE pack; the client waits two seconds and follows no redirect.
7. **Every port fails closed.** A session that cannot be read is "not signed in"; an entitlement, thread, profile or quota port that throws is `FEATURE_UNAVAILABLE` (503), never an allowance; a stored profile that no longer passes its validator is `PROFILE_NOT_SET` (confirming it again fixes it) and a profile database that cannot be read is `FEATURE_UNAVAILABLE`. The port that failed is a CODE in the trace (`QUOTA_PORT_ERROR`), never a message.
8. **The thread (D6 a):** the default adapter accepts no thread, or an id that matches the packet's own rule (letters, digits, `_`, `-`, 1 to 64); it cannot tell whose it is, because no store exists. A thread of another trader will be refused when step 7 has one.
9. **The quota (D5 A):** the default adapter allows everything. **Nothing may turn `INTAKE_ENABLED` on in production before step 7 meters** (the part 10 runbook says so); until then the gate is proved with a fake that refuses.
10. **Question flags.** `question.flags` carries `TERM_DROPPED` (the model's English lost a glossary term) and `AMBIGUOUS_NUMBER` (the normaliser left a number as typed), sorted; a signal for Section 5 and the trace, never a refusal.
11. **The terms of an Explain question** are the glossary terms the question names **in the language the model says it is** (the part 2 term-preservation list), so a French "or" in an English sentence is not gold.
12. **The calendar.** An events port that throws is an UNAVAILABLE calendar (`EVENTS_PORT_ERROR`), never "no news"; the reader's own UNAVAILABLE is `EVENTS_UNAVAILABLE`; rows it left out are `EVENTS_ROWS_LEFT_OUT` (a bug found by my own test: an unavailable calendar was also reported as "rows left out").
13. **STALE and UNKNOWN (4.11 item 8).** The packet contract has no field for "direction withheld", so none was added: the data block is built in its own stage (`DATA`) before the board, the route, the retrieval and the assembly, with the status in it and in the trace (`DATA_STALE`, `DATA_UNKNOWN`), and the packet is still built (plan: "a stale cycle is a packet with `data.status = STALE`"). That Section 5 gives no direction on it is step 7's rule and reads `data.status`.
14. **The trace** is snake_case like the packet, returned with every answer (refusals and errors too), and carries no user id, no text the trader typed and no secret.
