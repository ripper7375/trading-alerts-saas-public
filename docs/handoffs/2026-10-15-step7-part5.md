## 5. How it works (for the approval)

```
packet (intake) + model + dictionary + chart port
  -> evaluateAnswerGate   data status row, intent fits?, Report 2 column     refused -> fixed answer, NO model
  -> resolveShape         REPORT_2 -> action (no model) | no synthesis -> fixed answer | REPORT1 | ANSWER
  -> readChart            (only if the gate allowed one, a question called for it, the tier and the model allow it)
                          HEAD stamp -> chartMatchesCycle -> GET -> the object's own stamp -> chartMatchesCycle
  ... part 7: assemble, reserve, model, runChecks (part 4) ...
  -> composeReport1Result  flag unverified numbers -> fill {id} -> six sections -> envelope -> validateReplyResult
     composeAnswerResult | composeFixedAnswer | buildActionResult
```

**The data stamp is not a sentence.** `stamp.as_of` is the cycle slot (for a stale reply, the time the data stopped), `stamp.data_status` says FRESH, DELAYED, STALE, MARKET_CLOSED or UNKNOWN, `retuning` and `flags` say the rest. The interface words them.

**A figure reaches a trader one way.** The model writes `{MCD2.baseline}`; `resolveText` finds it in the dictionary of the cycle (only an entry the prompt offered), writes it in the locale's notation, and fails the whole text if it cannot. A literal the model typed anyway was judged by the number check of part 4; if it stayed wrong after the one regeneration the composer replaces it by the "not verified" mark of the language, and counts it in `checks.numbers_flagged`.

4. **MARKET_CLOSED answers everything but Report 2.** A direction question gets the last session's report labelled by the stamp (5.3 row 4); Report 2 gets a fixed answer with reason `MARKET_CLOSED` instead of opening a modal that would explain the same thing (Engine 4's offer check has its own `MARKET_CLOSED` row for the case where the modal is opened some other way).
5. **A STALE or UNKNOWN fixed answer shows the sensors' last states and NO prices.** A price of data that stopped is the most dangerous thing to hand a trader. With a live cycle and no synthesis reading it shows the sensors' levels and no direction.
6. **Report 2's zone ids come from the caller.** The packet of a REPORT_2 request carries no readings (Section 6 reads the pinned cycle by id), so `resolveShape` takes the stored zone ids as an argument, falls back to the packet's synthesis zones, and otherwise gives an empty list. Part 7 reads them.
7. **The chart rule's inputs that are not mine to compute:** `tierAllows` (the entitlement table is part 6), `firstOfCycle` (the thread's history is part 7), `modelVision` (the registry). They are plain arguments of `readChart` and `chartCalledFor`. The image goes to the gateway as a `data:` URL (the gateway accepts https and `data:`), with a reference the assembler's chart slot carries; **how many tokens the image costs is left to the orchestrator** (the assembler takes `ChartInput.tokens`; 5.4 caps the chart at 1,500).
8. **The chart is read in two steps on purpose.** The HEAD is cheap and drops a chart of another cycle without downloading it; the GET returns the object's own metadata, and that stamp is judged again, because the renderer replaces the object every cycle and a swap between the two calls must not put another cycle's picture in front of the model. `lib/reply` imports no AWS code: the port is handed in (`getChartStamp` and `getChartImage` fit it).
9. **Number styles.** My own table of the decimal mark and the thousands separator of the 19 locales (point and comma for English, Asian languages, Arabic, Urdu and Hindi; comma and point for the Latin-script languages of Europe and Latin America, Turkish, Vietnamese and Indonesian; comma and a narrow no-break space for French), not `Intl`, because the output must not depend on the ICU data of the machine (Node 20 and 24 differ). Digits are always ASCII. No currency sign is written (its place differs by language; the number check reads a bare figure). A percentage and a ratio have at most two decimals with no trailing zero; a time is `hh:mm UTC` on the cycle's own day and `yyyy-mm-dd hh:mm UTC` on any other. All of it is a draft for the native readers.
10. **The resolver is strict.** An id that exists in the dictionary but was never offered to the model (a match-only entry such as a distance) fails like an unknown one: the schema check of part 1, run with the dictionary's addressable ids, would have refused it before, and the resolver does not trust that it did.
11. **Levels are quoted by their id in the dictionary, and only if the dictionary holds that id at that price.** The packet has no `context_levels` (the bundle does, the packet does not), so the context levels (support and resistance, `sr_*`) are the ones the stored zones lean on: their invalidation level, their next opposing level and their confluence, whose origin is not a sensor (a sensor's own levels are listed from its envelope). They are named by the dictionary's ids (`Z1.next_opposing`, `Z1.invalidation_level`, `Z1.confluence_2`), a level two zones name is listed once under the first zone in rank order, and at most 40 are kept (the ones nearest the last price). Highest price first.
12. **The invalidation line is the server's sentence in 17 languages** (`invalidation-line.v1.json`), neutral about the side ("beyond"), with the price filled by the same resolver. It is added only for a chosen zone that no `watch` line covers (the structural row of D12; `missingInvalidationLines` of part 4 names them). My own checks accept every sentence in its language: no banned phrase under any of the four readings of the synthesis, and the price is read back and matched.
13. **News.** The packet's calendar block is copied as it is: its status (so an unavailable calendar is said aloud), its age, its events with `approximate` (the intake reader sets it when the calendar's `time_mode` is not exact). **The packet carries no forecast value, so there is nothing to call "not published"**; the order's "null forecast" sentence has no data to attach to until the packet carries one.
14. **The composer also builds the short answer and the action.** The order lists the Report 1 composer and the fixed answer; the shape resolver names `ANSWER` and `ACTION`, and the resolver and the envelope are right there, so `composeAnswerResult` and `buildActionResult` are included (tested, mutated). An action the model asked for is kept only if the gate lets Report 2 open and a cycle is pinned; the cycle, the trader type and the zones are the server's.
15. **`stateChanges` yields structure only.** A sensor that gained or lost its state is a change with `null` on one side; a status that moved while the state code stayed is not a change; the same cycle, a first message, an earlier cycle with no sensors, and a sensor whose reading could not be believed on either side give nothing for that sensor (unknown is not absent).
16. **Direction reading.** The `archetype` of a reading may be missing (taken as none, as the intake path never checks it); the `trend_relation` may not (the intake path's own facts refuse it, so the composer does too). A reading with a malformed field is `BAD_SYNTHESIS`, not repaired.
17. **The disclaimer is the version `disclaimer-1`;** the fixed text per language is part 8's, for counsel.
18. **Two files are named `shape.ts`** (`contracts/shape.ts` of part 1, the grammar of a model text, and `gate/shape.ts`, which reply a request becomes). The order names the second.

## 8. Problems and surprises

1. **The contract of part 1 had no place for three things the order asks the reply to do.** Found while writing the first test of 5.14 item 4 (where does "the reply says so" go?). Section 6, item 1.
2. **`inline()` quotes a name that starts with `_`** (`levelsOf` returns `"_hidden"` with the quotes), so such a level fails the name check and is left out, which is the safe outcome; the names that need the `lvl_N` fallback id are the ones of 33 to 40 characters. My first test assumed the other.

Writing the checks as one list of failures removed them.
