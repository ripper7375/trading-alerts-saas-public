## 6. Decisions for Davin (readings of mine where the plan or the order was silent)

I built each as the default and will change any of them on your word.

1. **The chunk limit that binds is 4,000 characters, not 1,500 tokens, and the dense vector sees less than a chunk.** The packet refuses a chunk over 4,000 characters (`KNOWLEDGE_CHUNK_MAX_CHARS`), and 4,000 characters of English prose is about 900 word pieces, so "split over 1,500 tokens" never fires on its own; the chunker enforces both limits (a `fits` test on tokens **and** UTF-16 length, the unit JavaScript counts in). Separately, txtai's pooling window for this model is the tokenizer's 512 tokens, not the 256 of the model's `sentence_bert_config.json`: a chunk of 513 to about 900 tokens is embedded from its first 512 only (the keyword index sees all of it). The build reports each such chunk as a warning (`OVER_DENSE_WINDOW`; the test corpus has two). **For you:** keep 1,500, or lower the split to about 450 tokens so a whole chunk is embedded? It changes how parts 7 and 8 are written, and the plan's "200 / 1,500" is yours.
2. **The build id is `kb-` + the first 32 hex digits of the SHA-256**, 35 characters. The packet accepts an `index_build_id` of at most 40 characters (`VERSION` in `packet.ts`), so the whole 64 digits would have made every OK pack invalid. The full hash is in `build_metadata.json` (`index_build_sha256`).
3. **A front-matter `id` must start with a letter or digit** (`^[a-z0-9][a-z0-9_.-]{0,63}$`); the order's pattern `^[a-z0-9_.-]{1,64}$` also allows `_x` and `.x`, which would give a chunk id the packet's pattern (`^[A-Za-z0-9][A-Za-z0-9._:-]{0,79}$`) refuses, and one such chunk makes the whole pack UNAVAILABLE at the monolith. `mcd_id` is checked against the registry list (MCD0 to MCD3), which is stricter than `^MCD[0-9]+$`.
4. **One front-matter block per file; chunk id = file id + "." + the slug of the chunk's first heading** (`d2.mcd1.playbook.sustained-breach-above-the-upper-band`, a repeated heading gets `-2`), and `related` lists chunk ids that must exist (a dangling one fails the build). The plan says "front matter on every chunk"; the order says "extract front matter from `.md` files", so the tags describe the file and each chunk inherits them. If part 7 needs different `state_codes` per section, it means one file per state, or a per-section override added then. A title line (`# ...`) stays with the first section.
5. **The intent templates are mine.** ADR-043 says "intent template + state codes + question" and gives none; `config/index.yaml` has ten short English phrases (`DIRECTION`: "market direction bias synthesis counter-trend stand aside" ...). They steer both halves of the search, so they belong to the recall test of part 9 and to your read; they are part of the build id.
6. **Expansions obey the same scope as the hits.** A chunk named in `related` is added only if it is in the intent's domains or is a playbook of a sensor in M\*; so a Direction answer for `m_star = [MCD1]` never pulls in an MCD2 playbook, or a D1 foundation, through a cross-reference. The 4.7 text does not say; the safer reading is built, and `Retriever._in_scope` is the one place to relax it. The budget rule is skip-and-continue: an expansion that does not fit does not stop a smaller one behind it.
7. **A sensor id or state code the registry does not list is dropped silently** (and is in the plan's `dropped_*` for the log), not answered with a 4xx. A hostile id therefore gives the answer of an empty `m_star`. The request model bounds lengths (64) and counts (16 and 32) and nothing else about their content.
8. **The wording backstop is context-free and a bare percentage passes.** A negated "not a guarantee" fails; "outcomes are never certain" is the way to say it. "82%" alone is not caught (D4 and D5 prose legitimately says "half risk is 50%" and "the 5% filter"); "an 82% chance" and "a probability of 0.7" are. `no risk` and `zero risk` are caught, so "no risk limit" would be too. The list is mine (six rules, `wording-1`, part of the build id); it needs your read before part 7 writes under it.
9. **The candidate window stays 40 (D11 (c)) and its limit is shown, not fixed.** `similar(:q, 40)` takes the best 40 of the whole corpus, then the SQL filters; a test shows that with a window of 1 an out-of-scope best hit hides the in-scope chunks. For a corpus of 100 to 300 chunks 40 may miss; the recall test of part 9 decides, as D11 says, and the change is one number.
10. **Two files of the monolith are copied into the service** (it is built alone on Railway): `dispatch-matrix.v1.json` byte for byte and the glossary's `version` (`1.0.0-draft`), by `scripts/intake/sync_knowledge_config.py` (`--check` is a test). A change to the matrix without a sync fails the Python suite; the service prefers its own copy, then the repository's. The glossary version is a label: an edit that keeps it does not change the build id.
11. **A corpus folder holding a `TEST_ONLY` file is a test corpus**: its index says `corpus_kind: TEST_ONLY` and `gate build --require-real` (the Dockerfile) refuses it. The marker is how "never mixed with the real `corpus/`" is enforced and not only promised.
12. **A D2 chunk must name its sensor** (`mcd_id`), or no scoped search could ever find it; and a state code listed under an `mcd_id` must belong to that sensor. D1, D3, D4 and D5 may name one or none.
13. **The service answers**: no key or a wrong key or a service with no key configured: 401 (fail closed), checked before the body; `/healthz` needs no key and shows only the build id; an unknown intent: 422; another routing version: 409. The monolith turns any non-2xx into an UNAVAILABLE pack with `KNOWLEDGE_HTTP_<status>`, so these codes are for the trace and for people. A failure of the search itself is 503 with the UNAVAILABLE pack and the process stays up.
14. **The model revision is the commit that was the head of the repository on 2026-10-13** (`1110a243fdf4706b3f48f1d95db1a4f5529b4d41`, Apache-2.0 per the model card's metadata), and only its `safetensors` weights and small files are fetched. I could not compare it with the revision the plan's author had in mind; it is one line in `index.yaml`.
15. **`gate check` runs two checks on the index, not one**: the fusion identity (with the cosine check, section 7) and "every chunk found by its own text in the first three". A deploy that cannot show both fails. The self-retrieval part searches once per chunk; its time on a corpus of a few hundred chunks is not measured (on the 15 chunks of the test corpus `gate check` took 8.4 s in all, nearly all of it importing txtai and loading the model).
16. **The pins:** direct dependencies exact; `numpy`, `tokenizers`, `safetensors`, `huggingface-hub`, `pydantic`, `starlette` exact too because they decide the numbers or the request shape; the rest float. `pytest` and `httpx` are in `requirements.txt` as the order lists them, so they are in the image (small, but a reading: a second file for development would keep them out).
17. **The recorded answers** (`tests/fixtures/contract/search-responses.json`) are a snapshot of the test corpus's answers, kept so the Jest suite can read what the service really sends. Regenerate with `WRITE_CONTRACT_FIXTURES=yes pytest tests/test_contract.py` after any change to the fixture corpus or the retrieval; the Python test checks statuses and chunk shapes, not ids, so a change of platform does not break it.

## 7. Problems and surprises

- **The pins I first wrote could not be installed in the image.** `requirements.txt` was first the freeze of my Windows venv on Python 3.14, where `numpy==2.5.4` resolved; numpy 2.5.x has **no Python 3.11 build** (`pip download --python-version 3.11` said "No matching distribution"). The image would have failed at `pip install`, far from where anyone was looking. Now `numpy==2.4.6`, the newest with a 3.11 wheel, and the whole file resolves for Linux/3.11 (4d). A standing fact in the gotchas file, with the command.
- **A passing "fusion = w·dense + (1−w)·keyword" check cannot tell normalised scores from rank fusion** (found by the test I wrote to show a `normalize: false` index failing, which passed): under rank fusion txtai's dense-only result is `1, 1/2, 1/3 ...` and the fused result is the same linear mix of two rank lists. The check now also requires the dense-only score to be the model's own cosine similarity (`embeddings.similarity`); that one fails on a rank-fused index. Without the second line the pin test of item 6 would have been green with the setting wrong.
- **My assumption about a test question was wrong because the template is part of the query**: I took the best hit of the bare question as the best hit of the search. The window test now asks the index with the plan's own query text.
- **My process-measurement harness hung the service**, and I first read that as a defect: the server's output went to a pipe nobody read, so its first log line blocked it. By hand (and with the output in a file) the first request takes 91 ms. Not a service defect; the first run also left a server running, which a second run then measured (a launcher process of 4.5 MB). Both are fixed in the harness; the figures in 4d are from the clean run.
- **The Python-backed Jest suites skipped silently again**: my first `jest` run put `C:/...` on the PATH, which Git Bash ignores, so `python` was the dead Store alias and 4 suites (273 tests) were "skipped" with a green summary. Caught by the 16-second total and the skipped count (the gotchas file says glossary-tool alone takes about 110 s); rerun with the `/c/...` form. The figure in section 3 is of the rerun.
