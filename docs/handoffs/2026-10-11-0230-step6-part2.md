## 6. Decisions for Davin (readings of mine where the plan was silent)

**If you say nothing, each stays as built.** The first four affect what traders see or what is refused.

1. **The door counts UTF-16 code units, and has a second limit.** The typed question may have 500 (the packet validator's unit, plan A5); it is measured before anything else runs, so a huge body costs one comparison, and a question of 501 spaces is "too long", not "empty". After normalising it may have 1,000 (a new constant `NORMALIZED_MAX_CHARS`): NFKC widens one character into up to 18 (U+FDFA), so 55 of them are 990 characters and 56 are refused. An over-long question is refused, never cut (§5.4).
2. **Numbers are never guessed.** `4,377.99`, `4.377,99`, `4 377,99`, `4'377.99`, `1,234,567`, the Indian `12,34,567`, the Arabic `٫` and `٬`, and a decimal comma (`0,75`, `4377,99`) become `4377.99` form. A number that could be read two ways is left exactly as typed and the text gets the flag `AMBIGUOUS_NUMBER`: `4.377` and `4,377` (German or English?), `1,000`, `10,500`, `2.500`, and `4400,4450` (one number or two prices). A space as a thousands mark merges a group of one to three digits with a group of three (`2 500` is 2500, `5 300` is 5300), but never when glued to a Latin letter (`M5 300` is untouched). **The risk:** a model reading `4.377` in a German question may still write 4.377 in English; the flag lets part 5 say so.
3. **Everything invisible is removed, not only the zero-width spaces:** every control character (except white space), every format character (zero-width joiner and non-joiner, bidirectional controls, the soft hyphen, the Unicode "tag" block that can carry hidden text), variation selectors and lone surrogates. **The cost:** the joiner and non-joiner are meaningful in a few Persian, Urdu and Indic spellings; the glossary forms go through the same step, so matching is unaffected, but the model sees the text without them. NFKC also rewrites a Thai sara am into two characters (the same on both sides).
4. **Scope is strict, as the order says.** A question that names gold AND another symbol or timeframe is out of scope ("gold and BTC", "M5 against H1"). A duration counts as a timeframe: "the last 2 hours" is H2, "10 minutes" is M10, "daily" is D1. A bare `USD` is not a second symbol (it is gold's quote currency); `DXY`, `EUR`, `XAUEUR`, silver and the rest are. Anything the model returns that the check cannot read as gold or as M5/M15 (`swing`, `5`, `XAUUSDT`) is refused, and so is the model's own `OUT_OF_SCOPE` label. **Known false positives:** `M2` (money supply) reads as a 2-minute chart, `D1` as daily (so a question that says "D1" meaning the corpus domain), and "1.5 hours" is not read at all. **Known limit:** a symbol or timeframe written in another script is found only if the model reports it.
5. **The glossary file contract `glossary/1`:** per term `id`, `en`, `en_variants` (other English wordings that count as the term), `definition`, `owners` (sensors `MCD0` to `MCD15`, `SYN` or domains `D1` to `D5`: what the Explain intent routes by), `never_translate`, and `forms` per locale (`en-US` required, one canonical form, variants, `status` draft or approved). A form needs two characters once normalised; two terms may not share a spelling in one locale; a never-translated term has one form, its English spelling. The validator reports every problem with its path.
6. **Spotting is language-blind, by design,** because it runs before the model says what language it is: a text is searched for the forms of all 17 languages at once and each hit says which languages have the form. Boundaries depend on the script (whole word for Latin, Arabic with its clitics, Devanagari and the rest; start of word for Korean; none for Chinese, Japanese and Thai). **Known limits:** Thai and Japanese find a term inside a longer word (`ทองแดง`, copper, finds `ทอง`, gold); Turkish suffixes defeat whole-word matching unless the glossary lists the inflected form; the French `or` (gold) is also the English word, so it is hinted in English sentences (harmless: the preservation check ignores hits of another language).
7. **Term preservation:** a spotted term must have its English term, or one of its listed wordings, in the English text as whole words (`stop-loss` equals `stop loss`; case ignored). Only hits that belong to the language the model reports count (all of them for `und`); a level name (`UOEDT`) counts in every language. The result is a signal (`TERM_DROPPED` in the report), never a refusal.
8. **The Understand step.** The question travels as a JSON string field of the user message, never inside the instructions; the system prompt says it is data. The answer must be exactly one JSON object (a code fence or any prose around it is `NOT_JSON`; a real adapter should ask the provider for JSON mode). One call, no retry (the adapter's job, D4). The English text is normalised before use, and refused if it is nothing afterwards or longer than 1,000. **The validator is stricter than the JSON Schema in three places, on purpose:** an English text of white space only; the English limit in code units (the schema counts code points, the packet counts units); a symbol or timeframe with a trailing line feed (Python's `$` allows it). `understand-parity.test.ts` pins all three. `scanText` can run before the model (to save a call); the fixed reply then has only the interface locale to go on.
9. **The barrel** exports the `text/` values and types (all pure); `understand-fixture.ts` and the lists of `scope.ts` are imported by path.
10. **Edits to Part 1 files:** `version.ts` (one constant), `index.ts` (exports), `boundaries.test.ts` (the new files and the one JSON import), and `schema-parity.test.ts`, whose labelled `understand-result/1` cases moved to a shared helper so the schema and the code are tested against one list (same cases, same expectations).
