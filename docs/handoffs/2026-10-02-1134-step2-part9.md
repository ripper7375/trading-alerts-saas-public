## READ THIS FIRST: the order's definition of `repush_rows_unsent` cannot reach 0 on the real VPS

I built it as ordered (decision 1 below has the options). Everything in this part works and is tested, but **RETUNING started by a real promote would not end**, because of how the collector behaves today:

- `promote_cycle()` writes every bar of the window with `INSERT OR REPLACE` and does not list `synced_at`, so after **every** cycle (promote or not) all ~3,000 M5 rows (and the M15 rows on a refresh slot) are unsent again (`export_collector_validator_v2.py:1447`; `PUSH-WORKER-THROUGHPUT-OPEN-ISSUE.md` §1a).
- The manifest is built **once per slot, right after the cycle's newest bars were sent** (`queue_manifest`), so at that moment the unsent rows older than `slot - 300` are the whole rest of the window: about 2,700 M5 rows at least, 5,997 in the fixture world. Not 0, whatever the worker's throughput.
- `test_the_collectors_full_requeue_leaves_the_whole_window_unsent_at_manifest_time` pins this on the sender's own passes (the count stays above 5,000 after a full drain and a re-queue) and fails the day the collector changes.

So the gateway will see `repush_rows_unsent` of thousands in every manifest, and the state machine (correctly, per ADR-015) keeps RETUNING. **Nothing reads `retuning` yet** (the `cycle-ready` job has no consumer until step 3), so nothing is harmed today. It must be decided **before step 3 reads the flag**, or every cycle after the first promote is CAUTIONARY for ever. A second finding bears on the same decision: with ADR-013's newest-bars-first order, the bars sensors read (the newest 288 M5 and 96 M15 closed bars) and the statistics at the slot are re-pushed **in the promote cycle's first pass**, so they are already new-tuning when that cycle goes READY. What stays old-tuning for minutes is the older part of the window, which no sensor window reads.

## 2. Deviations from the order (and why)

Live code and evidence won over the order's wording where they disagreed (non-negotiable 7). Each is small and reversible; confirm or say which to undo.

1. **Promote detection compares with the previous cycle only; M15 is, in practice, never compared.** My first version compared M15 with the latest earlier cycle that carried it. The full-sequence test showed the flaw: a real promote retunes M5 at slot k, and the new M15 hashes only appear at the next refresh slot (k+1 to k+3), where they differ from the last M15 on record, so one promote fired a second PROMOTE and started RETUNING over. The order says "the previous cycle", and M15 is absent from the cycle before every refresh slot, so it is not compared. Consequence: **a reconfiguration of the M15 indicators alone (terminal and M5 untouched) is not detected.** A promote always changes the terminal, so none is missed. The rule is in the header of `retuning.ts` and pinned by tests.
2. **The RETUNING flag is written on the row at the first look (PENDING), not only at READY.** A manifest job that exhausts its retries leaves its row PENDING for good (the known part 4 limit); without the early write the next manifest would read "not RETUNING" from it and a promote would silently end. Written only when true, so ordinary cycles make no extra write.
3. **"The next verified manifest" is read as: state READY (the landed-row check passed).** The manifest that reports 0 does **not** have to be verified itself (ADR-015: "reports 0 ... followed by one verified manifest"); a zero from a cycle that went INCOMPLETE still counts, and the next READY cycle ends it. The stricter reading (the zero must also be verified) is one condition away; recommend keeping the literal one.
4. **A manifest that arrives behind a newer one writes no events** (not in the order). The push worker sends manifests newest slot first, so after an outage an older one can arrive after a newer one. It still gets its own flag, but a second PROMOTE or RETUNE_COMPLETE for the same physical promote would be a false record. Costs one query, and only when there is an event to write.
5. **`RETUNE_COMPLETE` is written before the PENDING to READY update, not after.** That update is the commit point: after it a retried job returns early, so an event written later could be lost. Cost: if a job fails after the event and then exhausts its three retries, an event exists for a cycle that stayed PENDING, and a later cycle may write a second `RETUNE_COMPLETE`. Rare, and the PENDING-forever row is already a known limit; a transaction would close it but this gateway uses none yet.
6. **A promote wins over a RETUNING that was about to end**: a promote while RETUNING starts it over, and the earlier zero does not end it (tested).
7. **`repush_rows_unsent` is built exactly as ordered** (unsent rows with open time before `slot - 300`, 0 when none). See the section above: that is where I kept the order against what the live code shows.
8. **The contract file's text changed, its fields did not** (the description of `repush_rows_unsent` said "not sent by this version of the sender"). Because the gateway's copy and four fixtures derive from it, the fixtures were regenerated with `scripts/generate_cycle_manifest_fixtures.py` (the corpus is 100 cases, was 96: four new cases for the field), and three specs that assumed the field absent were updated.
9. **Runbook §4 was wrong since part 3** (it still said the newest bars change last) and is corrected, with a new subsection; the order did not ask for it.

### How a promote moves through the gateway

The manifest arrives and its row is created PENDING. The service reads the latest earlier cycle (any state) and compares terminal, hashes and modes. **Changed:** one `PROMOTE` row in `cycle_events` (`XAUUSD_PROMOTE_<slot>`, effective slot = the manifest's slot, terminal, hashes, modes, and what they were before), and the row is flagged RETUNING at once. **Not changed, but the previous cycle was RETUNING:** RETUNING continues; if the previous cycle reported exactly 0, this manifest, once verified, ends it: `RETUNE_COMPLETE` (`XAUUSD_RETUNE_COMPLETE_<slot>`) is written, then the cycle is announced with `retuning: false` and the row marked READY with the same value. A manifest without the count never ends it.
