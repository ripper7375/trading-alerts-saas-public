## 6. Decisions for Davin (readings of mine where the plan or the architecture was silent)

I built each as the default below; say if any is wrong. None touches money or authentication, so none needs the separate sign-off of non-negotiable 5.

1. **The live data status comes from the gateway, not from a TypeScript copy of its rules.** `market_cycles.data_status` is only FRESH or DELAYED (a cycle "ready in time"); STALE and MARKET_CLOSED are computed by the gateway on every read from the market-hours gate (broker clock, GMT+2 or GMT+3 by the US daylight-saving window) and the age of the newest ready cycle. A second copy in TypeScript would drift. So `checkOffer` takes a `LiveDataStatus` and `parseLiveDataStatus` reads the gateway's `dataStatus` object; **a status that was not supplied, or is not one of the four, is `DATA_STATUS_UNKNOWN` and not an offer.** The plan's `read/cycle.ts` still reads "the newest market cycle" (it returns its slot, stored status and RETUNING flag for the caller's comparisons) but cannot say STALE. The alternative is a twin of `computeDataStatus` and `isMarketOpenXauusd` (about 100 lines and a DST table, with its own differential test).
2. **More than the empty list fails closed.** The plan fixed only "empty or unset Tier-1 list". I applied the same rule wherever "unknown" could become "offered": a Tier-1 list that cannot be read or **does not cover all four kinds** (CPI, Core PCE, FOMC rate decision, NFP: a list with three would stay silent through the fourth); a calendar that cannot be read or holds no row at all (5.3: an unavailable calendar is never "no news"); a synthesis that cannot be read, or is INVALID or STALE with a direction, or has a direction and no trend relation; no usable zone, a picked zone that is not the reading's, no newest price; no `symbol_specs` row, an unreadable one, one older than 7 days, one dated more than 5 minutes ahead of our clock (its clock cannot be trusted, and a far-future date would never go stale). Each has its own code (`NOT_OFFERED_ROW` lists them; the broker figures are "row 10", which the table does not have). Say if the incomplete-list rule is too strict for the days when you have ids for some kinds only.
3. **The window edges are inclusive, and an unknown `time_mode` is approximate.** A release at exactly 15:00 either side blocks; one second more allows. `time_mode` 0 is the only exact one; 1, 2, 3 and NULL (the column is nullable) get the 60-minute window.
4. **"A newer cycle changed the synthesis" means the newest reading of the same profile, from a later cycle, differs from the pinned one in its bias, trend relation, rule, branch or status.** It does not mean a different list of reasons or different zone prices (those move every five minutes). The answer is a third verdict, `REFRESH_OFFERED`, with the changes listed; rows 6 to 10 still win, so a refresh is never offered over a reason not to offer. A newer reading that cannot be read is reported by the reader and does not offer a refresh.
5. **"Price already past the zone's invalidation" uses the newest reading's reference price (the last closed M5 close, A2) and means at or beyond it:** `<=` for a LONG, `>=` for a SHORT. With a zone picked, that zone decides. Before a pick (Report 1's check), Report 2 is offered while at least one zone is still valid and the invalid ones are flagged (`offer.zones`); it is not offered when every zone is past. Zones on the other side of the reading are not its zones.
6. **Half risk is pre-set when the reading is CAUTIONARY or the cycle was RETUNING as observed (`retuning_observed`),** not as applied: with `SENSOR_RETUNING_ENFORCED` false the sensors are not CAUTIONARY yet 6.4 says "cycle RETUNING", and half risk is the safe direction.
7. **The style notice works both ways.** A counter-trend setup for a trend-following trader is the table's example; I added a with-trend setup for a trend-countering trader (`STYLE_WITH_TREND`), since "outside the trader's style" is the row's wording. "Both" never gets a notice.
8. **The calendar's age is the age of the newest observation** (section 7 item 1), and I named it that in the result (`newestObservationAt`). The 45-minute line is crossed at 45:01.

## 7. Problems and surprises

1. **`economic_events` is written only when something changed.** The gateway's processor says so: after the first sync the stream "carries only what actually changed". So the newest `captured_at` in the table is the time of the last change, not of the last export of the calendar, and nothing in the database records that an export happened. The plan's "calendar not exported for 45 minutes" cannot be measured from the table. What the code can say, and does, is how old the newest observation is; the blackout is not weakened by it (it applies from the last known schedule whatever the age). If the exact meaning matters, the exporter needs a heartbeat (a row or a table that records each export), which is a change on the VPS and the gateway, not in Engine 4.
2. **`lib/economic-events/queries.ts` can return a stale observation.** It filters rows by `event_time` and then takes the newest per `value_id` (`distinct`). A release that was rescheduled out of the window keeps an older observation inside it, and that older observation is what comes back. For a countdown that is cosmetic; for a safety decision it is not, so the blackout's reader first finds the releases with ANY observation in the window and then reads ALL their observations (a test shows both a release moved out and one moved in). I did not change `queries.ts` (outside this part) and wrote the trap in `database-traps.md`.
3. **There is no `ajv` in `node_modules`** (the two `"ajv"` lines in `package.json` are `overrides`), and adding a dependency is not mine to do. The Tier-1 parser is hand-written and a test runs it against everything the schema file states (required keys, no other keys, the four kinds, the id and name patterns, the version rules).
4. **None of the 31 golden zones is the last level on its side** (all have a next opposing level), so the adapter test for "nothing lies beyond" builds that zone from a real one.
5. **A CRLF slip cost half an hour of the mutation run.** I edited `offer.ts` with a Python `write_text`, which writes CRLF on Windows; Jest and `tsc` do not care, but the mutation harness asserts each mutant's line equals the file's and all four workers crashed at the first mutant of that file (149 of 597 done). I had checked with `grep`, which cannot see it in Git Bash (both facts were already in `environment-gotchas.md`; I repeated the slip). Found, fixed with Prettier (the repository's `endOfLine` is `lf`), and the whole run redone. Two bullets added to the gotchas file. I also ended my own shell once by stopping processes on a word my command contained (second bullet).
6. **Prisma's `Int` is 32-bit** (`event_time`, `captured_at`, `cycle_slot`): a query bound beyond 2147483647 (January 2038) is refused by the driver. `toDbInt` refuses it first with a message that names the bound. Not a problem for twelve years; written in `database-traps.md`.
7. **The first version of the future-date check, the sort of the reasons, the `in` checks and four other things were dead code** that the mutation check showed (section 4). They are gone; the tests that hold the behaviour stayed.
