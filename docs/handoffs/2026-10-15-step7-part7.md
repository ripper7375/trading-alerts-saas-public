## 1. Done in this session

**7a: the orchestrator.**

- **`runReply(request, ports)` (`lib/reply/orchestrator.ts`).** Seven steps: GATE (flag, session, tier, the body is read and a request already served is returned from the store, thread owner, profile, quota floor, then the HOLD), INTAKE (`runIntake` in process, no HTTP), ANSWER (the answer gate and the shape), MODEL (`runAnswerStep`), COMPOSE (Report 1 / short answer / fixed answer / action; the direction is copied from the synthesis reading by the composer), SETTLE (`hold.end`: the hold becomes the charge for what the paid calls cost, the rest is released) and STORE (the thread, the trace row and the two messages, all awaited before the run returns). It owns no route, key, database client or clock.
- **`lib/reply/run/`.** `types.ts` (the ports, the outcomes), `request-id.ts`, `hold.ts` (the quota hold, taken inside a wrapped gate quota port; duplicate and abort handling), `calls.ts` (a model call becomes a trace record; token and cost sums), `stages.ts` (the stage tracker and the evented trace recorder: GATE, UNDERSTAND, DATA, CONTEXT, MODEL, CHECKS), `answer-step.ts` (prompt assembly, the primary and fallback call, the schema, the number check and the wording check, the ONE extra call, the backstops, the deadline), `regenerate.ts` (the message the model is shown when a check failed), `trace.ts` (the trace row, built from what happened).
- **`lib/reply/server/`.** `ports.ts` (`createReplyPorts(env)`: the real ports; `requestBounds`, the worst case of a request of a kind), `store-ports.ts` (the thread, message and trace stores as ports), `flags.ts` (`REPLY_ENABLED`, `REPLY_ALLOWED_USER_IDS`, `allowListSession`).
- **Platform.** `lib/platform/chat/thread-port.ts` (the gate's thread check over the database, by owner) and `createThread` takes an optional `id` (the thread's id is made before the thread exists so the trace row can name it); `lib/intake/server/access.ts`'s `threadPort` is now the database ownership check; `lib/reply/meter/quota-port.ts` gained `settleOrRelease` (settle what the paid calls cost, release when none was paid).

**7b: the routes.**

- **`POST /api/chat/message`.** A JSON error with an HTTP status for every decision about who may ask (400, 401, 403, 404, 409, 413, 415, 422, 429 with the balance, 503); then, from the moment the gate has passed, an NDJSON stream of stage events (GATE, UNDERSTAND, DATA, CONTEXT, MODEL, CHECKS) and exactly ONE final event (`result`, `refusal` or `error`), delivered whole, never token by token (D24). A request served before is a stream of one event. A client that leaves before any model call gets 499 and nothing is charged; after one, the run goes on (the route hands it to `after()`), settles and stores. `maxDuration = 60`; the request's own deadline is 55 seconds, a call 25 seconds (primary) or 20 (fallback) (D23).
- **`/api/chat/threads` and `/api/chat/threads/[id]`.** `GET` list (newest message first, cursor pagination with a strict cursor), `GET` one thread with its messages, `PATCH` rename (the trader's title is never replaced by a derived one, D15), `DELETE` (the thread and its messages; the trace row stays, D16). Every store call has the user id in its `where`; a thread that is not yours and one that never was are one answer, a 404 `THREAD_INVALID` with the same body.
- **`GET /api/chat/state`.** The models that passed (none yet) with their MEASURED units per message or null, the balance (`configured: false` while `PRO_MONTHLY_UNITS` is unset), the trader's type and the cycle badge; a part that cannot be read is null and the rest is still answered.
- **Titles (D15).** A new thread is titled from the final answer: `XAUUSD · LONG · 18 SEP 20:55` (symbol, bias, slot).
- **The trace (D16).** One row per answer, written at completion, with zero question text, the keyed hash of the trader, the calls that were really made, what the ledger really charged, and the `risk` group left open for `attachRisk`. A request that was charged and could not be filed leaves an `ERROR` row.

## 5. How it works (for the approval)

**One request, in order.**

1. **GATE.** `REPLY_ENABLED` (404 for everybody otherwise), the session (`REPLY_ALLOWED_USER_IDS`, when set, turns a trader who is not on it into a Free one), the tier (the entitlement table), the body (read only now, and only the named fields are taken: `client_request_id`, `question` or `kind`, `thread_id`), the server's request id, a lookup of that id in `request_traces` (a request served before returns what was stored), the thread (owned by the caller), the profile, and the quota floor. When the floor passes, the HOLD is taken in the wrapped quota port: the worst case of the whole request (see item 14 of section 6) is reserved in the ledger, keyed by the request id. A balance that cannot cover it is a refusal with the numbers; a request nobody can price is "feature unavailable", not a quota refusal.
2. **UNDERSTAND and the rest of the intake path**, in process, through `runIntake`; the Understand call is made by the gateway adapter and its cost is recorded the moment it finishes.
3. **ANSWER.** The answer gate and the shape decide: a refusal, a STALE cycle and a Report 2 request end here with no model call; an ACTION is the Trade Setup button; the rest go to a model.
4. **MODEL.** The prompt is assembled (caps, cut order, chart rule: the chart is asked for once a cycle, only when data, call, tier and model allow it), the primary model is called (25 s; the fallback is asked at 20 s when the primary fails), the JSON is read, the schema, the numbers (±0.05) and the wording are checked, and at most ONE extra call is made for whichever failed first. After it, a wrong number is flagged and a wrong phrase or schema is the board-only fixed answer. A deadline of 55 s reaches every call as an abort signal.
5. **COMPOSE.** Report 1 / short answer / fixed answer / action; the direction is copied from the synthesis reading; a reply the contract refuses is never shown (the board-only answer goes out with the reason `SCHEMA_FAILED`).
6. **SETTLE.** The hold becomes the charge for the calls that were paid for, up to what the balance has left; with no paid call it is released.
7. **STORE.** The thread (when this message made a new one, titled from the answer), the trace row and the two messages, each awaited. A failure is an `error` event (`PERSISTENCE_FAILED`); a thread this request made is discarded if the trace or the messages are refused; a request that was charged and could not be filed leaves an ERROR trace row.

**On the wire.** The status is chosen by how far the run got: before the gate has passed, a JSON error with a status; after it, a 200 stream of stage events and one final event. The route starts the run immediately and hands it to `after()`, so a client that disconnects cancels only the stream: if a model was already called the run finishes, settles and stores; if not, the run ends as ABORTED, the hold is given back and the response is a 499.

**Idempotency has two independent guards.** The stored trace answers a request that was served (a stream of one event, nothing is charged or called). The ledger's reservation, keyed by the same request id, answers one that is still running or was settled without its reply being filed: it is never run twice, and the trader is told to try again.

## 6. Decisions and readings of mine

1. **The server's request id** is `SHA-256("reply-request/1" LF user id LF client request id)`. The client sends one `client_request_id` per press (letters, digits, `_` and `-`, up to 64; the route requires a UUID). The same trader sending the same id gets the same request id, which is the key of the reservation, the stored messages and the trace row; two traders can never collide and a client id seen in somebody else's traffic is another request for this trader.
2. **A duplicate that is still running** is an `INTERNAL` error with `retryable: true`. The stream contract has no "in progress" code, and adding one would change what you approved in part 1.
3. **ONE extra model call is shared** between the schema retry and the number/wording regeneration (D11 and ADR-053 allow one regeneration; the hold covers the answer twice and no more). Whichever fails first spends it.
4. **A client that leaves after a model call is ignored**; before it, the request ends and the units come back (499). The deadline is the only thing that stops a run that was dispatched.
5. **Refusals leave a trace row only for an INSTANT prompt.** The trace row has a required `intent`; a button press has one (the button), and a typed question refused at the gate or the door has none, and a guessed intent in a 7-year audit row is worse than no row. A refusal costs nothing, so no row loses money.
6. **A reply that cannot be filed is not shown, and its cost stays charged.** The hold is settled before the store (so a failing store never leaves a hold open), and the model was paid for either way. The trader gets an `error` event with `PERSISTENCE_FAILED` (not retryable). The same request id is never run again: a second press is answered from the trace row when that holds the reply, and otherwise is refused as a duplicate of a request that was settled. If you would rather refund a reply that was paid and not filed, that is a small change in `orchestrator.ts` (section 8, problem 6).
7. **The gate's quota port is wrapped, not edited.** The six checks of the gate and their order are unchanged; the hold is taken after the floor check passes and before the Understand call.
8. **The thread's id is made before the thread exists** (`newThreadId`, `createThread({ id })`) so the trace row can name it; the thread row is created at store time and discarded if the trace or the messages are refused; a thread that was there before is never removed by a failed write.
9. **Persistence order:** thread (when new), trace, messages. The trace is written before the messages so that a message never exists without the audit row of the reply it holds.
10. **An ERROR trace row** is written when a charged request could not create its thread, with no reply and no calls beyond those made; if the trace write itself fails there is nothing more to write.
11. **Titles (D15)** come from the final answer: symbol, bias (when the answer has one) and the cycle's slot, e.g. `XAUUSD · LONG · 18 SEP 20:55`; a rename sets `title_source = USER` and no derived title replaces it.
12. **Stage events** come from the intake path's own trace recorder (`EventedRecorder`), so the stages and their times are those the trace records; stages a request never reaches are SKIPPED events, in order, before the next one that starts.
13. **The deadline** is a port (`deadline(ms)` returns a signal and a cancel); the extra call is not made with less than a set time left (`MIN_EXTRA_CALL_MS`); past the deadline the answer is the board-only fixed answer with the reason `DEADLINE`.
14. **The hold's amount** (`requestBounds`): the Understand call at its prompt ceiling (typed requests only) plus the answer at the full 19,600-token budget and a chart, on whichever of the launch pair would cost more (only one answers), through the estimator of part 6. With no launched model or a missing price there is no bound and the request is "feature unavailable".
15. **`REPLY_ALLOWED_USER_IDS`** is applied in the session port (`allowListSession`): a trader who is not on a list that exists is a Free trader for the gate, so they get the same refusal as a Free trader; a list that exists and is empty lets nobody in. The function lives in `flags.ts` so the threads and state routes load it without the gateway, storage and the ledger.
16. **The threads list** uses an opaque cursor (base64url of the last message time and the thread id), strictly decoded (200 characters, a safe integer, an id of 1 to 64 characters); the default page is 50, the most 100.
