## 6. Decisions needed from Davin, with the options seen

None blocks part 5. Each is a choice I made that is yours.

1. **No foreign key from `entry_zones` to `synthesis_readings`.** I followed chapters 1 and 2 (no foreign keys anywhere in the Stack D tables); a zone is joined to its reading by (symbol, cycle_slot, profile). The alternative is a composite foreign key on that key: a zone could never exist without its reading, at the cost of relation fields in both Prisma models (the sync spec, the stubs and the type mapping would need to skip them). With the same-transaction write the two cannot drift today. Keep as built?
2. **The database re-derives the SHA-256 and the JSONB copy of every stored text.** A writer must hash exactly the text it stores. The benefit is that the record cannot disagree with its own hash. The cost is the second point below. Keep, or leave the hash and copy checks to the writer?
3. **A refused row rolls back everything in its transaction, and D9 puts SYN rows in the cycle's own transaction with `mcd_outputs`.** A SYN row that breaks one of the 25 CHECKs would therefore lose the cycle's sensor rows too, which is the opposite of what part 3 made the runner do (a bug in synthesis can only cost SYN rows). Tested: a refused zone rolls back both tables. Options for part 5: **(a)** keep D9 as approved and make the writer check every reading, every zone and every one of these rules in TypeScript before the transaction, leaving out SYN rows it cannot vouch for (what I recommend; the CHECKs are then a last line of defence that should never fire); **(b)** write the SYN rows in a second transaction after the sensor rows, so a SYN failure cannot touch them (the two sets could then disagree if the second fails). Say which for part 5.
4. **Retention.** I defined none: readings and zones are kept like `mcd_outputs`. From the fixtures one cycle is about 7 to 10 KB in `synthesis_readings` (text, JSONB copy, zone text, columns) and about 1 KB per zone row, so roughly 3 to 4 MB a day, about 1 GB a year before compression, if the pipeline runs around the clock. Say if you want a retention rule.
5. **A reading that fails its guard is never saved, and so is never counted in the database.** Part 3 keeps it out of the table (the engine returns `reading_json: null` and the problems); the only trace is the log. The measurement kit of part 6 counts refusals, so it will need a place to read them: the gateway's log, or a small table later. Part 6 decides; I note it now so nobody expects the tables to hold it.
6. **Constants in the database.** Five zones at most, a stop of at least 13, half a cent of tolerance, the three invalidation words. Changing any of them is a new decision and a new migration (like the n >= 30 gate); the zone parameters file `zone_params.yaml` holds 13 as `min_stop_distance`, so changing it there without a new migration would make the database refuse every zone between the old and new figure. A test that compares the two is a cheap addition in part 5 if you want one.

## 7. Problems and surprises the next session must know

- **The mutation check found a real gap in the tests, not in the migration.** 71 mutants of the migration, both schemas and the stubs: 67 killed at once and four survived. Two were redundant checks (`jsonb_typeof` on the zone text only changed which error was raised, and `stop_distance > 0` is implied by the 13 rule); I made the first a `CASE` so a text that is not a list is always a plain constraint violation, and removed the second. One was a missing test case (the audit document as a list of the four names passed the key check; now tested). **One was a column type: `DOUBLE PRECISION` changed to `REAL` in the migration passed every spec**, because `schema-sync.spec.ts` compared column names and order but never types, and a REAL prints the same cents. It now compares each column's SQL type, nullability and default with what Prisma derives from the model (the drift check I ran by hand would have caught it, an automated test did not). That gap exists for the chapter 1 and 2 tables too; I did not touch them.
- **The database-only pass:** running the gated spec alone (without the file-level spec) against the same SQL mutants shows which rules the database spec itself proves by behaviour: all but the column-type one, once two cases were added (a reading that lists fewer zones than its count, and a runway with no opposing price while the audit document agrees there is none).
- **PostgreSQL reports the first failing CHECK by constraint name, alphabetically**, so a test of one rule must break only that rule; the spec builds consistent rows from a changed document and overrides single columns only for rules about columns.
- **The `?&` operator and `to_char(to_timestamp(...) AT TIME ZONE 'UTC', ...)`** are in the CHECKs; both are tested (a Pacific/Auckland session writes the same row). The migration has a `?` in it, so a tool that treats `?` as a parameter marker would misread the file; `psql` and Prisma's `db execute` do not.
- **`entry_zones.levels` and the reading's `reading` are JSONB with no key order**; the text columns are the record, and `reading_json` and `zones_json` are what a replay compares.
- **The `duration_ms` is the wall time of the whole synthesis step**, so both profile rows of a cycle carry the same figure.
- **Tooling:** a Bash heredoc with a lot of quoting broke twice more (multi-line edits were run from script files again, and a backslash inside a Python string reached TypeScript as a newline once: two syntax errors, caught by Prettier and the compiler); the first full-pass mutation log was empty until the end because Python buffers a redirected stdout unless it runs with `-u`.
- **Not checked:** nothing ran against staging or production, the Railway image or the real `market_data_v6`; the writer that will fill these tables does not exist (part 5), so the column mapping in the spec is mine and part 5 must reproduce it; no migration was applied anywhere that matters.
