# D6 inventory: every operation-service database path under the 2,000 ms checkout deadline

> Unit P-operation of the database-scaling second wave. **Evidence type: a reading of the code** at `ed4ca861` (plus the fixture
> observations quoted from [the evidence report](../2026-10-24-operation-pool-deadline-evidence.md)). Nothing here was run against
> production. Which `MIGRATE_*` flags are on in production, the traffic mix and the healthy checkout distribution are **not known**.
> "Awaits" counts **sequential** database round trips in the handler (each is a separate pool checkout; a transaction is one checkout
> for its whole life). "Budget" is the monolith client's abort: reads (GET, HEAD) 5,000 ms, writes 15,000 ms, never retried
> (`lib/operation-service/client.ts:56,66`). A 2,000 ms wait per checkout is **nominal headroom only**: it ignores SQL time, PgBouncer
> queueing, other awaits and network.

## What a checkout failure looks like (observed in the fixture)

- A pool wait that exceeds the deadline surfaces from a raw or model query as a **plain `Error`** ("timeout exceeded when trying to connect"),
  with no Prisma class and no `code`. A connect that does not finish surfaces as a plain `Error` ("Connection terminated due to connection timeout").
- Nest's catch-all filter (`common/filters/all-exceptions.filter.ts`) turns anything that is not an `HttpException` into **HTTP 500 "Internal server error"**
  and logs the stack (`statusCode >= 500`), so the original message is in the log stack, not in the response body. The monolith sees a 500, not a 504 or 503.
- An interactive transaction under saturation fails with **Prisma's own `P2028`** ("Unable to start a transaction in the given time") at about 2.0 s
  in both runs (before and after the change); the pool timeout wins only when `maxWait` is raised (then a plain `Error`, 2,010 ms).

**Note 1 (budget).** Three sequential checkouts can wait 3 x 2,000 ms = 6,000 ms in the worst case, which is more than the 5,000 ms read budget; two
can wait 4,000 ms, which leaves 1,000 ms for everything else. This is **not a regression** (today the wait has no bound and the monolith aborts at 5 s
whatever the service is doing), but the deadline does not guarantee that these routes finish inside the caller's budget. The three-await rows are the
notifications list, and the profile and 2FA-status reads when the user is found only by e-mail (`resolveUserId`'s fallback, a historic workaround).
Each await only waits the full 2 s if the pool is still saturated at that moment, which the unit cannot tell from here.

**Note 2 (silent degradation).** `getPreferences` catches every error and answers 200 with the defaults. A checkout timeout is now one more way to get
that answer. `updatePreferences` re-reads the stored row and merges the incoming fields, so a stored preference is only overwritten if the client sends it back.

## D. Background work (the `operation-service-worker` process, its own pool of 10)

`railway.toml` declares two services from one codebase: `operation-service` (`start:prod`, HTTP) and `operation-service-worker` (`start:worker`). Each process builds its own
`PrismaService` and therefore its own pool (max 10) with this deadline. Davin stated 1 replica for `operation-service`; the worker's deployment and replica count were not stated.

## Flagged rows (reported to Davin; the order's D2 says no code change here)

- **F1 `POST /auth/refresh`.** Rotation revokes the old token before it issues the new one and reads the user. A failure after the revoke loses the session (the user logs in again). Not new in kind (any database error does it); the deadline adds a trigger under saturation. Budget 15 s, four checkouts, so it fits.
- **F2 `DELETE /drawings/:id`.** Orphan `PRICE_TOUCH_LINE` alerts if the last statement fails (they count against the user's alert quota, and the engine is not notified). Same remark: not new in kind.
- **F3 `DELETE /users/sessions`.** The `Session` rows are deleted only for sessions that were active when the handler started, so a failure after the `updateMany` is not healed by a retry. Whether any code path reads the `Session` table (the monolith signs in with a JWT) was **not verified**.
- **F4 `void this.reload()` on `alerts:changed`.** A rejection there is an unhandled rejection. Node 24 (the version here) ends the process on one (probe: exit code 1; the same default since Node 15), and no `unhandledRejection` handler exists in `operation-service/src`, `@nestjs/core`, `@opentelemetry/sdk-node` or `bullmq`. Today a saturated pool makes `reload()` wait; with the deadline it can reject after 2 s and take the worker process down, which `railway.json` restarts (`ON_FAILURE`). This is the one **new failure mode** found. Not changed (D2; the fix is a `.catch` on that call).
- **F5 fire concurrency 10 = pool max 10.** A burst of fires can hold every connection of the worker's pool, so the reload and the cron reads can wait; dispatch itself retries.
- **Budget rows (Note 1).** Three-await reads can wait 6 s in the worst case against a 5 s budget.
