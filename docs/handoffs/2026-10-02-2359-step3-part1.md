## 7. Problems and surprises the next session must know

1. **MCD0 calls both timeframes defective on all three real cycles** (S3 of the plan, now shown at cycle level): on v1, v3 and v4 every channel MCD is CAUTIONARY, and MCD3 carries four reasons (`UPSTREAM_CAUTIONARY:MCD1`, `UPSTREAM_CAUTIONARY:MCD2`, `MCD0_DEFECT_M5`, `MCD0_DEFECT_M15`). If the live rate looks like this, sensors will almost never read VALID in shadow. That is what the five-day review (B3) is for, and ADR-061 (half risk on CAUTIONARY) would then halve the risk on most setups.
2. **MCD3's reading through the runner is not the stored one, by design.** The stored MCD3 envelope was made from unmarked MCD1 and MCD2; the runner hands it the marked ones (Q5 a), so its status and reasons differ. Everything else is equal on all three slots, and given the stored upstream the real MCD3 reproduces its stored envelope exactly (both asserted). The same applies to any later comparison: MCD0 to MCD2 are comparable with their stored envelopes, MCD3 is comparable modulo status and reasons.
3. **MCD1 and MCD2 have no per-MCD fixture for v3.** For that slot the reference is MCD3's stored `upstream.json`, which the committed evaluators wrote on the full bundle; for v1 and v4 it is asserted equal to their own fixtures.
4. **`inputs_sha256` is the hash of the bundle's canonical text** (sorted keys, no spaces), not of the text the caller sent; the same bundle with shuffled keys hashes the same (tested). It is `None` only if a bundle cannot be written as JSON at all (junk types); the readings are still produced. To replay a stored cycle, part 5 sends the stored bundle with `retuning_enforced` equal to the stored `retuning_applied` (when `retuning_observed` is false the switch has no effect, so either value gives the same readings).
5. **`evaluator_envelope_sha256`** is the hash of the reading before inheritance; `envelope_sha256` is the stored one. They differ exactly when the worker marked it. For a reading replaced by a guard they are both the replacement's.
6. **Timings and the Python version live under `runtime` and nowhere else.** Everything else in the result is byte-identical between runs. Part 2's `duration_ms` and `evaluated_at` columns come from there and from the gateway's clock.
7. **The kit's `never_throws` fallback has no `depends_on`**, so a failing MCD3 would be saved naming no dependency; the runner rebuilds that envelope (and only that exact envelope) with the registry's dependencies. An EVALUATOR_ERROR reading with its own details is kept as it is.
8. **A YAML flag trap, again:** `flag: off` is the boolean false. The loader refuses it in the registries and in `worker_config.yaml` and says to quote it.
9. **Prettier and generated files.** `mcd_worker/fixtures/*.json` is already covered by `.prettierignore` (`mcd*` matches `mcd_worker`); the `.source.md` notes are not, and the hook re-pads their tables, so the provenance check compares them with the padding removed (`build_fixtures.same_text`). It was formatted here, so nothing changes at commit time. Run the suite after the commit anyway (the 2026-10-01 lesson).
10. **My Bash heredoc rewrote `\n` inside Python code** on two occasions and broke three files (`mutation_check.py`, then `build_fixtures.py` and `test_fixtures.py`); each was caught by a syntax error or an `ast.parse` of every file before any evidence was taken, and repaired with the Edit tool. The gotcha is already in `environment-gotchas.md`.
11. **No pytest**, so the plan's `test_x.py::test_y` names are `unittest` names (`module.Class.test`), run with `python -B -m unittest`. `test_tools.py` is outside the mutation harness's own test run on purpose (inside a mutated copy every pattern would read as stale and every mutant as killed).
12. **Not measured:** the real `mcd_outputs` size, database latency, Python in the Railway image (B0), anything about production. The cold-start figure above is a Windows laptop, not the Railway image.
