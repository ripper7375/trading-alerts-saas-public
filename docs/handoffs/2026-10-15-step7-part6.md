## 5. How it works (for the approval)

```
gate (every request)                          meter (around the model calls, part 7 wires it)
  flag, session, tier  <- entitlement table     estimateRequest   Understand + answer (+ 1 regeneration), at the maximum
  thread, profile                               reservationLadder base+regeneration, then base alone
  quota floor  <- createQuotaPort               meter.reserve     ONE statement: hold if used + reserved + n <= limit
     allowance = PRO_MONTHLY_UNITS (Pro),         refused  -> the model is NOT called (5.14 item 2)
                 0 (Free), unset -> refuse        granted  -> run the calls, record each paid call
     balance >= floor?                          meter.settle      ONE statement: used += min(cost, what is left); hold released
     (an empty account is refused                                 no call made -> meter.release instead
      before the Understand call)               reaper            RESERVED past its deadline -> EXPIRED, units back,
                                                                  ONE statement per period, oldest deadline first
```

**A unit is one micro-dollar** (D2). A period is a UTC month. A request id is the key of its reservation, so a retry finds its own row and holds nothing more, and `runMetered` refuses to run the model again for an id that already has one (`duplicate`).

**What is charged.** The settlement is the sum of the recorded calls' costs in units, **up to what the balance has left after the hold is given back**. If the gateway could not say what a call cost, the whole reservation is charged (a paid call is never free, and never more than was held). A request that never reached the model is released and costs nothing. A request that fails after a call is still settled for what was spent. A reservation the reaper expired can still be settled late if the units are still free. **Charged is never more than the cost, and the books can never break the period's CHECK; whatever the balance could not take is in `cost_micro_usd` and is reported as `absorbedUnits`.**

**What is held.** The ceiling of the request: the Understand call at its prompt ceiling (5,000 estimator tokens) and 700 output tokens, the answer at the prompt the caps allow and the model's `max_output_tokens`, each priced at the registry's dated price with the model's calibration margin and a 10% margin on the cost, plus one regeneration (a second answer) if the ledger grants it. A trader with a balance below the base worst case is refused with the balance and the units needed.

**Rules for any new ledger SQL, from the two defects of section 8:** (1) a statement that updates a row from a CTE must have a CTE of ONE row (the reaper's statement is for one period); (2) a value worked out from a locked row and written under a CHECK must be capped by the row version the UPDATE itself updates (the settlement's `LEAST(charge, room)`); (3) test it on a plan the planner does not choose today (session settings), under load, and audit the sums afterwards.

## 6. Decisions and readings of mine

D2, D3, D4, D5 and D22 are built as the order states them. These are the places where the order, the plan or the documents were silent or could be read two ways. They stand unless you object.

1. **Settlement charges up to the room, not `used + actual` unconditionally (please look at this first).** The order says the settle shifts the hold to `used` with `used = used + actual_units`. That is the formula in the normal case and it is what the code does whenever the balance has the room. But `used + reserved <= limit` is a CHECK of the period (the order's own), and a cost above its hold, or a late settlement after another request took the freed units, can push the sum over the limit: the statement would then fail, the settlement would be lost and the paid call never charged. So the charge is `LEAST(actual, limit - used - (reserved - own hold))`; `actual_units` on the row is what was charged, `cost_micro_usd` what the gateway said, and the difference is the business's, never the trader's. A test (`absorbed`) shows each case and the audit still adds up. If you would rather the trader be charged the full cost and the balance go over its limit, that is dropping the CHECK and the cap, a different design (a negative balance).
2. **Unknown cost charges the whole reservation; a RELEASED row is final.** `actualUnits: null` means "the gateway could not say", and the row is charged its hold. A settlement that arrives for a RELEASED row is refused (`ALREADY_RELEASED`), not charged: RELEASED said no model was called, and a charge for it is a bug of the caller to see, not to hide. EXPIRED rows do settle (the reaper favours the trader, the late cost is still charged if the units are free).
3. **The whole worst case is held up front, at the ceiling.** The order says the estimate is the Understand call plus the answer at the maximum plus one regeneration "if the balance permits". The ledger is the one place the balance is checked (atomically), so the plan is a LADDER (`reservationLadder`): try base+regeneration, then base alone, then refuse with the balance. A request granted only the base may not regenerate (D11: a number still wrong is shown as "not verified"). Part 7 reserves before the Understand call, with the ceilings; settling gives the unspent part back. The cost: a trader whose balance covers a typical request but not the ceiling is refused (the plan's risk note). The meter's "about N analyses left" figure is part 8's.
4. **The margins and the figures I chose, all constants with a test and all for S3 to replace:** a 10% margin on the cost of each call (`COST_MARGIN_BP = 1000`, for a price that moved or a host that charges more than the one the registry price was read from); the Understand prompt ceiling of 5,000 estimator tokens (a test builds the largest prompt the intake path can make, 4,023, and fails if this falls below it); a reservation lives 10 minutes before the reaper may take it (`DEFAULT_RESERVATION_TTL_MS`; the request deadline of D23 is part 7's, this is longer than any of them); the floor is one unit while nothing is priced.
5. **A month's limit rises at once and never falls mid-month.** `ensurePeriod` creates the row with the allowance and raises its limit if the configured allowance is higher (`GREATEST`); lowering `PRO_MONTHLY_UNITS` takes effect from next month, so a trader is never taken below what they were granted. If you want a lowered allowance to apply at once, it needs the CHECK to be allowed to fail.
6. **The columns are 32-bit integers** (`limit`, `used`, `reserved`, `actual_units`, `cost_micro_usd`, `reserved_units`), like `units_charged` in `request_traces` (part 1). The bound is 2,000,000,000 units ($2,000 a month); the sums are made in 64 bits so they can never wrap. A larger plan is a migration to `BIGINT` and the JavaScript number would still hold it.
7. **D5: part 6 uses no hash key.** I read "reuses `ENGINE4_AUDIT_HMAC_KEY` through the existing helper" and found nothing in this part to hash: the ledger is the balance, deleted with the account (`ON DELETE CASCADE`), and what a request cost stays in `request_traces.units_charged` and the model group, which already carry the keyed hash and the key version (part 1). So the migration says so and no key is read. If you want settled lines to outlive an account (a financial record), that is `SET NULL` plus a hash column in a new migration.

## 8. Problems and surprises

1. **A settlement could fail with a CHECK error when the period changed while it waited (fixed).** Found by the long interleaving on the real server (one run in about fifteen). `settle` works the charge out from the period row its `FOR UPDATE` returns, which is the NEWEST version, and then updates the version its own snapshot saw, which can be older (a release or a reaper run committed in between, so the older version holds MORE units). PostgreSQL checks the CHECK constraints on that first, older version before it follows the update chain, so a charge that fits the newest numbers broke `ai_quota_periods_balance_fits_the_limit` on the older ones, and the statement raised 23514. The books were never wrong (the failed statement changes nothing), but the call threw and the charge was not recorded; `runMetered` would have kept the model's reply and left the reservation to expire, a free answer. The UPDATE now caps the charge by the version it updates (`LEAST(c.charge, GREATEST(limit - used - (reserved - release), 0))`); on the newest version, which is the one it ends up writing, the cap takes nothing off. A deterministic regression test holds the reservation row with a second connection while a release commits (fails on the old statement with 23514, passes on the new), and four SQL mutants of the cap are killed.
2. **The reaper lost the period update of a statement that took several periods (fixed, and the most important thing in this part).** After heavy churn the same interleaving started to fail in about two runs of three with `reserved N is not the M its reservations hold`: reservations were EXPIRED and their units had never gone back to the period. `pgbench` with the real statements (ten clients, one in ten the reaper) showed it plainly: **371 of 1,012 reaper period updates lost in 10 seconds (56,244 units), with no error**, and every update that was applied was right. A trigger that logged every reaper change showed transactions that expired reservations and updated no period. What I know, and what I do not: it needs a **nested-loop plan** (the planner chose one once the tables were bloated; `enable_nestloop = off` removed the loss, `enable_hashjoin = off` and `enable_seqscan = off` did not), another statement must have changed the same period after the reaper's snapshot, and it **did not happen when the statement's CTE had one row** (0 of 3,849 with one period per statement). Taking the period lock first, reading the update from the main query, and removing the `args` join each changed nothing. I did not find the cause in PostgreSQL's source and I did not test another version (18.1 only); it looks like the recheck PostgreSQL makes when the row it is updating changed (EvalPlanQual) dropping the row when the join CTE has several rows. **The reaper now expires one period per statement and `reapExpired` loops** (section 6, item 16): 0 lost updates in every shape I tried (reserve-only, settle, release and mixed workers, `enable_nestloop`, `enable_hashjoin` and `enable_seqscan` off, four traders with a tight limit; five mixed rounds of 20 seconds and six variant rounds of 10 seconds, with no deadlock and no failed transaction, while the old statement deadlocked in the same load). The regression test in `ledger.pg.spec.ts` (3 traders, the reaper against 9 racing reservations, 40 rounds, the session pushed to nested loops) fails in the first round on the old statement with `reserved 475 is not the 75 its reservations hold` and passes on the new one. The settle, release and reserve statements only ever touch one period and lost nothing in the same load. **Check the version and plans of the production PostgreSQL before S4** (section 9).
3. **A scripted patch through a Bash heredoc collapsed `\\` and wrote a test that passed for the wrong reason.** A Node patch script written through a heredoc collapsed `\\b` and `\\s` in a regular expression into a backspace character and a bare `s`, so `expect(sql).not.toMatch(/\bDELETE\b/)` could never match and passed; the same collapse cut a string in the boundaries test, which did fail (a syntax error), and that is how the first was found. It happened again while I was hunting the defect above. A scan for control characters over every changed file exists (it found the first); the rule is in `environment-gotchas.md`: scan after a scripted patch, write regular expressions with the Edit tool.
4. **A `test.each` row with two entries and a callback with three parameters hangs the test** (Jest hands the third parameter `done`), so the first run of the gated spec looked frozen for ten minutes. Rows are padded now.
5. **My first mutation harness opened a console window for every process on your PC** (detached workers on Windows) and you had to restart it. I am sorry. Every child process of the harness is now started hidden (`windowsHide: true`, never `detached`), the workers are ordinary background tasks, I checked that no window appeared, and I ask before starting many processes, a server or a database. The rule is in `environment-gotchas.md`.
6. **The mutation check found real things before the server did:** the Understand prompt ceiling I wrote (4,000 estimator tokens) was below the largest prompt the intake path can build (4,023): it is 5,000 now and a test builds the largest prompt and fails if it grows past the constant; a regeneration that costs nothing was refused; a worst case of zero would have been refused by the ledger; the floor from the registry had no test; a user id of exactly 128 characters had no test.
7. **Apart from the two defects above, the model and the real SQL agreed on the first run,** except two expectations of mine in the CHECK tests (a negative limit also breaks `used + reserved <= limit`, and PostgreSQL names the first failing CHECK by name; a count of 13 where there are 12). The real error shape of a unique or foreign-key violation through `@prisma/adapter-pg` is recognised (`isUniqueViolation` / `isForeignKeyViolation`; a spec triggers each through the real client).
8. **`jest --runInBand` hung on this machine;** the ordinary invocation ran a suite in 5 seconds. The first minutes of the first mutation run mutated the main tree; I stopped it, put the files back from its backup (compared byte for byte) and ran every mutant in scratch copies outside the repository.
