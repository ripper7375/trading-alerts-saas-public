## 5. How it works (for the approval)

**One request for the workspace.** A badge press and a typed question both go through the provider's `ask`, which refuses a request while one is in flight (a guard on a REF set before anything is awaited) or a thread is being opened. `busy` is that, for the whole workspace: the composer, both badges, "New thread" and every other thread's row read it. The badge that was pressed spins because the in-flight request's input is an instant label; for a typed question both badges wait and neither spins.

**What an answer does to each panel.** The reducer puts the question and the card in Panel B's items and sets the thread; Panel A's active thread IS that id, so it highlights with no message between the panels; when the request ends, Panel A reads its first page again, quietly, and the new thread is there. `onSettled` tells the badge how it ended: a result opens Panel B if it was collapsed, a refusal is repeated below the badge.

**Opening a thread.** `selectThread(id)` makes the thread active at once, empties Panel B, shows "Opening the conversation…", reads `GET /api/chat/threads/[id]` and fills Panel B with the stored messages as the cards the live panel draws. A second pick while one is loading is refused (the trader waits); an answer that arrives for a thread that is no longer the one being opened is dropped. A question asked in an opened thread carries its `thread_id`.

**What the panel never does.** It sends no user id, tier, language, model, symbol or equity; it adds no number, direction or disclaimer; it never translates a title (the server's title is market data and is drawn as it came), an id or a price.

## 6. Decisions and readings of mine

1. **A thread picked in Panel A is opened into Panel B** (see READ THIS FIRST). The order says "active thread highlighting" and "active thread switching"; I read it as opening the conversation. The cost is the stored-message reader (`itemsFromMessages`) and three reducer actions.
2. **Opening a thread, a new thread and deleting the thread being answered wait while a request is in flight.** The workspace has one request at a time, and a reply that arrives for a thread that is no longer on screen would be put into the wrong conversation. They are disabled (not hidden) with the same dimming as the badges; the trader can stop the request first. Deleting ANOTHER thread is allowed.
3. **Panel B opens on SUCCESS, not on the press.** The order says "success handling ... expands Panel B if it was collapsed". A refusal leaves it collapsed: the notice is below the badge and the refusal card waits in Panel B for when it is opened. The press itself changes no layout (so the chart does not resize under the trader's finger).
4. **The refresh after a request returns the list to its first page.** A thread that moves to the top shifts every page behind it, so a cursor of the old order could skip one; the cost is that a trader who had pressed "Show more" sees the first page again after asking something.
5. **`replyEnabled` and `instantPromptsEnabled` are independent.** The badges are instant prompts only when `INTAKE_INSTANT_PROMPTS_ENABLED` is on (as in step 6), and they use the chat only when `REPLY_ENABLED` is also on. Chat on and instant prompts off: the older canned-prompt badges, which fill the composer. Chat off and instant prompts on: `POST /api/intake/instant`, as today (it is a 404 in a production build, D8).
6. **The chat off reads nothing.** Before, a Pro Panel B read `GET /api/chat/state` and got a 404 to say "not switched on"; now `ChatWorkspace` starts in that state and sends nothing. The same words, one request fewer. If the page says on and the server says off (the staging allow-list, a 404), the panel falls to the same state from the answer.
7. **The Free tier's one thread is the recorded example**, shown only when a recording exists; until part 10 adds it, Panel A shows the same "not available yet" note as Panel B (D19).
8. **`Delete` states the audit rule in the words of D16**: the messages are removed for good; a separate audit record of each request stays on our servers, cannot be changed or deleted, and holds no part of the trader's questions. That last clause is true of the trace as part 1 built it (no question text) and is the sentence counsel should read first.
9. **The thread title is never translated** (it is the server's deterministic title or the trader's own, drawn in `<bdi dir="auto">`); the bias badge and the time are the reader's.
10. **`TradingWorkspace.chatFetchImpl`** exists only for the preview and the tests; no page passes it. The alternative (a context) would have put test hooks in production code with the same effect.
11. **The two pages are named in the reply boundaries guard** (`app/terminal/page.tsx`, `app/free/page.tsx`) because they import `isReplyEnabled` from `lib/reply/server/flags`. That file reads no `process.env` of its own (the page passes it), as its header requires.
12. **The thread list's page size is 30** (the server's default is 50, its largest 100): a narrow sidebar does not need 50 rows at once. It is one constant (`THREAD_PAGE_SIZE`).
