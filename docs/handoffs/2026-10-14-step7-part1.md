### 4b. Mutation check of the new code

**What was run.** A harness in the session scratchpad (outside the repository) mutates the code and runs the tests once per mutant: a comparison or logical operator swapped, a number moved by one, a string constant replaced, a condition forced true or false, a regular expression's anchor dropped or bound moved, an issue report dropped, a boolean flipped; for the SQL also a whole CHECK or trigger deleted and the guard function edited by hand. A mutant is run first against the nearest test files and, if it survives, against every test of this part.

**TypeScript: 2,410 mutants** of the 13 files that hold logic (`shape`, `fields`, `report1`, `answer`, `result`, `stage-events`, `trace-fields`, `delivered`, `retention`, `title`, `threads-store`, `messages-store` and the trace `store`; the data-only `intake.ts`, `intent-shapes.ts` and `version.ts` and the one-line door `hash.ts` have nothing to mutate). 2,346 were killed by the nearest tests, 46 only by the wider run, 9 did not compile; **9 survived**:

- 2 sat in a branch that cannot be reached (`stage-events.ts`: once the type of an event is known the value is an object, so `exactObject` never answers "nothing"): the branch is **removed**.
- 3 were real gaps: the duplicate-zone rule fired on ids that are not strings; the flag message did not name the known flags; the bad-locale case of a missed-knowledge record was untested. Three tests were added and the three mutants were then killed.
- 4 are **equivalent** (the tie-break of the retention sort): the ids are unique, so `<` against `<=` and a different positive number cannot change the order, and V8's sort reads a 0 for "greater" the same as a 1 (shown on shuffled, reversed, block and interleaved lists of 40 to 1,000 rows). They would differ on an engine that does not.

This was the **second** pass. The first, against the first test set, left 315 survivors; they led to the `damage` suite (every place of every valid example is damaged and the issue must sit there), pinned constants and boundary tests for every limit and regular expression, message assertions, and simplifications of the code (the stage-order state, the month arithmetic, the chat write as one `update` that returns the count). The 2,410 above were generated from the code as it stood after that round; the only later change to code is the removal above, and the 7 survivors were re-run against the final tests.

**SQL: 430 mutants** of the hand-written part of the migration, in two tiers: the migration-sync text test, then (for survivors) the gated spec on a database built from the mutated file. 230 were killed by the text test, 166 by the database; 3 were rejected by PostgreSQL as invalid SQL (not counted); **31 survived both**: 22 were gaps in the spec (the limits and anchors of the three trace ids and of the chat message's request id; a cycle slot of 0 in three tables; a risk group that is an array or a string; a reply hash with no reply; a blank or over-long archive reference; the user-id check not run when there is no reply) and are now killed by 32 new spec tests (123 to 155); **9 are equivalent**: `btrim` against `ltrim` (3: a blank string is blank under either), `char_length` against `length` (3: the same function in PostgreSQL) and `> 0` becoming `> 1` in the three cycle-slot checks (a multiple of 300 above zero is above one).

**What this does not show.** A mutation score measures the tests, not the design: nothing here says the limits are the right limits (section 6, item 1) or that the SQL is right on a PostgreSQL other than 18.1. The equivalence of the retention tie-break rests on V8's sort.

## 5. What the contracts say (for the approval in section 6)

**`report1.v1`, what the model writes (D9, D10).** Five keys and no others: `headline`, `zones[]`, `rationale[]`, `watch[]`, `risks[]`; a line is `{ text, cites[] }`. A `{value id}` in a text is the only way a number reaches the trader; the grammar is strict (a stray, nested, empty or lower-case brace is refused) and `VALUE_ID` is `MCD2.baseline`, `Z1.invalidation`, `LAST_PRICE`, `DAY.high`. A text is one line of plain text (no control, separator, bidirectional override or tag character; the marks Arabic, Persian and Urdu need are allowed). Without a context only the shape is checked; with one (`contextOfPacket(packet, valueIds)`) the zones, the cited ids and the placeholders must exist in this packet.

| Field             | Limit                                                                            |
| ----------------- | -------------------------------------------------------------------------------- |
| `headline`        | 1 to 160 characters                                                              |
| a line's `text`   | 1 to 240 characters, at most 8 placeholders                                      |
| `rationale`       | 1 to 6 lines                                                                     |
| `watch`           | 1 to 4 lines (part 4 requires the `{Zn.invalidation}` line of each zone)         |
| `risks`           | 0 to 5 lines                                                                     |
| `zones`           | 0 to 5 ids `Z1` to `Z5`, none twice                                              |
| `cites` of a line | 0 to 4 of `MCD1` to `MCD15`, `Z1` to `Z5`, `SYN`; the gate (`MCD0`) never speaks |
| all texts         | 2,400 characters in total (§5.4 gives the answer 1,500 tokens)                   |

**The six sections of the report (D10), as data (`REPORT1_SECTIONS`):** 1 Summary ← `headline` + the SYN direction line; 2 M15 vs M5 alignment ← `rationale` + the trend relation + the two channel sensors; 3 Levels ← the engines alone (envelope geometry, context levels); 4 Entry zones ← `zones` + the stored zones (band, reference, invalidation, room); 5 What would change the picture ← `watch` alone; 6 Risks and news ← `risks` + the calendar block + the data status. A test holds that every model field feeds exactly one section and every engine source is used.

**`answer.v1`, the short answer (D9).** `locale` (one of the 19; with a context it must equal the packet's reply locale), `text` (1 to 800 characters, same grammar), `cites[]`, `action` (`null` or `OPEN_TRADE_SETUP`; the list is closed). No direction key either.

**`reply-result/1`, the ONE checked result (D24, ADR-054).** Four kinds: `REPORT1` (the composed report: headline, `DirectionLine` copied from SYN, alignment with the two channel lines, levels, the stored zones, watch, risks, the news block), `ANSWER`, `FIXED_ANSWER` (a reason from five, the direction or none, the board as ids, statuses and state codes, the levels: **no free-text sensor summary**, D20), `ACTION` (`OPEN_TRADE_SETUP` with the cycle, trader type and zone ids, no model). Every kind carries the thread, the reply locale, the intent, a **data stamp as data** (`as_of` slot, data status, retuning, flags), a **disclaimer version** (the interface shows the fixed text for its language; counsel reviews the text), provenance (request id, model, prompt version, reply version), `checks` (numbers flagged, regenerations) and `changes` (what moved since the thread's last cycle). The text of a line arrives with its placeholders filled and its numbers formatted; a number that could not be verified is already the locale's "not verified" and is counted in `checks.numbers_flagged`.

**The stream (D24).** NDJSON, one object a line, canonical key order. `stage` events (`GATE`, `UNDERSTAND`, `DATA`, `CONTEXT`, `MODEL`, `CHECKS`; each STARTED then DONE with its milliseconds, or SKIPPED), then exactly ONE terminal event that is the last line: `result`, `refusal` (the intake refusal, unchanged) or `error` (`INTERNAL`, `LEDGER_UNAVAILABLE`, `PERSISTENCE_FAILED`, with a retryable flag). `decodeStream` checks the whole text: a cut stream, a blank line, a line that is not JSON, a second terminal event, a stage out of order. The reply is never streamed token by token.

**The trace (§7.4, D16).** One row per answer, written once at the end. Seven strict groups, no field that could hold the question: **request** (reply version, request id, the client's idempotency key, thread, tier, kind, intent, language, interface and reply locale, question flags as codes), **data** (cycle slot, status, retuning, flags, sensor statuses, rule and rules version, the last-price bar, intake and routing versions, packet fingerprint), **knowledge** (M\*, chunk ids, index build id, status, and "missed knowledge" as intent, M\*, locale, chunk count and fingerprint), **model** (model, prompt version, fallback, the ten components of §5.4, cycle-block hash, real token counts, one record per call with role, outcome, attempts, tokens, cost in micro-dollars and latency, units, cost), **checks** (the answer gate of §5.3, shape, schema retries, numbers extracted, matched, violations by class, flagged; wording violations by category; regenerations; whether direction equalled SYN; the fixed-answer reason), **risk** (attached later by Section 6) and **time** (start, total, deadline hit, stages). The groups hold each other to account: the class counts add up to the violation count, the regeneration count equals the regeneration calls, a REPORT1 outcome was made as a REPORT1.

**Tables.** `request_traces`: the 12 columns a dashboard filters on (tier, locale, intent, cycle slot, data status, model, units, regenerations, number and wording violations, outcome, total time) are projections of the groups and the database checks each equals its group's value; the reply as canonical JSON text with its SHA-256 (the database re-derives it); Report 2 and the consent action (attached later); `archived_at` and `archive_ref`. `chat_threads` (symbol, title and its source, trader type, last bias and cycle, a 120-character preview, counts, last message time) and `chat_messages` (sequence unique per thread, one USER and one ASSISTANT message per request, the typed question as text or the delivered reply as JSON, 12 months to `expires_at`).

## 8. Problems and surprises
