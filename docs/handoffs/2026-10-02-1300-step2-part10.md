## READ THIS FIRST: what Option A changes, and the one reading of mine you must confirm

**Option A is built as ordered.** While a symbol is RETUNING, the gateway counts the M5 rows of `market_data_v6` from `slot - 3000 × 300` to the slot whose `cycle_id` is below the promote cycle's `m5_collection_cycle_id`. At 0, the manifest that counted it, once verified (READY), ends the RETUNING and writes `RETUNE_COMPLETE`. The sender's `repush_rows_unsent` stays in the manifest and on the row as a diagnostic, and nothing reads it. A sender without the field no longer matters.

**The reading to confirm (decision 1).** The order says "followed by one verified (READY) manifest". I read it as: the manifest that counts 0 must itself be READY, so the count and the verification are of the **same** manifest and RETUNING ends at the first such cycle. The first settled wording (a zero reported by one manifest, one more verified manifest after it) would need a place to keep the zero from one cycle to the next. The only places are a new column on `market_cycles` (a change to the unapplied part 2 migration and three schema mirrors, outside the files the order named) or overloading `check_detail`, which the readers parse. The gateway's count is of landed rows, so the extra manifest would add little. The difference in behaviour is at most one slot. It is in the ADR-015 amendment as "Reading to confirm". If you want the extra manifest: a column, one condition, about a session's work.

**How long RETUNING lasts is now what it honestly is.** The collector re-queues the whole window every cycle and the worker re-sends the oldest rows first, so a worker slower than the window leaves the middle of it old until it ages into the oldest part. That is a reading of the code, **not a measurement**: the push worker's throughput has never been measured (ADR-013, `PUSH-WORKER-THROUGHPUT-OPEN-ISSUE.md`). In that regime RETUNING could last hours, and it would be right to: the window really is mixed. The READY log line prints how many pre-promote rows are left, and the measurement kit reports each episode's length.

## 2. Deviations from the order (and why)

Live code and evidence won over the order's wording where they disagreed (non-negotiable 7). Each is small and reversible; confirm or say which to undo.

1. **"Followed by one verified manifest" is read as one step** (the count and the verification are of the same manifest). Read this first, above; decision 1.
2. **The count is read inside the service, not stored.** The order named only `retuning.ts` and `cycle-manifest.service.ts`; I added no column. So the gateway's count is visible in the READY log line and in `RETUNE_COMPLETE`'s detail, not in SQL. A column (`retune_window_old_rows`) would give a progress you can query; it is a change to the unapplied migration (decision 5).
3. **The promote cycle's id is read from the `PROMOTE` event's cycle row, not carried in the event.** The order's query uses `promoteCycleId` without saying where it comes from. Two reads (the event by `effective_slot`, then `market_cycles.m5_collection_cycle_id`), only while RETUNING.
4. **The window bound is the order's, in time.** `slot - 3000 × 300` to the slot, not "the newest 3,000 rows". The collector's 3,000 bars span more than 250 hours across a weekend, so a time bound never counts a row the collector no longer re-pushes (that would hold RETUNING on for ever); the cost is that the oldest bars of a window with a gap go unchecked (the worker re-pushes those first). It is also one bar wider than the window when the newest row is the stub: a row that has just scrolled out can hold RETUNING one more cycle, no longer. Tested at the service level (`a row that has just scrolled out of the window holds RETUNING for one more cycle, and no longer`). M15 is not counted (the order names M5 only).
5. **ADR-015 is amended in place, not superseded by a new ADR number.** The decision (RETUNING until the window is re-pushed, sensors CAUTIONARY) is unchanged; only how "complete" is measured. The file's own rule says a changed decision needs a new entry. If you want one, it is a copy of the Amendment under the next number.
6. **The kit is TypeScript in `src/cycle/` plus a JavaScript wrapper, not a `.py` file.** The data lives in the gateway's Postgres, the gateway has Jest and Prisma, and the plan allowed "script or SQL". A `.ts` under `scripts/` would break the build (section 9, item 2).
7. **Part 9's "a sender without the count never ends a RETUNING" and its deploy warning are gone** (no longer true); `waiting-on.md` says so.
8. **`RETUNE_COMPLETE` lost `zero_reported_at_slot`** (it described the old rule) and gained the fields above.

## 9. Problems and surprises the next session must know

1. **A one-bar slack in the window.** The order's bound is one bar wider than the collector's window (a time bound, deviation 4). In the first version of my own tests, a "whole window re-pushed" cycle right after a promote did NOT end RETUNING, because the bar just below the previous window was still old. It is real, small and bounded to one cycle (the real worker re-sends the oldest bar first, so it is usually already new); it is pinned by a test and written in the ADR.
2. **Never put a `.ts` file under `railway-gateway/scripts/`.** `tsconfig.json` includes `scripts/**/*.ts`, so one TypeScript script there changes the build's common root and `nest build` writes `dist/src/main.js` instead of `dist/main.js`, which breaks `node dist/main`. I found it by reading the config before writing the kit, not by breaking the build. A test fails if a `.ts` appears there; the gotchas file has it.
3. **`railway run` cannot reach the production database from a laptop** (it injects the private `postgres.railway.internal` address). The kit's runbook line uses `DATABASE_PUBLIC_URL`. I corrected my first draft of the runbook after checking `prisma.production.config.ts`.
4. **My first mutation run read every mutant as "crash"** (Python decoded jest's UTF-8 output as cp1252) and I then killed the harness mid-mutant, which left `retuning.ts` mutated on disk. I restored it from the backup taken before any mutation, verified its sha256 and key lines, and changed the harness to keep one backup and refuse to start if a source differs from it. Nothing was reported from that run. The gotchas file has it.
5. **A mutant killed by "Test suite failed to run" is detection, but weak:** a describe-level computation threw before any test ran. Counted separately in the kit's result.
6. **The gated pg specs wipe the same tables** (as in part 9): never run `promote-retuning.pg.spec.ts` and `cycle-readers.pg.spec.ts` at the same time.
7. **`measure-cycles` crosses two clocks in two lines** (`manifest after validated`, and the VPS-clock lines): read a negative value there as clock skew, not as a bug (the line says how many are below 0).
8. **A quarantined row keeps its old `cycle_id`** and would hold RETUNING on until it leaves the window; collector cycle ids are assumed to only grow. Both are in the promote runbook.
9. **No UI text was added**, so the i18n rules do not apply.
