## 7. Problems and surprises the next session must know

1. **P1: with the real push worker, RETUNING can last days, not hours.** _This is a simulation, not a measurement._ What Option A counts is the M5 rows of the whole 3,000-bar window whose `cycle_id` is below the promote cycle's (`railway-gateway/src/cycle/retuning.ts:86-102`; it ends only at exactly 0, line 257). Every cycle rewrites the whole window under its own id (`promote_cycle`), but the worker re-sends only the newest 386 rows as the priority set and then the **oldest** unsent rows (`backfill_worker_api_gateway_v5.py:785-793`, `1042-1071`), so the middle of the window keeps its pre-promote `cycle_id` until it ages into the oldest part. I drove the unchanged `push_cycle` against the collector's re-queue semantics (every slot rewrites every bar, M15 every third slot, the gateway's upsert overwrites `cycle_id`, 3,000 bars per timeframe, every slot a trading slot) and counted the rows Option A counts. "Passes per slot" is how many times the worker's main loop runs per 5 minutes; a pass sends up to 500 rows (50 ms between rows plus the request, then a 30 s sleep), so 2 to 4 is what the constants suggest and the real value is unmeasured:

   | Most rows the worker can send | Pre-promote rows left, after … slots | Window clean after (trading days, 276 slots a day) |
   | ----------------------------- | ------------------------------------ | -------------------------------------------------- |
   | 100 a minute (1 pass a slot)  | 2,711 → 1,712 (+1000) → 712 (+2000)  | about 2,710 slots, **9.8 days**                    |
   | 200 a minute (2 passes)       | 1,688 (+1000) → 686 (+2000)          | about 2,690 slots, **9.7 days**                    |
   | 300 a minute (3 passes)       | 744 (+1000) → 243 (+1500)            | about 1,740 slots, **6.3 days**                    |
   | 400 a minute (4 passes)       | 182 (+1000)                          | about 1,180 slots, **4.3 days**                    |
   | 600 a minute (6 passes)       | 139 (+3), 130 (+12)                  | about 140 slots, **half a day**                    |
   | 800 a minute (8 passes)       | 0 (+1)                               | **one slot**                                       |

   At every rate below 800 a minute the first slots drop the count by an amount that depends on the rate (the oldest backlog and the M15 rows older than the M5 window are sent first), and after that the old rows fall by only about one a slot, because only rows that scroll out of the window get replaced; so the time is roughly the size of the remainder. The open throughput issue puts capacity at 375 to 600 rows a minute (unmeasured): that is half a day to about five. The builder's tests do not see this because they re-push arbitrary amounts per cycle (`promote-retuning.pg.spec.ts`, `pushWindow(m, 1000 | 2000 | 'all')`). Script and logs: session scratchpad, `sim_retune.py`, `sim-p*.log`.
