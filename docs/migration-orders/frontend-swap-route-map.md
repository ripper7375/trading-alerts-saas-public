## 1. F65 — BFF Boundary (RESOLVED)

**Decision:** Retain Next.js `app/api/**` as the permanent Backend-For-Frontend (BFF) proxy
layer. The browser talks only to its own origin (`/api/**`); Next.js route handlers read the
`httpOnly` NextAuth session cookie/JWE server-side, acquire service tokens via
`getOperationServiceToken()` / `getMoneyServiceToken()`, and call `operation-service` /
`money-service` through the server-only generated clients (`operationApi`/`moneyApi` from
[lib/api/index.ts](../../lib/api/index.ts)). Direct browser-to-microservice calls
(`NEXT_PUBLIC_*` endpoints) were rejected.

**Rationale (verified live, not just cited):**

1. **Auth semantics (F45).** NextAuth session cookies are `httpOnly`; browser JS has no access to
   them. Direct calls would require minting a bearer token into JS-reachable memory — one XSS
   away from account takeover, the same tradeoff F45 already rejected for money-service.
2. **Client bundling (L6).** Confirmed live this session: `lib/api/index.ts`'s own header comment
   states `operationApi`/`moneyApi` transitively import `next/headers` and will break the Next.js
   build if imported into any `'use client'` component. Zero current importers exist anywhere in
   `app/`/`components/`/`hooks/` (verified via the Phase-7 CONFIRM check and this session's own
   git-drift check, `8810b260..HEAD` on `app/api/`, `lib/api/`, `seed-code/` — zero commits).
3. **CORS/attack surface.** Confirmed live: F30 already resolved this exact question in Session
   3-4 ("skip CORS config if we continue proxying server-side — the browser never talks directly
   to NestJS") and `operation-service/src/main.ts`'s CORS config remains untouched. Direct
   browser-to-service calls would reopen a question already closed.
4. **Decommission scope (Session 8-1).** "Deleting migrated routes" in 8-1 means removing
   monolithic business logic and dead endpoints while KEEPING the thin, typed BFF proxy handlers
   — this route map's "Backing API" column is written on that assumption throughout.

**Undo cost:** Low/zero to maintain (this is the current production pattern already). High if a
browser-direct design were attempted later — would need a new token-vending or short-lived-token
mechanism (F45's own rejected options b/c).

**Approved by:** Davin, live in chat, 2026-08-22 (confirming the working-copy DRAFT→APPROVED
upgrade as his authentic edit, and the F65 decision within it).

## 2. F66 — Swap Mechanism & Brand Scope (RESOLVED)

**Swap mechanism:** Progressive layout-boundary replacement (Sessions 9-1…9-9), not a big-bang
branch swap. Each session transplants exactly one `layout.tsx` boundary + its guard + nav +
data/auth bindings, closing with a route-manifest diff (roadmap §Phase-9-preamble, reason 2:
"shell bugs cannot cross a session boundary" — the exact containment the Batch-3 double-`<AppHeader>`
bug needed and didn't have).

**Brand scope:** Rebrand UI chrome — page titles, headers, footers, metadata, OG images, legal
copy, `manifest.json`, email templates — from "Trading Alerts" to "DavinTrade".

**Live Stripe catalog — `⚠ NEEDS EXPLICIT SIGN-OFF`, confirmed:** Live Stripe Dashboard
product/price objects are **not** touched in code during Phase 9. Checkout UI renders
"DavinTrade Pro" while binding to the existing `STRIPE_PRO_MONTHLY_PRICE_ID`. Any Stripe-side
catalog renaming is Davin's own out-of-band administrative action.

**Approved by:** Davin, live in chat, 2026-08-22.
