## 1. Scope, invariants and non-goals

### 1.1 In scope

Replace the **final node** of the commission chain — the thing that actually moves money to an
affiliate's hands — from RiseWorks to Wise, inside `money-service`, without disturbing anything
upstream of the provider boundary.

```
Customer ──┬─► Stripe  ─┐
           └─► dLocal  ─┴─► Affiliate Program ─► [ DISBURSEMENT ] ─► affiliate
                              (Part 17)            Part 19  → RiseWorks   (archived)
                                                   Part 19.5 → Wise       (active)
```

### 1.3 Non-goals

- Migrating Stripe or dLocal (pay-**in** side) — untouched.
- Wise cards, balances-as-a-product, SWIFT receive, multi-currency treasury.
- Wise Platform _customer onboarding_ (creating Wise profiles for affiliates). Affiliates are
  **recipients**, not Wise users. No affiliate ever gets a Wise account in this design.
- Deleting any RiseWorks artefact.
- Frontend redesign (Phase 6 owns that). Part 19.5 adds the _minimum_ UI needed to collect
  recipient details and to complete the manual funding gate.

## 2. The two integration models, and why the design is capability-gated

Davin has not yet committed to an integration model (**F36**), and the account region is
**Thailand** (**F37**). Those two facts together produce a hard constraint:

|                                                   | **Model A — Wise Business + personal API token**                                          | **Model B — Wise Platform Enterprise partnership**                                              |
| ------------------------------------------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| How obtained                                      | Self-serve: Wise Business account → `Your Account > Connect and manage apps > API tokens` | Signed partnership + implementation team                                                        |
| Auth                                              | `Authorization: Bearer <personal token>` (static)                                         | OAuth client credentials + user tokens; optional mTLS                                           |
| Create quote / recipient / transfer / batch group | ✅                                                                                        | ✅                                                                                              |
| **Fund a transfer or batch group via API**        | ❌ **except** accounts in US, CA, AU, NZ, SG, MY                                          | ✅ (SCA-protected)                                                                              |
| Webhook subscription level                        | **Profile-level** (`POST /v1/profiles/{profileId}/subscriptions`)                         | **Application-level** (`POST /v3/applications/{clientKey}/subscriptions`) — recommended by Wise |
| Balance statements via API                        | ❌ (same regional exception)                                                              | ✅                                                                                              |
| SCA handling required                             | n/a in Model A (funding is manual)                                                        | Yes — `403` + `x-2fa-approval` OTT flow                                                         |

**Consequence for a Thailand-registered business on Model A:** money cannot leave the Wise balance
under program control. The system can do everything up to and including presenting a fully-formed,
completed batch group with pay-in details — then a human must fund it.

**Therefore the design does not treat funding as a method call. It treats funding as a _state_ of
the batch, with two possible transition mechanisms.** That is the single most important structural
decision in this document, and it is what makes Model A → Model B a config change later.

```
WISE_FUNDING_MODE=MANUAL   (default; Thailand, UK/EEA-on-personal-token)
   batch COMPLETED ──► payInDetails surfaced to admin UI
                   ──► human funds in Wise app / bank transfer using payInDetails.reference
                   ──► detected by (a) admin "Mark funded" action, or (b) balances#credit webhook
                   ──► transfers start processing ──► transfers#state-change drives the rest

WISE_FUNDING_MODE=API      (US/CA/AU/NZ/SG/MY on Model A, or any region on Model B)
   batch COMPLETED ──► POST /v3/profiles/{id}/batch-payments/{groupId}/payments {type:"BALANCE"}
                   ──► (Model B / UK-EEA: handle 403 + x-2fa-approval OTT challenge chain)
                   ──► transfers start processing ──► transfers#state-change drives the rest
```

Everything downstream of "transfers start processing" is **identical** in both modes. Only the
transition into `FUNDED` differs. `WISE_FUNDING_MODE=API` is **designed and documented here but
not built in Phase 1** — 4A-W6 builds the `MANUAL` path and leaves the `API` path as an explicit
`CapabilityUnavailableError`, so the failure is loud rather than silent.

## 3. Provider abstraction — additive capability interfaces

### 3.1 The problem

`PaymentProvider` (`money-service/src/disbursement/providers/base-provider.ts`, 174 lines) is
RiseWorks-shaped:

```ts
abstract class PaymentProvider {
  abstract readonly name: string;
  abstract authenticate(): Promise<AuthToken>;
  abstract sendPayment(request: PaymentRequest): Promise<PaymentResult>;
  abstract sendBatchPayment(
    requests: PaymentRequest[]
  ): Promise<BatchPaymentResult>;
  abstract getPaymentStatus(
    transactionId: string
  ): Promise<DisbursementTransactionStatus>;
  abstract getPayeeInfo(riseId: string): Promise<PayeeInfo>; // ← param literally named riseId
  abstract verifyWebhook(payload: string, signature: string): boolean;
}
```

`sendBatchPayment` assumes one call sends money. For Wise, one "send" is 4+ calls and may not
complete without a human.

### 3.2 Rejected option: widen the abstract class

Adding `fundBatch()` / `prepareBatch()` as abstract members forces `MockPaymentProvider` **and the
archived `RisePaymentProvider`** to implement them. That edits archived code (violates F42's
spirit), breaks 4A-2's ported test suites (the parity oracle), and makes `base-provider.ts` a
lie for two of its three implementations. **Rejected.**

### 3.3 Chosen option: keep the base class, add optional capability interfaces

New file `money-service/src/disbursement/providers/provider-capabilities.ts`:

```ts
/** Funding capability — implemented only by providers whose money movement is a
 *  separate, possibly-human step (Wise). Rise/Mock do not implement this. */
export type FundingMode = 'MANUAL' | 'API';

export interface PreparedBatch {
  providerBatchId: string; // Wise batch-group UUID
  providerBatchVersion: number; // Wise optimistic-concurrency version
  transfers: PreparedTransfer[];
  sourceCurrency: string;
  totalSourceAmount: number;
  failures: PreparedTransferFailure[]; // per-affiliate, non-fatal
}

export interface PreparedTransfer {
  commissionId: string;
  affiliateProfileId: string;
  providerTransferId: string; // Wise transfer id (numeric, stringified)
  providerQuoteId: string; // Wise quote UUID
  providerRecipientId: string; // Wise recipient/account id
  idempotencyKey: string; // customerTransactionId (UUID v4)
  sourceCurrency: string;
  sourceValue: number;
  targetCurrency: string;
  targetValue: number;
  rate: number;
  fee: number;
  reference: string;
}

export interface PayInInstruction {
  // mirrors Wise payInDetails[]
  type: 'bank_transfer';
  reference: string; // opaque — never parsed
  amount: number;
  currency: string;
  accountHolderName: string;
  accountNumber?: string | null;
  iban?: string | null;
  bankCode?: string | null;
  raw: Record<string, unknown>; // full Wise object, stored verbatim
}

export interface FundableProvider {
  readonly fundingMode: FundingMode;
  /** quote+recipient+transfer for every request, inside one provider batch. Money does NOT move. */
  prepareBatch(input: PrepareBatchInput): Promise<PreparedBatch>;
  /** close the provider batch to further changes; returns pay-in instructions. Money does NOT move. */
  completeBatch(providerBatchId: string): Promise<PayInInstruction[]>;
  /** MOVE MONEY. Throws CapabilityUnavailableError when fundingMode === 'MANUAL'. */
  fundBatchFromBalance(providerBatchId: string): Promise<void>;
  /** cancel a not-yet-funded provider batch */
  cancelBatch(providerBatchId: string, version: number): Promise<void>;
}

/** Recipient capability — providers that need a stored payee account object. */
export interface RecipientAwareProvider {
  getAccountRequirements(
    input: AccountRequirementsInput
  ): Promise<RequirementGroup[]>;
  createRecipient(input: CreateRecipientInput): Promise<ProviderRecipient>;
  getRecipient(providerRecipientId: string): Promise<ProviderRecipient>;
  deactivateRecipient(providerRecipientId: string): Promise<void>;
}

export function isFundable(
  p: PaymentProvider
): p is PaymentProvider & FundableProvider {
  return typeof (p as Partial<FundableProvider>).prepareBatch === 'function';
}
```

`WisePaymentProvider extends PaymentProvider implements FundableProvider, RecipientAwareProvider`.

**How `WisePaymentProvider` satisfies the unchanged base class:**

| Base member                   | Wise implementation                                                                                                                                                                                                                |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`                        | `'WISE'`                                                                                                                                                                                                                           |
| `authenticate()`              | Returns the configured static token with a far-future `expiresAt` in Model A. In Model B, performs the client-credentials grant and caches until expiry. Never throws for Model A.                                                 |
| `sendPayment(req)`            | Single-transfer quick-pay path: quote → resolve recipient → transfer. Returns `status: 'PENDING'` — **not** `'COMPLETED'`. Funding is separate.                                                                                    |
| `sendBatchPayment(reqs)`      | Delegates to `prepareBatch` + `completeBatch`, returns `BatchPaymentResult` with **every** `PaymentResult.status = 'PENDING'`. **`successCount` means "successfully drafted", not "paid".** ⚠️ See §3.4.                           |
| `getPaymentStatus(txId)`      | `GET /v1/transfers/{wiseTransferId}` → map `status` via §5.2 table                                                                                                                                                                 |
| `getPayeeInfo(id)`            | `GET /v1/accounts/{recipientId}` → `PayeeInfo{ riseId: <recipientId>, email, kycStatus: 'APPROVED'\|'PENDING', canReceivePayments }`. The field is _named_ `riseId` (I1) but carries a Wise recipient id. Documented, not renamed. |
| `verifyWebhook(payload, sig)` | RSA-SHA256 verify, base64 signature, Wise public key. Signature is asymmetric, so no secret is needed — the method shape still fits.                                                                                               |

### 3.4 ⚠️ Semantic hazard that must be handled in 4A-W6

`money-service/src/disbursement/payment-orchestrator.service.ts` (333 lines) currently does, in
`executeBatch`:

```
const result = await provider.sendBatchPayment(paymentRequests);
// …then writes per-transaction status from paymentResult.status
```

With RiseWorks/Mock, `sendBatchPayment` returning `COMPLETED` meant _paid_. With Wise it means
_drafted, awaiting funding_. If the orchestrator is left to interpret Wise results the same way,
`Commission.status` will flip to `PAID` and `AffiliateProfile.pendingCommissions` will be
decremented **before any money moves** — a silent accounting corruption.

**Design requirement (invariant-adjacent — escalate if it cannot be met):**
`PaymentOrchestratorService` must branch on `isFundable(provider)`:

- **not fundable** (Mock, archived Rise) → today's behaviour, byte-for-byte.
- **fundable** → after `prepareBatch`/`completeBatch`, write `DisbursementTransaction.status = 'PENDING'`,
  `PaymentBatch.status = 'PROCESSING'`, and **never** touch `Commission.status` or the affiliate
  balance. Those are written **only** by the webhook reducer (§5.3).

This is the boundary that makes the whole design safe: **in Wise mode, only a verified webhook (or
the reconciliation cron) may mark money as paid.**

### 3.5 ⚠️ Two concrete Rise-coupling bugs the Wise path _will_ hit (found 2026-07-25)

These are not hypothetical — they are in the code today and they fail **silently**, which is worse
than throwing. Both must be fixed in 4A-W6.

**(a) `affiliateId` resolves to an empty string for Wise transactions.**
`payment-orchestrator.service.ts` builds its payment requests like this (≈line 117):

```ts
affiliateId: txn.affiliateRiseAccount?.affiliateProfileId || '',
riseId:      txn.payeeRiseId || '',
```

`transaction.service.ts` (310 lines, ≈line 80) populates `affiliateRiseAccountId` and `payeeRiseId`
**from the Rise account relation**:

```ts
affiliateRiseAccountId: commission.affiliateProfile?.riseAccount?.id,
payeeRiseId:            commission.affiliateProfile?.riseAccount?.riseId,
```

A Wise-provider transaction has **no** `AffiliateRiseAccount`, so both are `undefined`, so
`affiliateId` and `riseId` both become `''`. Nothing throws — the batch is built with blank payee
identity and the Wise provider has nothing to resolve a recipient from.

**Fix (4A-W6):** derive the affiliate reference from the commission, not from the Rise relation.
`Commission.affiliateProfileId` is always present (it is a required FK). Either:

- resolve `affiliateId` from `txn.commission.affiliateProfileId` in the orchestrator, **or**
- have `WisePaymentProvider` ignore `PaymentRequest.riseId` entirely and look the recipient up by
  `commissionId → Commission.affiliateProfileId → AffiliateWiseRecipient`.

Prefer the first — it fixes the field for every future provider rather than working around it in
one. Either way it is a **behaviour-preserving change on the Rise/Mock path** (for Rise,
`affiliateRiseAccount.affiliateProfileId` and `commission.affiliateProfileId` are the same value by
construction), so the existing orchestrator tests must still pass unmodified.

**(b) `amountRiseUnits` is already correctly branched — leave it alone.**
`transaction.service.ts` ≈line 84 already does
`provider === 'RISE' ? usdToRiseUnits(...) : null`, so Wise rows get `NULL` with no change needed.
✅ No edit. But **five readers must tolerate that null**, and they are not the files a casual grep
suggests:

| Reader                                                                      | Note                                                                                                                                       |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `money-service/src/disbursement/transaction.service.ts` (~82, ~84)          | writer — already branched                                                                                                                  |
| `money-service/src/disbursement/payment-orchestrator.service.ts` (~118)     | reads `payeeRiseId` — this is bug (a)                                                                                                      |
| `app/api/disbursement/batches/[batchId]/route.ts` (~97)                     | `txn.amountRiseUnits?.toString()` — already null-safe ✅                                                                                   |
| `app/(dashboard)/admin/disbursement/transactions/page.tsx` (~33, ~35, ~281) | typed `number \| null` / `string \| null` — renders a Rise-specific column; should show the Wise transfer id instead when provider is WISE |
| `app/(dashboard)/admin/disbursement/batches/[batchId]/page.tsx` (~35, ~490) | same — `payeeRiseId.slice(0, 10)` behind a truthiness check ✅, but the column label is wrong for Wise                                     |

So the _type_ safety is already there; what needs work is the **UI labelling** (a Rise-address
column shown for a bank payout) — a W6 UI task, not a null-safety bug.

### 4.3 Why a separate `WiseTransfer` rather than columns on `DisbursementTransaction`

1. `DisbursementTransaction` is **shared** with archived Rise rows. Adding 18 Wise columns makes
   every historical Rise row carry 18 nulls and couples the shared table to one provider.
2. `money-service/prisma/schema.prisma` mirrors `DisbursementTransaction` by hand; a wide change
   there multiplies the L24 hand-sync risk.
3. The `balanceAppliedAt` / `balanceRevertedAt` guards belong to Wise's rollback semantics, which
   Rise does not have.
4. Retiring Wise later (or adding a third provider) is a table, not a schema surgery.

### 4.4 What is deliberately **not** stored

- Raw bank account numbers, IBANs, sort codes, routing numbers, national ID numbers, dates of
  birth. These are POSTed straight to Wise from the collection surface and never persisted
  locally. Only `accountTail` (4 digits) and an irreversible `detailsFingerprint` remain. See §7.4
  and flag **F41**.
- The Wise API token, in any table. Env/secret store only.
- Any derived FX rate cache — quotes are short-lived (30 min lock) and re-fetched per batch.

## 5. Lifecycle, state mapping and the idempotent reducer

### 5.1 Why `currentState` is a `String`, not a Prisma enum

Wise documents 10 transfer states today and explicitly warns that new **payout failure codes** can
appear and that integrations must tolerate unrecognised values. A Prisma enum turns a new Wise
state into a _write failure_ (dropped event, 500 back to Wise, retry storm). A `String` plus an
exhaustive-with-default mapping function turns it into a logged `skippedReason: 'unknown-state'`
and an alert. **Fail visible, not fatal.**

### 5.2 Wise state → internal status (this table is contract law)

> **INVARIANT — frozen at Session 4A-W1, 2026-07-26.** Changing any row below requires a Deviation
> with written justification, per this order's Step 9.2. It is not a routine edit.

| Wise `data.current_state`      | `DisbursementTransaction.status`      | `Commission.status`                      | Affiliate balance                              | Notes                                                                                                                                           |
| ------------------------------ | ------------------------------------- | ---------------------------------------- | ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| _(transfer created, unfunded)_ | `PENDING`                             | unchanged (`APPROVED`)                   | untouched                                      | `sendBatchPayment` result state                                                                                                                 |
| `incoming_payment_waiting`     | `PENDING`                             | unchanged                                | untouched                                      | Wise awaiting our funding                                                                                                                       |
| `incoming_payment_initiated`   | `PROCESSING`                          | unchanged                                | untouched                                      | funding in flight                                                                                                                               |
| `processing`                   | `PROCESSING`                          | unchanged                                | untouched                                      | AML/compliance/fraud checks                                                                                                                     |
| `funds_converted`              | `PROCESSING`                          | unchanged                                | untouched                                      | FX done                                                                                                                                         |
| **`outgoing_payment_sent`**    | **`COMPLETED`**                       | **`PAID`** (`paidAt` set)                | **pending → paid, once** (`balanceAppliedAt`)  | Wise has paid out. _Not_ proof of credit at the beneficiary bank.                                                                               |
| `bounced_back`                 | `PROCESSING` + `hasActiveIssues=true` | **left `PAID`**                          | **not reverted**                               | Wise says it may still deliver, or may go to `funds_refunded`. Reverting here would flap the affiliate's balance. Raise an admin alert instead. |
| `funds_refunded`               | `FAILED`                              | revert `PAID → APPROVED`, clear `paidAt` | **paid → pending, once** (`balanceRevertedAt`) | Terminal-unhappy. Affiliate must fix details; recipient → `INVALID`.                                                                            |
| `charged_back`                 | `FAILED`                              | revert if it was `PAID`                  | revert, once                                   | Can follow **any** state.                                                                                                                       |
| `cancelled`                    | `CANCELLED`                           | revert if it was `PAID`                  | revert, once                                   | Usually "never funded within 14 days".                                                                                                          |
| `unknown`                      | `PROCESSING`                          | unchanged                                | untouched                                      | Alert + manual review; never auto-resolve.                                                                                                      |
| _anything unrecognised_        | unchanged                             | unchanged                                | untouched                                      | Persist event, `skippedReason='unknown-state'`, alert.                                                                                          |

`transfers#payout-failure` is processed **separately and additively** (Wise's own instruction): it
writes `payoutFailureCode` / `payoutFailureDescription` / `hasActiveIssues` and raises an alert,
and it **never** changes `Commission.status` or the balance — because a payout failure does not
always change transfer state.

### 5.3 The at-most-once accounting guards

The existing Rise processor (`webhook-event-processor.service.ts`, 288 lines) guards idempotency
with `if (transaction.status === 'COMPLETED') return`. That is sufficient for a provider with no
rollback. Wise has rollbacks, so status alone is not a guard: `COMPLETED → FAILED → COMPLETED` is
reachable and would double-apply the balance.

**Rule:** the pending→paid move is gated on `WiseTransfer.balanceAppliedAt IS NULL`; the reversal
on `balanceAppliedAt IS NOT NULL AND balanceRevertedAt IS NULL`. Both are written **inside the same
`prisma.$transaction`** as the balance mutation. Concretely:

```ts
await this.prisma.$transaction(async (tx) => {
  const guard = await tx.wiseTransfer.updateMany({
    where: { id: wiseTransfer.id, balanceAppliedAt: null }, // ← the lock
    data: { balanceAppliedAt: new Date() },
  });
  if (guard.count === 0) return; // already applied; nothing to do

  await tx.disbursementTransaction.update({
    /* COMPLETED, completedAt */
  });
  const commission = await tx.commission.update({
    /* PAID, paidAt */
  });
  await tx.affiliateProfile.update({
    where: { id: commission.affiliateProfileId },
    data: {
      pendingCommissions: { decrement: commission.commissionAmount },
      paidCommissions: { increment: commission.commissionAmount },
    },
  });
});
```

`updateMany`-as-a-lock is the pattern already proven in this codebase: Session 4A-5's dLocal
replay fix (commit `1cc31b24`) and the Rise `handleInviteAccepted` `updateMany({ where: {
invitationAcceptedAt: null }})` both use it. Reuse it rather than inventing a new mechanism.

### 5.4 Out-of-order delivery and dedupe

Wise states plainly: _"Events may not be delivered in the order they occurred. Use
`data.occurred_at` to reconcile the order."_ Retries can also redeliver an event up to 25 times
over two weeks.

Two guards, both required:

1. **Dedupe — `WiseWebhookEvent.deliveryId @unique` (from `X-Delivery-Id`).** The controller does
   `create`; a unique-violation means "already received" → return `200` immediately, do not
   reprocess. This is cheaper and more precise than content hashing.
2. **Ordering — `WiseTransfer.lastEventOccurredAt`.** The reducer refuses any event whose
   `data.occurred_at` is **≤** the stored value, recording `skippedReason: 'stale-order'`. This
   makes `processing` arriving _after_ `outgoing_payment_sent` a no-op instead of a regression.
   Note the exception: `charged_back` may legitimately follow any state and must still be applied
   if its `occurred_at` is newer — which the same rule already handles correctly.

### 5.5 Store-then-process (why the Wise controller differs from the Rise controller)

Wise requires a `2xx` **within 5 seconds** and recommends "do some basic validation and then store
the notification for processing by a separate server process."

The Rise controller processes synchronously inside the request. For Wise:

```
POST /v1/webhooks/wise
  1. read request.rawBody               (main.ts already sets rawBody: true — Session 4A-4)
  2. verify X-Signature-SHA256 (RSA-SHA256, base64, Wise public key)  → 401 on failure, and
     still persist the attempt with signatureVerified=false
  3. if X-Test-Notification: true       → persist, mark processed, 200, do nothing else
  4. create WiseWebhookEvent (deliveryId unique)   → on P2002, 200 (duplicate)
  5. enqueue { webhookEventId } on BullMQ queue  money:wise-webhook
  6. return 200 { status: "ok" }        ← target < 500ms
```

A BullMQ worker (`@nestjs/bullmq` + `bullmq` are already dependencies of `money-service`; the
`money` queue prefix is already registered in `app.module.ts`) runs the reducer with retries and a
dead-letter path. **No new infrastructure and no new dependency is required.**

Response body shape `{"status":"ok"}` matches what Wise's own event docs document as the expected
200 body.

## 6. Payout flow, end to end

### 6.1 Recipient onboarding (new surface — flag F39)

Wise cannot pay an affiliate until a **recipient account** exists, and the required fields differ
per currency/country/route. They must be discovered at runtime, never hard-coded:

```
GET  /v1/quotes/{quoteId}/account-requirements     (Accept-Minor-Version: 1)
POST /v1/quotes/{quoteId}/account-requirements     (re-fetch when a field has
                                                    refreshRequirementsOnChange: true)
POST /v1/accounts                                  → { id: <recipientId>, … }
```

Design:

1. money-service exposes `GET /v1/wise/recipients/requirements?targetCurrency=THB&country=TH`
   which creates a throwaway quote (or reuses a cached one), calls Wise, and returns a **normalised
   field schema** (`RequirementGroup[]`) to the frontend.
2. The frontend renders that schema dynamically — no hard-coded THB form. `Accept-Minor-Version: 1`
   is mandatory so `accountHolderName` and `email` arrive as part of the dynamic schema (needed for
   KRW/JPY/RUB and it removes hand-rolled name validation).
3. `POST /v1/wise/recipients` receives the filled details, POSTs them to Wise, stores only
   `wiseRecipientId`, `accountTail`, `detailsFingerprint`, status `ACTIVE`.
4. `refreshRequirementsOnChange` handling is mandatory: `address.country = "US"` only reveals the
   `state` field on the POST round-trip.

**F39 decides _who_ fills the form:** affiliate self-service (recommended — the affiliate owns
their own bank data, and a bounced payout is their problem to fix) or admin-entered (fewer
surfaces, but the platform then handles third-party bank PII). Either way the _backend_ is the
same; only the guard differs (`AffiliateGuard` vs `AdminGuard`).

### 6.2 Batch payout — MANUAL funding mode (Phase 1, Thailand)

```
(cron: process-pending-disbursements, already cut over in 4A-3)
 │
 ├─1 CommissionAggregatorService  → eligible affiliates (≥ $50, APPROVED commissions)
 │     + NEW filter: AffiliateWiseRecipient.status === 'ACTIVE'
 │       (replaces the old AffiliateRiseAccount KYC-APPROVED filter)
 ├─2 BatchManagerService.createBatch → PaymentBatch{ provider: WISE, status: PENDING }
 │
 ├─3 WisePaymentProvider.prepareBatch:
 │     POST /v3/profiles/{profileId}/batch-groups   { sourceCurrency, name: batchNumber }
 │     for each affiliate  (sequential, rate-limit aware):
 │        POST /v3/profiles/{profileId}/quotes      { sourceCurrency, targetCurrency,
 │                                                    sourceAmount, targetAccount }
 │        GET  /v1/transfer-requirements  (validate)
 │        POST /v3/profiles/{profileId}/batch-groups/{groupId}/transfers
 │             { targetAccount, quoteUuid, customerTransactionId: <UUID v4>,
 │               details: { reference: "DavinTrade commission <batchNumber>" } }
 │     → WiseTransfer rows, status PENDING.  NO MONEY HAS MOVED.
 │
 ├─4 WisePaymentProvider.completeBatch:
 │     PATCH …/batch-groups/{groupId}  { status: "COMPLETED", version }
 │     → payInDetails[]  → WiseBatchGroup.status = AWAITING_MANUAL_FUNDING
 │
 ├─5 ⛔ HUMAN GATE. Admin UI shows the batch, its total, and payInDetails
 │     (reference, amount, currency, account holder, account number/IBAN).
 │     Davin funds it: from the Wise balance in the Wise app, or by bank transfer
 │     using payInDetails.reference verbatim (opaque — never edit or decompose it).
 │
 ├─6 Funding observed, one of:
 │     (a) admin POSTs /v1/wise/batches/{id}/mark-funded { evidence }
 │           → fundingSource = MANUAL_ADMIN
 │     (b) balances#credit / balances#update webhook matched to the batch amount
 │           → fundingSource = MANUAL_DETECTED   (best-effort; (a) is authoritative)
 │     → WiseBatchGroup.status = FUNDED, fundedAt set
 │
 └─7 Wise processes. transfers#state-change webhooks arrive per transfer →
       reducer (§5.3) → DisbursementTransaction / Commission / balance.
       Reconciliation cron (§6.5) catches anything the webhooks missed.
```

**Why the batch never auto-expires silently:** a Wise transfer is auto-cancelled if unfunded for
~14 days. The reconciliation cron must alert when a `AWAITING_MANUAL_FUNDING` batch is older than
a configurable `WISE_FUNDING_SLA_HOURS` (default 72) — otherwise the human gate becomes a silent
black hole. This is a **required** part of W6, not a nice-to-have.

### 6.3 Batch payout — API funding mode (designed, not built in Phase 1)

Identical through step 4, then:

```
POST /v3/profiles/{profileId}/batch-payments/{batchGroupId}/payments  { "type": "BALANCE" }
  ├─ 200 → fundingSource = API_BALANCE, status = FUNDED
  ├─ 403 + x-2fa-approval: <ott>  → SCA required (UK/EEA, Model B):
  │     GET  /v1/identity/one-time-token/status   (One-Time-Token: <ott>)
  │     clear ≥2 challenges of different types (PIN / device fingerprint / OTP / FaceTec)
  │     retry the fund call with  x-2fa-approval: <cleared ott>
  └─ insufficient funds → do NOT retry blindly; alert, leave AWAITING_MANUAL_FUNDING
```

In Phase 1, `fundBatchFromBalance` throws `CapabilityUnavailableError` when
`WISE_FUNDING_MODE=MANUAL`. Building the SCA chain is out of scope until F36 resolves to Model B.

### 6.4 Quick pay (single affiliate) and the `MAX_BATCH_SIZE` question

`app/api/disbursement/pay` (quick pay, one affiliate) maps to `sendPayment` → one quote, one
transfer, no batch group. In MANUAL mode it still needs funding, so it lands in the same
`AWAITING_MANUAL_FUNDING` gate as a batch of one — implement it as a 1-transfer batch group rather
than a special path, so there is exactly one funding gate in the system.

`MAX_BATCH_SIZE` stays **100** (I4) even though Wise permits 1000: the current value is already
proven through aggregation, batch-number generation and the admin UI's pagination, and raising it
is a separate, testable change with no urgency.

### 6.5 Reconciliation cron (new, required)

Webhook delivery is explicitly **best-effort** ("Please contact us if you believe you missed any
webhook events"). A money system cannot rely on best-effort alone.

New scheduled job in `money-service/src/crons/` — `wise-reconciliation`, hourly:

1. For every `WiseTransfer` not in a terminal state and older than 30 minutes:
   `GET /v1/transfers/{wiseTransferId}` → feed the response through the **same reducer** as a
   synthetic event (`deliveryId = "recon:<transferId>:<status>:<isoHour>"`, so it dedupes naturally).
2. For every `WiseBatchGroup` in `AWAITING_MANUAL_FUNDING` older than `WISE_FUNDING_SLA_HOURS`:
   raise an admin `Notification` + log.
3. For every `WiseWebhookEvent` with `processed=false AND attemptCount >= max`: surface on the
   admin health page.

Same reducer, same guards ⇒ reconciliation can never double-apply a balance. That is the whole
point of putting the guards on the row rather than in the handler.

## 7. Security

### 7.1 Webhook signature verification (RSA-SHA256, asymmetric)

```
header:  X-Signature-SHA256: <base64>
verify:  crypto.createVerify('RSA-SHA256')
               .update(rawBody)                 // exact bytes, not re-serialised JSON
               .verify(wisePublicKeyPem, signature, 'base64')
```

Both Wise public keys (production and sandbox) are **published** in Wise's docs — they are not
secrets. Ship them as constants in `wise-signature.constants.ts`, selected by `WISE_ENV`, but make
each **overridable by env** (`WISE_WEBHOOK_PUBLIC_KEY_PEM`) so a Wise key rotation is a redeploy,
not a code release. Exact PEMs are reproduced in `02-…` §5.

Verification order matters: **verify before `JSON.parse`**. Signature is over the raw bytes; parsing
first invites a parser-differential. And unlike dLocal/Rise, no shared secret exists — so there is
no `RISE_WEBHOOK_SECRET`-style env var to forget (Session 4A-5's Waiting-on #26 class of problem
disappears for Wise).

> **Lesson carried forward from Session 4A-5:** that session leaked `DLOCAL_WEBHOOK_SECRET` into a
> transcript via `railway variables --kv`. For Wise, verify env presence **value-blind**
> (`railway variables | grep -c WISE_API_TOKEN`, or a `/health-auth`-style boolean), never by
> printing values.

### 7.2 Secrets

| Env var                       | Sensitivity                        | Notes                                                                                                                                                         |
| ----------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `WISE_API_TOKEN`              | **CRITICAL — can move real money** | Full-access personal token (Model A) or client secret (Model B). Rotate on any suspicion. Never logged, never in a URL, never printed by a verification step. |
| `WISE_PROFILE_ID`             | low                                | Business profile id; appears in v3 paths                                                                                                                      |
| `WISE_ENV`                    | low                                | `sandbox` \| `production` — selects base URL **and** public key                                                                                               |
| `WISE_FUNDING_MODE`           | low                                | `MANUAL` \| `API` (F37)                                                                                                                                       |
| `WISE_SOURCE_CURRENCY`        | low                                | balance currency funds are drawn from (e.g. `USD`)                                                                                                            |
| `WISE_FEE_BEARER`             | low                                | `PLATFORM` \| `AFFILIATE` (F38)                                                                                                                               |
| `WISE_FUNDING_SLA_HOURS`      | low                                | default `72`                                                                                                                                                  |
| `WISE_WEBHOOK_PUBLIC_KEY_PEM` | low (public)                       | optional override for key rotation                                                                                                                            |
| `DISBURSEMENT_PROVIDER`       | medium                             | existing var; becomes `WISE` at cutover (was `MOCK`)                                                                                                          |
| `ALLOW_ARCHIVED_PROVIDERS`    | low                                | default unset; must be `true` for `RISE` to be constructible (§ runbook `03-…`)                                                                               |

`WISE_API_TOKEN` must be added to the Session 0-4 secret matrix. Read-only vs full-access matters:
a **read-only** token cannot create transfers, so W3/W5 (recipients + webhooks) can be developed
against a read-only token, and only W6 needs full access. **Recommendation: two tokens, promoted
per session** — it means a leak during W3/W5 cannot move money.

### 7.3 Network posture

- Endpoint requirements Wise enforces: HTTPS on 443, valid CA cert, FQDN (no IP), **no query
  string**, **no port in the URL**, no redirects (any 3xx is a delivery error). Railway's
  `https://money-service-production.up.railway.app/v1/webhooks/wise` satisfies all of these — the
  same shape already proven for `/v1/webhooks/dlocal` in Session 4A-5.
- Optional hardening: allowlist Wise's sender CIDRs `45.129.54.0/24` and `45.129.55.0/24`
  (production) — but Wise itself says IP allowlisting must never be the only control. Signature
  verification remains mandatory regardless.
- `X-External-Correlation-Id` (UUID) on **every** outbound Wise call, sourced from the CC-B
  correlation id. Wise echoes it, which makes support tickets tractable.

### 7.4 PII and data protection

Recipient bank details are **third-party personal data** (the affiliate's), and the platform is in
Thailand → PDPA applies alongside GDPR for EU affiliates. Design position:

- **Data minimisation by transit:** details are POSTed to Wise and not persisted. Local storage is
  `wiseRecipientId` + `accountTail` (4 digits) + irreversible `detailsFingerprint`.
- **No details in logs.** The Wise client must have an explicit request-body redaction list for
  `POST /v1/accounts` (redact the whole `details` object) — this is a _code requirement_, not a
  convention.
- Interaction with **F21** (the open 24h account-deletion GDPR gap): deleting an affiliate must
  also deactivate their Wise recipient (`DELETE`/deactivate at Wise), otherwise a "deleted" user
  still has bank details at a processor. Raise as new flag **F41** and cross-reference F21 rather
  than solving it inside a W-session.

### 7.5 Authorisation on the new endpoints

Reuse what Session 4A-6 already built and Davin already confirmed correct: `JwtAuthGuard` +
`AdminGuard` / `AffiliateGuard`, with the browser attaching `Authorization: Bearer <token>`
(blueprint §4.2, no cross-domain cookies — CLAUDE.md Waiting-on #34). No new auth mechanism.

- Admin-only: batch complete, mark-funded, fund-via-API, recipients list, config.
- Affiliate-scoped: own recipient create/update/read (if F39 → self-service).
- Webhook: **no guard** — signature _is_ the authentication. It must be excluded from
  `ThrottlerGuard`'s global limit — but **not** with `@SkipThrottle()`. ⚠️ **Corrected 2026-07-25
  (rev 2):** `@SkipThrottle()` removes the ceiling entirely, trading a throttling fault for a
  flooding fault. The policy set in **session 4A-W4** is an explicit generous per-route limit
  (`@Throttle({ default: { ttl: 60_000, limit: 300 } })` as the starting point), applied to
  `/v1/webhooks/dlocal` **and** inherited here. Legitimate provider traffic is low and bounded
  (Wise retries ≤25 times over ~2 weeks with exponential backoff), so a high ceiling costs nothing
  and still bounds a flood. ⚠️ This is a real trap: `ThrottlerGuard` is registered as
  `APP_GUARD` in `app.module.ts`, so it applies to the webhook route by default.

### 8.0 Prerequisites this module assumes, delivered by session 4A-W4 (rev 2)

Two CC-C requirements the Wise module depends on are **not currently satisfied by money-service**,
and neither is Wise-specific. Both are fixed in `4A-W4` before the webhook module is built:

1. **Graceful shutdown.** `money-service/src/main.ts` (51 lines) never calls
   `app.enableShutdownHooks()`. Nest only runs lifecycle hooks on SIGTERM when they are enabled, so
   `PrismaService.onModuleDestroy()` (`money-service/src/prisma/prisma.service.ts:36`) **has never
   executed**. Plan §13 CC-C states the consequence directly: _"Railway redeploys will otherwise
   sever in-flight batch payouts."_ That is precisely the `prepareBatch` scenario — a redeploy
   landing mid-loop while 40 Wise transfers are being created. `customerTransactionId` resumability
   (§6.2 step 3) mitigates the _consequence_; `enableShutdownHooks()` + a BullMQ drain on SIGTERM
   fixes the _cause_.
2. **BullMQ job-ID policy.** W5 introduces money-service's **first** queue consumer —
   `BullModule.forRoot` has existed since 4A-1 but there is no `registerQueue` and no `@Processor`
   anywhere (verified 2026-07-25). CC-C requires job IDs derived from business keys so a retry can
   never double-fire a payout. For `money:wise-webhook` the natural key is the
   **`X-Delivery-Id`** — the same value that already provides the dedupe guarantee at the DB level
   (§5.4), so the queue and the table agree by construction rather than by convention.

   **Policy, decided at 4A-W4 (binding on 4A-W5 and every session after it):** `jobId` MUST be
   derived deterministically from business event keys, never a random/auto-incrementing id —
   BullMQ dedupes enqueues on `jobId` at the Redis level, so a deterministic id makes a retried
   enqueue a no-op instead of a second job.
   - Webhook processing jobs: `jobId = wise:event:<deliveryId>` (the `X-Delivery-Id` header, same
     value as `WiseWebhookEvent.deliveryId`'s `@unique` column, §5.4).
   - Transfer execution jobs: `jobId = wise:transfer:<customerTransactionId>`.

   This composes with 4A-W4's other prerequisite: `Worker.close()` (called from the `@Processor`
   class's own `onModuleDestroy()`, per 4A-W4's shutdown-hook fix above) waits for the
   currently-processing job to finish before the process exits, so an in-flight job is never
   silently dropped and re-enqueued with a fresh id on the next boot.

Sandbox constraints to design around (Wise's own list): sandbox is UK-region / GBP-USD-EUR-stable;
rates are realistic but **not live**; simulation calls must be made **in order** with ≥5 s between

Thai (THB) route cannot be fully exercised in sandbox — plan the sandbox E2E as GBP→USD or
GBP→EUR and treat the THB route as verified only by W7's real smoke payout. **State this
limitation in W6's Done-when rather than discovering it mid-session.**

## 14. What could still bite (known unknowns, stated up front)

1. **Business Payment Approvals.** Wise documents that approval rules configured on wise.com are
   **incompatible with API-created transfers** — transfers fail with _"Quote cannot be accepted
   with this request due to missing approval."_ If Davin has any approval rule on the business
   account, it must be removed before W6. **This is a W1 entry-criterion, checked in the Wise UI.**
2. **Sandbox ≠ THB.** See §10. The Thai payout route's account-requirements shape is only knowable
   against production. W3 must therefore fetch and _record_ the real THB requirement schema from
   production (a read-only, non-money call) rather than guessing it.
3. **`transfers#active-cases` / `balances#credit` schema.** These are older profile-level events
   with v1/v2-era payloads; the modern documented pair is `transfers#state-change` +
   `transfers#payout-failure` (both with `4.0.0` schemas). Prefer the modern pair; treat
   `balances#credit` as a _convenience_ for funding detection with `MANUAL_ADMIN` as the
   authoritative path (§6.2 step 6).
4. **Quote/transfer 1:1.** One Wise quote creates exactly one transfer, and the rate locks for 30
   minutes. A 100-affiliate batch therefore makes ≥100 quotes and must complete inside the lock
   window — sequential-with-backoff at ≤100 req/s is fine, but a batch that stalls mid-preparation
   leaves orphan quotes. `prepareBatch` must be resumable: on retry, skip commissions that already
   have a `WiseTransfer` with a `customerTransactionId` (that's what the unique key is for).
5. **`amountRiseUnits` stays NULL for Wise rows** — already handled correctly by
   `transaction.service.ts`'s existing `provider === 'RISE' ? … : null` branch, and every reader is
   already null-safe (§3.5(b)). The residual work is UI labelling, not null-safety.
6. **Slice 4 overlap.** Sessions 4A-9/10 will move the remaining write APIs, including
   `batches/[batchId]/execute`. W6 changes that path's behaviour. Whichever runs second must
   re-read the other's Deviations — flag this in the handoff, not at merge time.
