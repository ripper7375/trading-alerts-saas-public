**Ground-Truth Prerequisites & Environment Setup — dLocal Configuration**

This configuration targets dLocal's Sandbox environment for a Payins/Payouts integration under the DavinTrade test account. All values are sourced directly from the Merchant Dashboard (Developers > Integration > API Credential > Sandbox credentials) and cross-referenced against dLocal's official documentation (Get API Credentials and Payins Security/Authentication reference pages).

The base environment variable `DLOCAL_API_URL` should be set to `https://sandbox.dlocal.com`, which is the correct base endpoint for sandbox testing before any production cutover.

dLocal does not expose a single credential literally called an "API key." Authentication is instead built from three distinct values obtained from the dashboard: X-Login, which identifies the merchant account making the request; X-Trans-Key, which is sent alongside X-Login to authenticate the request; and a Secret key, which is used to generate the HMAC-SHA256 signature placed in the Authorization header of every API call. In the conventional `.env` naming scheme used here, `DLOCAL_API_KEY` should be populated with the full X-Trans-Key value, and `DLOCAL_SECRET_KEY` should be populated with the full Secret key value. Both are currently masked in the dashboard UI (shown as `kfwX6*******` and `JdkIbq************` respectively) and must be unmasked via the "View credentials" action to obtain the complete strings before they are placed into any environment file.

The caveat that Antigravity should account for during implementation is that X-Login is a required third credential that is not captured by either `DLOCAL_API_KEY` or `DLOCAL_SECRET_KEY` in this two-variable naming convention. Every signed request to dLocal's API needs X-Login sent as its own header alongside X-Trans-Key, and it also forms part of the signature input itself (`hmac(secretKey, "X-Login+X-Date+RequestBody")`). Depending on which SDK or client library Antigravity chooses to implement against, this value may need its own environment variable, commonly something like `DLOCAL_LOGIN` or `DLOCAL_X_LOGIN`, rather than being folded into `DLOCAL_API_KEY`. Before finalizing the environment schema, it would be worth confirming how the specific SDK or HTTP client library in use expects to receive this value, since treating `DLOCAL_API_KEY` as sufficient on its own would produce authentication failures against dLocal's API.
