## จังหวะการทำงานในทุกๆ รอบ (ควรอ่านส่วนนี้อย่างระมัดระวังให้เข้าใจ)

ทุกๆ รอบการทำงานจะมีจังหวะการทำงาน 5 ขั้นตอน (Beats) เหมือนกันเสมอ แค่เนื้อหาเปลี่ยนไปเท่านั้น:

```
BEAT 1  คุณ → ส่งให้ Cowork (Advisor):  ส่งแผนร่างคร่าวๆ (PRE-DRAFT) ให้, แล้วรอรับแผนร่างฉบับละเอียด (DRAFT)  (~ไม่กี่นาที)
BEAT 2  คุณ:                     อ่านแผนละเอียด DRAFT (1-2 หน้ากระดาษ), แล้วทำการอนุมัติ หรือถามกลับ  (~5-10 นาที)
BEAT 3  คุณ → ส่งให้ Claude Code:       ส่งคำสั่งเปิดงาน (OPEN) → ระบบเช็คความพร้อม (CONFIRM) → คุณสั่งลุยงาน "go"     (~5 นาที)
BEAT 4  Claude Code ทำงาน.       คุณแค่รอตอบคำถามถ้าระบบมีการขอให้ตัดสินใจ (Escalation)          (อาจใช้เวลาหลายชั่วโมง)
BEAT 5  คุณ → ส่งให้ Claude Code:       ส่งคำสั่งปิดงาน (CLOSE) → ระบบอัปเดตเอกสารต่างๆ → ได้ PRE-DRAFT งานชิ้นต่อไปออกมา (~10 นาที)
        ...แล้วคุณก็เอา PRE-DRAFT งานชิ้นต่อไปวนกลับไปเริ่ม BEAT 1 ใหม่อีกครั้ง
```

ระบบเส้นทางด่วน (Fast-path) หรือรอบการสลับระบบ จะข้ามจังหวะ 1-2 ไปเลย โดย PRE-DRAFT จะถูกส่งตรงมาให้คุณอนุมัติได้เลย
ส่วน Session 0-1 จะข้ามจังหวะที่ 1 เพราะยังไม่มีงานอะไรมาก่อนหน้า

เวลาทั้งหมดที่คุณต้องออกแรงลงมือเองในแต่ละรอบ จะอยู่ที่ไม่เกิน ~20–30 นาที นอกเหนือจากนั้นคือหน้าที่ของ Claude Code ในการทำงาน

คุณจะได้แผนการพอร์ตโค้ด DRAFT มาแบบแยกย่อยทีละไฟล์ (ไฟล์เก่า → โค้ดที่ต้องเก็บไว้ → เป้าหมาย → สิ่งที่เปลี่ยนไม่ได้ → วิธีพิสูจน์เทียบเท่า) หน้าตาจะคล้ายๆ ไฟล์ `4B-2-alert-engine.migration-order.md` **สิ่งที่คุณต้องเช็คในจังหวะ 2 คือ:** แต่ละไฟล์ควรมีบรรทัด "สิ่งที่เปลี่ยนไม่ได้" กำกับไว้เสมอ (ให้สงสัยไว้ก่อนถ้ามันเขียนว่า "ไม่มี"), เช็คว่าเทสต์เก่าจะถูกพอร์ตตามมาด้วยและผลลัพธ์จะต้องออกมาเท่าเดิม, และงานรอบนี้ต้อง จบ ที่การเริ่มจับเวลาทดสอบรันโค้ดเบื้องหลัง (shadow-run) — ถ้ามีแผนเกี่ยวกับการสลับระบบติดมาด้วย ให้สั่งกลับไปแก้ว่า: _"Split it — cutover is its own session."_

**ส่วนที่เพิ่มเข้ามาในจังหวะ 3 (คำสั่ง OPEN):** _"re-verify the SOURCE file list and line counts
explicitly."_ การตอบรับกลับที่ดีควรจะมีตารางแจกแจงไฟล์ และระบุจำนวนบรรทัดของโค้ดอัปเดต ณ วันนี้ มาด้วย

**จังหวะที่ 4 — ตัวอย่างคำถามระหว่างทางที่คุณมักจะพบ (เหตุการณ์จริงจาก alert engine):**
"ไฟล์ watches.ts ดึงระบบรูปร่างมาจากโครงสร้างเว็บฝั่งผู้ใช้งาน (frontend) ตามแผนบอกว่าให้ไปดึงข้อมูลแชร์มาจากฝั่ง 4B-1 ยืนยันว่าฝั่ง 4B-1 ทำเสร็จแล้ว — ผมจะดำเนินงานต่อตามแผนนะครับ" (ตรงนี้ไม่ต้องทำอะไร — มันแค่เล่าให้ฟังตามจุดที่กะไว้แล้วว่าจะต้องเจอ)
ส่วนแบบที่ **คุณต้องเข้ามาดูแล** มักจะหน้าตาแบบนี้: "ระบบสั่งเวลา (cron) บน vercel ตั้งค่าให้ทำงานตอนเวลา 02:00 UTC แต่ในคอมเมนต์โค้ดดันเขียนไว้ว่า 03:00 — ตกลงจะให้ยึดอันไหนเป็นหลักครับ?"
คุณก็ให้คำตอบแบบฟันธงไป; แล้วมันจะจดบันทึกสิ่งนี้ลงในข้อเบี่ยงเบน (Deviations)

**จังหวะที่ 5 — การปิดเซสชั่นจะมีคำสั่งให้ตรวจสอบเพิ่ม.** เติมประโยคนี้ต่อท้าย U-C:

> ...and confirm shadow/mirror-run STARTED and the source files are now CC-F frozen — state
> the exact 48h end time.

จากนั้นทันที: ส่ง **U-WAIT** — เพื่อบังคับให้มันบันทึกเวลาจบลงใน CLAUDE.md. ทีนี้คุณก็แค่รอไปอีก 48 ชั่วโมง โดยไม่ต้องยุ่งกับส่วนนี้อีก; คุณสามารถแวบไปรันงานเฟส 5 แทรกระหว่างรอนี้ได้ถ้าต้องการความคืบหน้า

## ตัวอย่าง E — เซสชั่น 4A-3, การสลับระบบ CUTOVER (ทางด่วน fast-path — ไม่ต้องพึ่งพา Advisor)

จากรอบที่พอร์ตโค้ดเสร็จแล้ว (BUILD) จะมี PRE-DRAFT สั้นๆ ไม่เกิน 10 บรรทัดเตรียมพร้อมสำหรับรอบนี้ติดมาด้วยอยู่แล้ว

**จังหวะที่ 2 (ทำข้ามจังหวะ 1-2 เลย) — ตัวคุณ, ทันทีที่อ่าน PRE-DRAFT จบ ให้พิมพ์ว่า:**

> Fast-path approved as written — mark it APPROVED and proceed to CONFIRM at next session
> open.

**จังหวะที่ 3 — ตัวคุณ (สั่งไปที่ Claude Code):** ใช้ U-B สำหรับเซสชั่น 4A-3 และบวกด้วยข้อความนี้:

> First: the shadow-run diff — total requests compared, match rate, EVERY mismatch with
> your explanation.

**สิ่งที่แสดงว่าพร้อมสลับ:** "ผ่านไปแล้ว 48 ชม. <มี timestamp ระบุ— เช็คด้วยว่าเวลาเกินจริง!> ทดลองรันควบคู่ไปทั้งหมด 14,382 รีเควส, เหมือนกันเป๊ะ 14,380 ครั้ง. มีไม่ตรงกัน 2 ครั้ง: สาเหตุเป็นเรื่องการจัดรูปแบบตัวเลขบนหน้าจอ อธิบายได้ด้วย <เหตุผล>, แต่ข้อมูลเชิงลึกคือตรงกัน" **สัญญาณเตือนภัยที่แปลว่า ห้ามสลับระบบเด็ดขาด:** เจอข้อแตกต่างที่ระบบอธิบายมาว่า "น่าจะโอเคนะ" หรือ "อธิบายไม่ได้", เวลา 48 ชั่วโมงยังไม่พ้นไปจริงๆ, "ไม่ได้เทียบความแตกต่างมาให้ แต่รันเทสต์ผ่านหมดนะ"

**ตัวคุณ (จะสั่งประโยคนี้ได้ก็ต่อเมื่อข้อแตกต่างทุกจุดถูกอธิบายอย่างชัดเจนแล้วเท่านั้น):**

> Every mismatch explained — approved. Flip MIGRATE_MONEY_CRONS, monitor 30 minutes, and
> report error rate. Anything degrades: flip back first, tell me second.

**จังหวะที่ 5:** ใช้ U-C. ในตาราง cutover จะเปลี่ยนสถานะบรรทัดนี้ไปเป็น CUT-OVER; จากนั้นคุณก็จะได้ PRE-DRAFT ของเซสชั่นพอร์ตโค้ดตัวถัดไป; แล้วก็วนกลับไปสู่วงจรตัวอย่าง D ใหม่อีกครั้ง

## ตัวอย่าง F — เซสชั่น 4A-10, การสลับระบบเรื่องเงิน (พิธีการสูงสุดขั้นสุดยอด)

เหมือนกับตัวอย่าง E ทุกประการ แต่เพิ่มเติมข้อกำหนดขึ้นมาเพียง 1 ข้อ — ก่อนที่คุณจะอนุมัติการสลับระบบ ต้องถามประโยคนี้ก่อนเสมอ:

> This touches real money. Walk me through it as if I'm auditing you: every write path,
> every idempotency protection, what happens if it runs twice, what happens if it dies
> halfway. Then wait.

**คำตอบที่ควรให้ผ่าน หน้าตาเป็นแบบนี้:** ระบบแจกแจงช่องทางการบันทึกข้อมูลได้ทุกจุด; สำหรับแต่ละจุดจะระบุการป้องกันการตัดเงินซ้ำ ("ระบบของ Stripe ใช้คีย์ป้องกันความซ้ำซ้อน ดึงมาจาก <รหัสไอดีลูกค้า>"), อธิบายได้ว่าถ้ารันคำสั่ง 2 รอบติดจะเกิดอะไร ("รันรอบที่สอง ระบบจะแสดงผลของรอบแรกกลับมา ไม่มีการตัดเงินซ้ำแน่นอน"), และถ้าเกิดตายกลางคันล่ะ ("ระบบ webhook จะพยายามใหม่ + มีตารางเช็คซ้ำเพื่อเล่นใหม่ได้อย่างปลอดภัย").
**ถ้ามาทรงตอบอ้อมแอ้มเดาสุ่ม = ห้ามผ่าน.** ให้คุณตอบกลับไปได้เลยว่า:

> Not convinced on <X>. Demonstrate it in staging: run it twice, show me one charge.

สำหรับการสลับระบบการล็อกอิน (4B-20/21) ก็ต้องปฏิบัติด้วยมาตรฐานเดียวกัน: _"Walk me through what breaks if this goes
wrong and how users get back in. Rollback demonstrated in staging?"_

## ตัวอย่าง G — เมื่อระบบหรือเซสชั่นรวน (ไม่ว่าจะอยู่ในเฟสใดก็ตาม)

นี่คือบทเรียนถอดประสบการณ์ตรงมาจากเหตุการณ์เรื่อง git เมื่อปี 2026-07-12 — และนี่คือวิธีรับมือที่ดีที่สุด:

1. **เมื่อ Claude Code เจออะไรที่ผิดแผนแล้วหยุดทำงาน** (เจอความขัดแย้ง, ติดเรื่องสิทธิการเข้าถึง, หรือเจอบั๊กดักหน้าไม่ให้บรรลุเป้าหมาย) พฤติกรรมที่ดีคือ: มันจะต้องแจ้งคุณก่อนที่จะหาทางฝ่าไฟแดงไปเอง แต่ถ้าหากคุณเห็นว่ามันพยายามจะแหกด่าน ให้บอกมันไปว่า _"Stop. Show me exactly what you're stuck on, what you've
   tried, and what you need from me."_
2. **ระบบจะเสนอทางออก** (มักจะมาเป็นตัวเลือกข้อ 1 2 3) ให้คุณเลือกข้อที่เป็นการแก้ปัญหาจากต้นตอแทนที่จะใช้วิธีเลี่ยงปัญหา, เลือกอันที่สามารถย้อนกลับได้แทนที่จะฝังรากลึก, และเลือกอันที่ให้มันบอกคุณก่อนไม่ใช่แอบแก้เองเงียบๆ (ตัวอย่างจริง: การแก้พิมพ์ผิด 1 ตัวอักษรในไฟล์ tsconfig คือวิธีที่ถูกต้องกว่าการข้ามการตรวจด้วย `--no-verify` เยอะมาก)
3. **ถ้าเรื่องไม่คาดฝันกลายเป็นโปรเจกต์ย่อยซะงั้น,** อย่าไปยัดงานให้มันใหญ่ขึ้นในเซสชั่นปัจจุบัน:
   > That's its own piece of work. Finish what can be finished cleanly, record the rest as
   > a blocker in CLAUDE.md, and PRE-DRAFT an ad-hoc session for it.
4. **ถ้ามองไม่เห็นทางจบเซสชั่นแบบสวยงาม:**
   > Abort per the abort rule: leave the codebase green, write the blocker into CLAUDE.md,
   > summarize for a fresh session. We stop here.
5. **หลังจากนั้น, เสมอ:** ถอดบทเรียนอะไรได้บ้าง? (ถ้าเสียเวลาไปเกิน 30 นาที, ปัญหาเกิดซ้ำ, หรือปัญหานี้หลุดไปถึงระดับขึ้นระบบโปรดักชั่น → ต้องเอาไปบันทึกลงตัว L) อย่าให้เหตุการณ์ที่เคยกินเวลาคุณไปครึ่งบ่ายในอดีต กลับมากินเวลาซ้ำเป็นรอบที่สอง

## 5 นิสัยที่ทำให้กระบวนการทั้งหมดนี้ทำงานได้ลื่นไหล

1. **จงอ่านกระดาษ 1-2 หน้านั้น ก่อนอนุมัติจริงๆ เถอะนะ** เพราะการที่คุณอ่านก่อน คือระบบรักษาความปลอดภัยด่านเดียวที่เป็นด่านตรวจของมนุษย์; ระบบถูกออกแบบมาให้มั่นใจว่า "แค่นั้นก็พอ" แต่ไม่ได้ออกแบบมาให้ "จะอ่านหรือไม่อ่านก็ได้"
2. **ตรวจสอบเรื่องเวลารอคอยด้วยตัวเอง** ระยะเวลา "48 ชั่วโมง" เป็นการเปรียบเทียบเวลาที่คุณทำเองได้สบายๆ — จงทำมันซะ
3. **ฟันธงเจาะจง, และสั่งบันทึกเสมอ** ตอบคำถามที่ถูกถามมาแบบตรงประเด็น; และปิดท้ายทุกครั้งด้วยการสั่งว่า "record it in the Decision Log."
4. **ขอหลักฐาน, ไม่เอาลมปากความมั่นใจ** "แสดงให้ฉันดู" ดีกว่า "คุณแน่ใจเหรอ?" — เสมอ, และตลอดไป
5. **อย่าเร่งเวลารอ, และอย่ายัดงานรวมกันทีละหลายเซสชั่น** ปฏิทินและเวลาคือตัวแปรในการทำงาน 1 เซสชั่น, 1 เป้าหมาย, 1 การอนุมัติ ต่อรอบการทำงานเสมอ
