# RAG Architecture — Production Module Decomposition

## DavinTrade Trading Advisory SaaS

### Source: V3.2 + V3.3 Combined Reference

---

## How to Use This Document

This decomposition maps every component in the RAG architecture to a discrete,
buildable production module. Each module entry includes:

- **Purpose** — what it does
- **Source** — which document section defines it
- **Inputs / Outputs** — data contracts
- **Dependencies** — which modules must exist first
- **Key implementation** — primary code/config artifact

Modules are grouped into 14 functional layers. Build order follows
layer sequence (Layer 1 → Layer 14), but within a layer, modules
are largely independent.

---

## LAYER 1 — Data Collection & MT5 Ingestion

> Collects live OHLCV + indicator data from MT5 terminals every 5 minutes
> and delivers it into PostgreSQL via a validated, queued pipeline.

---

### M01 — MT5 Expert Advisor (MQL5)

**Purpose:** Runs inside MetaTrader 5 terminal. Collects OHLCV + all indicator
values on every new bar (every 5 minutes per symbol/timeframe combination).
Sends structured payload to Flask MT5 Service via HTTP POST.

**Source:** V3.2 §3.2, V3.3 §3.2

**Outputs:**

```
MT5DataPayload {
  symbol, timeframe, timestamp,
  open, high, low, close, volume,
  tema_value, hrma_value, smma_value,
  atr_value, atr_percentile, adx_value, rsi_value,
  trend_direction, volatility_regime, swing_momentum,
  support_levels[], resistance_levels[],
  reversal_probability
}
```

**Dependencies:** None (entry point of pipeline)

**Key implementation:** SimpleDataCollector.mq5 EA deployed on Contabo VPS
(Windows Server 2022). One EA instance per symbol group. Covers
15 symbols × 9 timeframes = 135 active streams.

---

### M02 — Flask MT5 Service (Python)

**Purpose:** Receives MT5DataPayload via HTTP POST. Validates schema,
normalises field types, and enqueues job to BullMQ. Acts as the
VPS-side bridge between MQL5 and the Railway-hosted Node.js backend.

**Source:** V3.2 §3.2, V3.3 §3.2

**Inputs:** MT5DataPayload (HTTP POST from M01)
**Outputs:** BullMQ job payload (Redis queue)

**Dependencies:** M01

**Key implementation:** Flask app on Contabo VPS. Validates required
fields, rejects malformed payloads with 400. On success enqueues to
Redis-backed BullMQ queue and returns 202.

---

### M03 — BullMQ Queue + Workers (NestJS)

**Purpose:** Processes queued MT5 data jobs. Dequeues payloads,
performs final normalisation, and executes PostgreSQL INSERT.
JSONB comments are auto-generated by the DB trigger (M06) —
no application logic required here for comment generation.

**Source:** V3.2 §6.1, V3.3 §3.2

**Inputs:** BullMQ job (from M02)
**Outputs:** PostgreSQL INSERT (to M04)

**Dependencies:** M02, M04, M06

**Key implementation:**

```typescript
// BullMQ worker
@Process("mt5-data")
async handleMT5Data(job: Job<MT5DataPayload>) {
  await db.query(
    `INSERT INTO candles (symbol, timeframe, ...) VALUES ($1,$2,...)`
    // JSONB trigger fires automatically on INSERT
  )
}
```

## LAYER 2 — PostgreSQL Database

> Core persistent storage. Market data, user state, session history,
> token logs. All structured as single-table with composite + GIN indexes.

---

### M04 — PostgreSQL Schema

**Purpose:** Defines all tables. Core table is `candles` (250+ column
schema: OHLCV + all indicator values + JSONB comments column).
Supporting tables: user_profiles, conversation_sessions, token_usage_log.

**Source:** V3.2 §2.1.1, §2.1.4, §2.1.5 | V3.3 §2.1, §2.3, §2.4, §2.5

**Key tables:**

```sql
candles (
  id, symbol, timeframe, timestamp_adjusted,
  open, high, low, close, volume,
  -- 200+ indicator columns (tema, hrma, smma, atr, adx, rsi,
  --   keltner bands, trend_direction, volatility_regime, etc.)
  comments JSONB         -- auto-populated by trigger M06
)

user_profiles (
  user_id, tier, email, profile JSONB
  -- profile JSONB contains: preferred_trading_llm,
  --   has_custom_workflow, workflow_version, trading_style, etc.
)

conversation_sessions (
  session_id, user_id, messages JSONB,
  market_meta JSONB,    -- fetch_timestamp, query_params, bar_range
  summary TEXT, updated_at
)

token_usage_log (
  id, user_id, session_id, date,
  llm_role VARCHAR,     -- "vanna" | "trading"
  model_id VARCHAR,     -- e.g. "claude-sonnet-4-6"
  input_tokens, output_tokens, estimated_cost_usd, created_at
)
```

**Dependencies:** None (foundational)

---

### M05 — Two-Stage Index System

**Purpose:** Enables sub-25ms SQL queries on the candles table through
a two-stage narrowing strategy. Stage 1 composite index filters by
symbol + timeframe + time range (millions → ~12 rows). Stage 2 GIN
index searches JSONB comments on the tiny result set (~1ms).

**Source:** V3.2 §2.1.2 | V3.3 §2.1.2

**Key indexes:**

```sql
-- Stage 1: composite + time (the "Where and When")
CREATE INDEX idx_candles_symbol_tf_time
  ON candles (symbol, timeframe, timestamp_adjusted DESC);

-- Stage 2: GIN on JSONB (the "What Happened")
CREATE INDEX idx_candles_comments
  ON candles USING GIN (comments);
```

**Dependencies:** M04

---

### M06 — JSONB Auto-Comment Trigger

**Purpose:** PostgreSQL BEFORE INSERT trigger that auto-populates the
`comments` JSONB column on every candle row. Evaluates indicator values
and generates structured narrative descriptions. Fires at DB layer —
zero application code required. Every row permanently self-describing.

**Source:** V3.2 §2.1.2 (Trigger section) | V3.3 §6.1

**Key implementation:**

```sql
CREATE OR REPLACE FUNCTION generate_ohlcv_comments()
RETURNS TRIGGER AS $$
BEGIN
  -- TEMA comments (crossover, position relative to price)
  -- HRMA comments (trend strength, direction)
  -- ATR comments (volatility regime, percentile)
  -- ADX comments (trend strength)
  -- Momentum / swing state comments
  -- Support / resistance proximity comments
  NEW.comments = v_comments;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_ohlcv_comments
BEFORE INSERT ON candles
FOR EACH ROW EXECUTE FUNCTION generate_ohlcv_comments();
```

**Dependencies:** M04

---

### M07 — JSONB Comment Logic Update Pipeline

**Purpose:** Manages changes to the JSONB comment generation logic
over time without data loss. When indicator logic changes, a migration
script backfills historical rows. Ensures comment schema remains
consistent with current indicator definitions.

**Source:** V3.2 §2.4.3 (JSONB Extensibility)

**Key pattern:**

```sql
-- Backfill script (run on schema update):
UPDATE candles
SET comments = generate_comments_v2(
  tema_value, hrma_value, atr_value, ...
)
WHERE timestamp_adjusted >= '2026-01-01';
```

**Dependencies:** M04, M06

## LAYER 3 — Vector DB (txtai)

> Semantic knowledge base. Three collections with different ownership.
> Embedding at load/upload time. Cosine similarity at query time.

---

### M08 — Collection (1): trading_knowledge

**Purpose:** Developer-managed VectorDB collection. Contains trading
concepts, methodology, rules, principles, risk management frameworks,
and market structure theory. Read-only to users. Embedded once at
ingestion; updated only by SaaS developer.

**Source:** V3.3 §2.2

**Key setup:**

```python
txtai_app.add([
  {"id": "concept_001", "text": "Support levels are price zones..."},
  # ... all trading knowledge documents
])
txtai_app.index()  # build collection (1) index
```

**Dependencies:** None (static knowledge, loaded at startup)

---

### M09 — Collection (2): indicator_knowledge

**Purpose:** Developer-managed VectorDB collection. Contains indicator
definitions, formulas, interpretation guides, and implication rules
for all indicators in the system (TEMA, HRMA, SMMA, ATR, ADX, RSI,
Keltner Channel bands, etc.). Read-only to users.

**Source:** V3.3 §2.2

**Dependencies:** None (static knowledge, loaded at startup)

---

### M10 — Collection (3): trading_workflow (User Namespace)

**Purpose:** User-managed VectorDB collection. Contains SKILL.md
step-by-step trading analysis procedures. Each user has an isolated
namespace. Falls back to default namespace if no custom workflow
uploaded. Default SKILL.md provided by SaaS developer.

**Source:** V3.3 §2.2, §2.7

**Key namespace pattern:**

```
vectordb://workflow/default/{chunks}    <- SaaS default, all users
vectordb://workflow/{user_id}/{chunks}  <- user custom SKILL.md
```

**Dependencies:** M08, M09 (same txtai instance)

---

### M11 — Semantic Search Engine

**Purpose:** Handles all VectorDB query-time operations. Embeds the
user's natural language query, runs cosine similarity search against
all three collections, returns Top-N chunks per collection ranked by
relevance score. Resolves correct workflow namespace per user.

**Source:** V3.3 §4.3

**Key implementation:**

```typescript
async function searchVectorDB(query: string, userId: string) {
  const namespace = await resolveWorkflowNamespace(userId);
  const [knowledge, indicators, workflow] = await Promise.all([
    txtai.search('trading_knowledge', query, (topN = 5)),
    txtai.search('indicator_knowledge', query, (topN = 3)),
    txtai.search(namespace, query, (topN = 3)),
  ]);
  return { knowledge, indicators, workflow };
}
```

**Dependencies:** M08, M09, M10

## LAYER 4 — VANNA NL2SQL Engine

> Translates natural language queries into SQL without embedding.
> Handles all symbol/timeframe/time synonym resolution.

---

### M12 — VANNA Framework Setup

**Purpose:** Configures and initialises the VANNA NL2SQL framework.
Connects VANNA to the PostgreSQL schema (candles table structure,
column names, sample queries). Provides the foundation for all
NL→SQL translation.

**Source:** V3.3 §4.2 | DUAL-RAG-SYSTEM-ARCHITECTURE.md

**Dependencies:** M04

**Key implementation:** VANNA training on candles schema + sample
question/SQL pairs covering all 15 symbols × 9 timeframes × 10
time horizon patterns.

---

### M13 — Symbol / Timeframe / Time Resolver

**Purpose:** VANNA training data module. Provides comprehensive
synonym mappings for all 15 symbols (including all trader slang and
nicknames), all 9 timeframes (including multi-TF pairs for
low/mid/high analysis), and 10 natural language time horizon
phrases mapped to LIMIT N patterns.

**Source:** V3.3 §6.4 (Working Memory Configuration — VANNA mappings)

**Key mappings (excerpt):**

```
Symbol:     "gold / xau / bullion / yellow metal" -> XAUUSD
            "guppy / geppy / the beast"           -> GBPJPY

Timeframe:  "low timeframe"    -> M5 + M15
            "high timeframe"   -> H1 + H4
            "long term"        -> H4 + H12

Time:       "recently / now"   -> LIMIT 12 (default TF)
            "last few days"    -> 12 H4 bars
            "this week"        -> 12 H12 bars
            (nothing given)    -> LIMIT 12 of resolved TF
```

**Dependencies:** M12

---

### M14 — SQL Query Generator

**Purpose:** Core NL→SQL translation runtime. Receives natural language
query from the Clarification Gate (M16), applies resolved parameters,
generates executable SQL including JSONB comments column in SELECT.
Returns SQL string to Query Router (M20).

**Source:** V3.3 §4.2

**Generated SQL pattern:**

```sql
SELECT timestamp_adjusted, symbol, timeframe,
       open, high, low, close, volume,
       tema, hrma, smma, atr_value, adx_value, rsi_value,
       comments       -- JSONB always included
FROM candles
WHERE symbol = 'XAUUSD' AND timeframe = 'H1'
ORDER BY timestamp_adjusted DESC LIMIT 12;
```

**Dependencies:** M12, M13

---

### M15 — VANNA LLM Service

**Purpose:** Admin-configured LLM backend for VANNA NL→SQL translation.
Low-to-mid competency model sufficient for deterministic structured
task. Not exposed to users. Admin selects model via environment config.
Handles ~500–1,500 tokens per call.

**Source:** V3.3 §2.8.2

**Supported backends (VANNA 2.0):**

```
AnthropicLlmService  -> claude-haiku-4-5      (recommended)
OpenAILlmService     -> gpt-4o-mini / gpt-4.1-nano
GeminiLlmService     -> gemini-2.0-flash-lite  (cheapest)
MockLlmService       -> dev/test only
```

**Dependencies:** M12, M14

## LAYER 5 — Query Orchestration

> Receives raw user query. Routes through clarification, tier access
> check, and fallback chain before dispatching to engines.

---

### M16 — Clarification Gate

**Purpose:** First checkpoint for every incoming query. Checks three
dimensions: (1) symbol resolvable?, (2) timeframe resolvable?,
(3) time horizon — defaults silently to LIMIT 12, never asks.
Routes to clarification loop if symbol or TF missing.

**Source:** V3.3 §3.1, §5.1

**Key logic:**

```
symbol resolved + TF resolved  -> proceed to engines
symbol resolved, TF missing    -> clarification loop (ask TF only)
symbol missing, TF resolved    -> clarification loop (ask symbol only)
both missing                   -> clarification loop (ask both)
time_ref missing               -> DEFAULT LIMIT 12, no ask
```

**Dependencies:** M13, M17

---

### M17 — 5-Stage Clarification Loop

**Purpose:** Handles incomplete queries through a structured 5-stage
loop: (1) parameter extraction, (2) confidence check, (3) targeted
question to user, (4) merge response + retry, (5) intelligent
defaults after 2 failed rounds (XAUUSD, H1, last 12 bars).

**Source:** V3.3 §5.1

**Stage 5 defaults:**

```
symbol    -> XAUUSD
timeframe -> H1
time_ref  -> last 12 bars
Response: "Proceeding with XAUUSD H1 last 12 bars."
```

**Dependencies:** M16

---

### M18 — Fallback Priority Chain

**Purpose:** 11-item ordered fallback handler covering every failure
mode after the clarification gate. Handles missing TF, no symbol,
tier violations, unknown symbols, unsupported timeframes, stale data,
pure conceptual queries, and clarification exhaustion.

**Source:** V3.3 §5.2

**Chain summary:**

```
Item 1:  Primary flow — full happy path
Item 2:  Missing TF -> clarification
Item 3:  No symbol -> major markets overview
Item 4:  PRO symbol + FREE user -> upsell
Item 5:  PRO timeframe + FREE user -> upsell
Item 6:  Both violations -> combined upsell
Item 7:  Unknown symbol -> spelling check / out-of-scope
Item 8:  Unsupported TF -> nearest match suggestion
Item 9:  Stale data -> last available + disclaimer
Item 10: Pure conceptual -> VectorDB only
Item 11: Clarification exhausted -> apply defaults
```

**Dependencies:** M16, M17, M19

---

### M19 — Tier Access Controller

**Purpose:** Validates that the resolved symbol and timeframe are
accessible under the user's current plan tier. Blocks access and
returns structured upsell message with available alternatives and
upgrade link for all tier violations.

**Source:** V3.3 §5.2 (Items 4–6)

**Tier definitions:**

```
FREE:  5 symbols (XAUUSD, BTCUSD, EURUSD, USDJPY, US30)
       3 timeframes (H1, H4, D1)
PRO:   15 symbols (all FREE + 10 more)
       9 timeframes (M5, M15, M30, H1, H2, H4, H8, H12, D1)
```

**Dependencies:** M04 (user_profiles tier field)

---

### M20 — Query Router (Parallel Dispatcher)

**Purpose:** After all checks pass, dispatches three parallel retrieval
operations simultaneously using Promise.all: SQL engine (VANNA +
PostgreSQL), Semantic engine (txtai VectorDB), and User Profile loader.
Total latency = max(all three), not sum.

**Source:** V3.3 §6.2, §4.1

**Key implementation:**

```typescript
const [sqlResult, vectorResult, userProfile] = await Promise.all([
  executeSQL(vannaSql), // 10-25ms
  searchVectorDB(query, userId), // 80-150ms
  getUserProfile(userId), // 5ms
]);
// Total: ~150ms (not 180ms sequential)
```

**Dependencies:** M14, M11, M04, M34–M37 (rate limit checks precede this)

## LAYER 6 — Context Assembly

> Assembles the complete context package delivered to the Trading LLM
> every turn. Handles conversation history, data freshness, and
> system prompt construction.

---

### M21 — Parallel Retrieval Engine

**Purpose:** Executes the three-engine parallel fetch (M20) and
assembles raw results into a structured context object ready for
prompt injection. Validates each result (handles empty DataFrame,
empty VectorDB results gracefully).

**Source:** V3.3 §6.2

**Output structure:**

```typescript
{
  sqlDataFrame:    OHLCVRow[],      // numeric + JSONB comments
  knowledgeChunks: KnowledgeChunk[], // VectorDB top-N
  userProfile:     UserProfileJSONB
}
```

**Dependencies:** M20

---

### M22 — Data Freshness Layer

**Purpose:** Manages the core problem of stale conversation context
in a live market system. Every turn always re-fetches market data
fresh (never caches DataFrame). Calculates bar delta since last
fetch. Generates Short Remark when new bars have printed.
Classifies content as TYPE A (static, keep) or TYPE B (market data,
never store in history).

**Source:** V3.3 §6.5.1–§6.5.4

**Master rule:**

```
Show Short Remark = (market_data_fetched == true)
                  AND (new_bars_printed >= 1)
                  AND (session.turn > 1)
```

**Dependencies:** M21, M23

---

### M23 — Conversation History Manager

**Purpose:** Manages per-session conversation history with token
budget enforcement. Stores only TYPE A content (user intent,
clarifications, conclusions — never raw OHLCV or indicator values).
Prunes/summarises older turns when token budget (10,000 tokens) is
exceeded. Saves interaction after each turn.

**Source:** V3.3 §6.3, §6.5.2–§6.5.3

**TYPE A vs TYPE B:**

```
TYPE A (store in history):
  user intent, symbol/TF preferences, trading style
  AI conclusions in narrative form
  clarification exchanges

TYPE B (NEVER store — re-fetch every turn):
  raw OHLCV values, indicator numbers
  JSONB narratives from prior bars
  specific price levels or bar timestamps
```

**Dependencies:** M04 (conversation_sessions table)

---

### M24 — User Profile Loader

**Purpose:** Fetches the user's PostgreSQL JSONB profile on every
query. Provides trading style, risk tolerance, symbol preferences,
active Trading LLM model, workflow configuration, and tier to the
context assembly pipeline.

**Source:** V3.3 §2.3

**Profile JSONB key fields:**

```json
{
  "tier": "PRO",
  "trading_style": "swing",
  "risk_tolerance": "medium",
  "preferred_trading_llm": "claude-sonnet-4-6",
  "has_custom_workflow": true,
  "workflow_version": "v2"
}
```

**Dependencies:** M04

---

### M25 — Working Memory / System Prompt Builder

**Purpose:** Constructs the system prompt injected into every Trading
LLM call. Includes: trading analyst role definition, working memory
config (max tokens per query type), VANNA symbol/TF/time mappings,
bar-awareness injection (data fetched at, symbol/TF, bar range,
new bars since last turn), and market data staleness instruction.

**Source:** V3.3 §6.4, §6.5.6

**Context budget allocation:**

```
200k total context window:
  System prompt + working memory  1-2k
  Conversation history (pruned)   10k
  User profile JSONB              1k
  VectorDB knowledge chunks       20-30k
  SQL DataFrame (numeric+JSONB)   50-100k  <- largest
  Current user query              0.5k
  Output budget                   38-118k
```

**Dependencies:** M22, M23, M24

## LAYER 7 — Trading LLM Layer

> Calls the user-selected (PRO) or fixed (FREE) Trading LLM with the
> fully assembled context. Handles response streaming and post-
> processing.

---

### M26 — Trading LLM Router

**Purpose:** Resolves which LLM model to use for the current user.
FREE tier: always returns gemini-2.5-flash regardless of profile
settings. PRO tier: returns user's preferred_trading_llm from profile,
defaulting to claude-sonnet-4-6. No override possible for FREE tier.

**Source:** V3.3 §2.8.3

**Key implementation:**

```typescript
function resolveTradingLLM(user: User): string {
  if (user.tier === 'FREE') {
    return 'gemini/gemini-2.5-flash'; // fixed, no override
  }
  return user.profile.preferred_trading_llm ?? 'claude-sonnet-4-6';
}
```

**Dependencies:** M24

---

### M27 — LiteLLM Integration (txtai)

**Purpose:** Provides the unified multi-provider LLM interface for
the Trading RAG system via txtai's LiteLLM layer. Supports 100+
providers through a single interface. Introductory phase restricted
to Anthropic, OpenAI, and Google providers only.

**Source:** V3.3 §2.8.3

**Introductory phase models:**

```
FREE:  gemini/gemini-2.5-flash       (fixed)
PRO:   claude-sonnet-4-6             (default)
       claude-opus-4
       gpt-4o
       gpt-4.1
       gemini/gemini-2.5-pro
```

**Dependencies:** M26

---

### M28 — Short Remark Generator

**Purpose:** Generates the data refresh notice prepended to trading
analysis responses when new bars have printed since the last query.
Neutral, factual, 3–5 lines in blockquote format. Prevents user
confusion between stale and current market analysis.

**Source:** V3.3 §6.5.5

**Output template:**

```
> Data refreshed. Previous analysis was based on bars from
> [from_prev] to [to_prev].
> This analysis is based on the latest bars from
> [from_curr] to [to_curr]
> ([N] new [TF] bars have printed since the last analysis).
```

**Dependencies:** M22

---

### M29 — Response Handler

**Purpose:** Processes Trading LLM output. Extracts text from
content blocks, prepends Short Remark if applicable, formats
markdown → HTML for UI rendering, streams or sends complete
response to frontend, stores TYPE A content to conversation
history, and logs token usage to token_usage_log.

**Source:** V3.2 §4.5 | V3.3 §6.5.7

**Post-response actions:**

```
1. Prepend Short Remark (if applicable)
2. Format response (markdown -> HTML)
3. Stream or send complete to frontend
4. Store TYPE A content to conversation_sessions
5. Log to token_usage_log (llm_role="trading", model_id)
6. Update market_meta in session
7. Invalidate monthly cost Redis cache (M36)
```

**Dependencies:** M22, M23, M27, M28, M40

## LAYER 8 — User Workflow Upload System

> Allows users to upload custom SKILL.md trading workflow files.
> FREE tier: 1 version, 50KB max. PRO tier: unlimited versions, 500KB.

---

### M30 — Workflow Upload API

**Purpose:** REST endpoint accepting user SKILL.md uploads. Enforces
tier-based validation gate: file type (.md only), file size (50KB
FREE / 500KB PRO), content structure check, version limit check
(FREE: warn on replace, PRO: always allow). Returns validation
errors or upgrade prompts on failure.

**Source:** V3.3 §2.7.3

**Validation gate:**

```
1. File type:    .md only
2. File size:    FREE <= 50KB, PRO <= 500KB
3. Content:      must contain workflow steps
4. Version:      FREE: warn if replacing, PRO: auto-increment
```

**Dependencies:** M04, M31, M55

---

### M31 — Workflow Embedding Pipeline

**Purpose:** On successful upload validation, chunks the SKILL.md
file, embeds all chunks via txtai, and indexes them into the user's
namespace in Collection (3). Rebuilds the user's namespace index.
Triggered synchronously on upload (or async via BullMQ for large files).

**Source:** V3.3 §2.7.3

**Key implementation:**

```python
txtai.add(
  documents=chunk_markdown(skill_md_content),
  namespace=f"workflow/{user_id}"
)
txtai.index()  # rebuild this user's namespace index
```

**Dependencies:** M10, M30

---

### M32 — Workflow Namespace Router

**Purpose:** Resolves which VectorDB workflow namespace to query for
a given user at search time. Returns user namespace if custom workflow
exists (has_custom_workflow == true), else returns default namespace.
Consistent logic for both FREE and PRO tiers.

**Source:** V3.3 §2.7.5, §4.3

**Dependencies:** M10, M24

---

### M33 — Workflow Version Manager

**Purpose:** Manages filesystem storage and JSONB metadata for user
workflow versions. FREE tier: always overwrites skill_v1.md (no
history). PRO tier: creates skill_vN.md, maintains symlink
active_skill.md, stores version history array in user_profiles JSONB.
Supports rollback for PRO tier.

**Source:** V3.3 §2.7.4

**Filesystem layout:**

```
/user_workflows/{user_id}/
  skill_v1.md
  skill_v2.md              (PRO only)
  active_skill.md -> skill_v2.md
```

**Dependencies:** M04, M30

## LAYER 9 — Rate Limiting & Plan Enforcement

> Three-layer enforcement protecting SaaS profitability and preventing
> abuse. Checked in order on every incoming query before any LLM call.

---

### M34 — Per-Minute Rate Limiter

**Purpose:** Layer 1 enforcement. Rolling 60-second window counter
per user stored in Redis. Blocks burst abuse and protects inference
latency. Returns HTTP 429 with retry-after header on violation.

**Source:** V3.3 §2.9.1, §2.9.2, §2.9.3

**Limits:** FREE: 3/min | PRO: 10/min
**Redis key:** `ratelimit:minute:{user_id}` TTL 60s

**Dependencies:** Redis

---

### M35 — Daily Query Cap

**Purpose:** Layer 2 enforcement. Calendar-day query counter per user
in Redis. Resets at 00:00 UTC via TTL expiry. Blocks spam and
controls daily operating cost. Returns block message with day-reset
timestamp and upgrade prompt for FREE users.

**Source:** V3.3 §2.9.1, §2.9.2, §2.9.3

**Limits:** FREE: 20/day | PRO: 40/day
**Redis key:** `ratelimit:daily:{user_id}:{YYYY-MM-DD}` TTL 86400s

**Dependencies:** Redis

---

### M36 — Monthly Query Cap

**Purpose:** Layer 3 enforcement. PRO tier only. Per-model monthly
query cap enforced via PostgreSQL token_usage_log COUNT, cached in
Redis for 5 minutes to avoid per-query DB hit. Different caps per
model (claude-opus-4: 30/mo, claude-sonnet-4-6: 200/mo, etc.).

**Source:** V3.3 §2.9.1, §2.9.3, §2.9.4

**Per-model caps (PRO):**

```
claude-sonnet-4-6    200/month
gpt-4o               200/month
gemini-2.5-pro       250/month
gpt-4.1              120/month
claude-opus-4        30/month
```

**Redis key:** `ratelimit:monthly_cache:{user_id}` TTL 300s

**Dependencies:** M04, Redis

---

### M37 — Concurrent Session Limiter

**Purpose:** Layer 4 enforcement. Prevents duplicate query submission
and limits in-flight queries per user. Redis counter incremented on
query start, decremented on response finish. Returns "Query already
in progress" if limit exceeded.

**Source:** V3.3 §2.9.3

**Limits:** FREE: 1 concurrent | PRO: 3 concurrent
**Redis key:** `ratelimit:concurrent:{user_id}` TTL 30s

**Dependencies:** Redis

### M38 — Plan Limits Configuration

**Purpose:** Single source of truth for all plan limit values.
`PLAN_LIMITS` TypeScript config object consumed by all rate limit
modules (M34–M37). Changing limits requires updating only this one
object. Also defines fixed Trading LLM model for FREE tier.

**Source:** V3.3 §2.9.4

**Key structure:**

```typescript
const PLAN_LIMITS = {
  FREE: { perMinute:3, perDay:20, concurrent:1,
          tradingLLM:"gemini/gemini-2.5-flash" },

          perMonthByModel: { "claude-opus-4":30, ... } }

```

**Dependencies:** None (pure config)

### M39 — Tier Upsell Message Handler

## LAYER 10 — LLM Cost Surveillance

> Monitors total LLM API cost (VANNA + Trading combined) in real time.
> Five SQL surveillance views, three-tier alert system, and automated
> actions for critical cost events.

---

### M40 — token_usage_log Writer

**Purpose:** Writes a row to token_usage_log after every LLM call
(both VANNA and Trading). Records llm_role, model_id, input/output
token counts, and estimated USD cost. The single source of truth for
all cost surveillance downstream.

**Source:** V3.3 §2.5, §2.8.4

**Write points:**

```
After VANNA LLM call:    llm_role="vanna",   model_id=admin_model
After Trading LLM call:  llm_role="trading", model_id=user_model
```

**Dependencies:** M04, M15, M27

---

### M41 — Cost Surveillance Worker (BullMQ)

**Purpose:** BullMQ scheduled job running every 5 minutes. Executes
all 5 surveillance SQL views, evaluates alert thresholds, stores
all triggered alerts to dashboard, sends notifications for HARD
alerts, and executes automated actions for CRITICAL alerts.
Reuses existing BullMQ infrastructure from MT5 pipeline.

**Source:** V3.3 §2.9.6 (Alert Delivery Implementation)

**Dependencies:** M40, M42–M46, M47–M49

---

### M42 — SQL View 1: Platform P&L Snapshot

**Purpose:** Real-time platform-wide LLM cost vs revenue. Aggregates
VANNA + Trading costs together. Calculates llm_margin_usd and
llm_cost_pct_of_revenue for the current calendar month.

**Source:** V3.3 §2.9.6 (SQL View 1)

**Key metrics:** total_llm_cost_usd, vanna_cost_usd, trading_cost_usd,
llm_margin_usd, llm_cost_pct_of_revenue

**Dependencies:** M04, M40

---

### M43 — SQL View 2: Per-User Total Cost

**Purpose:** Full per-user cost picture combining VANNA and Trading
LLM costs. Shows net_margin_usd per user (revenue contribution minus
total LLM cost). Enables identification of revenue-negative users.

**Source:** V3.3 §2.9.6 (SQL View 2)

**Key metrics:** total_cost_usd (both roles), vanna_cost_usd,
trading_cost_usd, net_margin_usd, trading_model

**Dependencies:** M04, M40

---

### M44 — SQL View 3: MTD Cost Projection

**Purpose:** Projects full-month LLM cost from current month-to-date
daily burn rate. Enables early warning before month-end if spend is
on a bad trajectory. Shows days elapsed vs days in month.

**Source:** V3.3 §2.9.6 (SQL View 3)

**Key metrics:** mtd_total_cost_usd, avg_daily_cost_usd,
projected_month_cost_usd, days_elapsed / days_in_month

**Dependencies:** M04, M40

---

### M45 — SQL View 4: Cost Velocity

**Purpose:** Day-over-day cost trend and acceleration analysis.
Detects whether cost is growing faster than user growth (a
profitability risk signal). Includes 7-day rolling average and
day-over-day percentage change.

**Source:** V3.3 §2.9.6 (SQL View 4)

**Key metrics:** daily_total_cost, rolling_7d_avg_cost,
dod_cost_change_pct, cost_per_active_user

**Dependencies:** M04, M40

---

### M46 — SQL View 5: VANNA Efficiency Monitor

**Purpose:** Tracks VANNA LLM cost-per-query over time. Detects
prompt bloat (input token creep) and model degradation. 7-day
rolling average per model enables trending alerts before costs
become significant.

**Source:** V3.3 §2.9.6 (SQL View 5)

**Key metrics:** avg_cost_per_query, avg_input_tokens,
rolling_7d_avg_per_query (by model)

**Dependencies:** M04, M40

---

### M47 — Alert Engine

**Purpose:** Evaluates all alert thresholds against surveillance view
outputs. Three severity levels: SOFT (dashboard only), HARD (email +
Slack), CRITICAL (email + Slack + auto-action). Covers per-user alerts,
platform-wide alerts, VANNA-specific alerts, and rate limit abuse alerts.

**Source:** V3.3 §2.9.6 (Alert Thresholds)

**Critical alert conditions (auto-action triggers):**

```
Any user LLM cost > revenue/user  -> block_user
LLM cost % revenue > 50%          -> freeze_opus
PRO user total LLM > $10/day      -> throttle_user
```

**Dependencies:** M42–M46

---

### M48 — Alert Delivery Service

**Purpose:** Delivers alert notifications through appropriate channels
based on severity. SOFT: store to admin dashboard only. HARD: email

- Slack. CRITICAL: email + Slack + trigger M49. All alerts persisted
  to alerts table for dashboard history.

**Source:** V3.3 §2.9.6 (Alert Delivery Implementation)

**Dependencies:** M47

---

### M49 — Auto-Action Executor

**Purpose:** Executes automated protective actions for CRITICAL alerts
without requiring admin intervention. Three action types: throttle_user
(Redis rate override to 1/min), freeze_opus (Redis flag blocking
claude-opus-4 platform-wide for 24h), block_user (Redis flag blocking
all LLM calls for user pending admin review).

**Source:** V3.3 §2.9.6 (executeAutoAction)

**Redis keys written:**

```
override:throttle:{user_id}         EX 3600
override:freeze_model:claude-opus-4 EX 86400
override:block:{user_id}            EX 86400
```

**Dependencies:** M47, Redis
