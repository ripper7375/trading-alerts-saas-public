## 1. Verdict

**The plan works well as a map. It is not ready to be APPROVED as an order.**

What the plan does well:

- It covers all 17 checks and maps every one to a section.
- The tiering idea is sound: make small, isolated fixes first, and leave cross-cutting refactors (config schemas, `APP_GUARD` inversion, health split) until routes and runbooks stop moving.
- Most findings are real. Of the 28 claims I checked line by line (§3), 12 are confirmed, 11 are partly right and 5 are wrong. The good findings include the deletion token in logs, the gateway with no `trust proxy` and no shutdown hooks, the unbounded `fetch` calls, the Redis retry that gives up permanently, and the missing outbox recovery.

What blocks approval:

1. **The P0 is under-scoped.** The fixed test accounts are an open ADMIN entry point in production today, and the production login page shows the password on screen (§2). The plan files this as one Tier 1 item, touches only `operation-service`, and has no escalation flag.
2. **The sequencing premise is wrong.** Tier 2 is framed as a gate "before `money-service` Slice 4 write cutover (Session `4A-10`)". In fact, Slice 4 (all 4 write-API groups), the Slice 1 crons and the Stripe webhook are **already cut over** (`docs/migration-orders/migration-cutover-table.md`, Slice 1, 2 and 4 rows). So Tier 2 is not a gate. It is a list of live money-path defects, and its order should follow blast radius (§4.1).
3. **Several claims do not match the live code.** Two describe code that does not exist: §4.3.2's two-write loop and §5.15.2's `REDACT_PATHS`. One asks for a transaction that is already there (§4.3.1). One overstates severity (§4.2: the mock returns `PENDING`, not `PAID`). Executing these literally would spend sessions on code that is already correct.
4. **Checks 2, 3, 14 and 17 are written for Kubernetes and not translated to Railway.** Railway has no `preStop` hook. Its healthcheck gates a deploy; it is not a continuous probe. The time between SIGTERM and SIGKILL is a Railway setting (§4.2).
5. **The drain design conflicts with how Nest 11 shuts down.** Nest runs every `onModuleDestroy` **before** `beforeApplicationShutdown` and before the HTTP server closes. All three `PrismaService` classes disconnect in `onModuleDestroy`. So the §5.3 drain cannot protect database work as written. Also, `return503OnClosing` does not exist in 11.2.3 (§4.3).
6. **No CI runs these services.** None of the 14 workflows in `.github/workflows/` mentions `operation-service`, `money-service` or `railway-gateway`, yet the plan schedules CI last (§5.9.4, Tier 3). CI is what makes every other tier safe, so it should come first (§4.5).
7. **The plan does not use the order shape the repo requires.** It has no `Decisions taken` section. It has no `⚠ NEEDS EXPLICIT SIGN-OFF` marks on the auth, CORS and secrets items in Tier 1 and Tier 3; only Tier 2 has an escalation note. Its tiers are multi-session batches, not one verifiable unit each (non-negotiables 1, 2, 5 and 7; §4.7).

**Recommendation:** Davin acts on §2 now, separately from this plan. The Advisor then revises the plan along §6, and it comes back as numbered orders.

## 2. P0: act now, outside the tier model (⚠ auth, needs Davin)

### 2.1 What the code does today

The same `FIXED_TEST_ACCOUNTS` map exists in two live login paths:

- `operation-service/src/auth/auth.service.ts:158-292` is the bridge path. It is live in production since Session 4B-21.
- `lib/auth/auth-options.ts:170-384` is the monolith `CredentialsProvider`. It is **still registered**. The header comment at L147 says it "was retired" in 4B-21, but that comment is out of date. NextAuth's credentials callback is therefore reachable whatever `NEXT_PUBLIC_AUTH_BRIDGE_ENABLED` says.

In both paths:

1. `admin@tradingalerts.com` accepts `ChangeMe123!` and `AdminPassword123!` even when `ADMIN_PASSWORD` is set. The environment value is only **added** to the list.
2. The fixed-account branch returns **before** the `twoFactorEnabled` check (`auth.service.ts:311`). These accounts skip 2FA.
3. The `upsert` writes `role`, `tier`, `isActive: true` and `emailVerified`, and overwrites `password` with a hash of the hard-coded password. This reactivates a disabled account and resets any password an admin chose. DECISION-LOG **F80** (OPEN) already records the `isAffiliate` side of this same overwrite.
4. If the upsert fails, `operation-service` issues a session for an **in-memory** user (`id: test-user-…`) with the map's role (`auth.service.ts:252-291`).
5. `components/auth/login-form.tsx:266-348` renders a **"Quick Test Credentials"** panel with click-to-fill buttons, with no environment gate. One button is "Admin (Fixed)", which fills `admin@tradingalerts.com` / `ChangeMe123!`. `app/(auth)/login/page.tsx` renders this form.

**Consequence (from reading the code; not tried against production):** anyone who opens the production login page can sign in with the ADMIN role, and 2FA does not apply.

### 2.2 Why the plan's §3.1 fix is not enough

- It changes `operation-service` only. The monolith is left "if Davin approves", and the login-page panel is not mentioned.
- Its gate is inconsistent. The code snippet uses an allow-list (`test` / `development` / flag). Review question 1 instead writes `NODE_ENV !== 'production'`, which **opens** the gate when `NODE_ENV` is unset. The repo already has the right pattern in `app/api/test/seed/route.ts:15,67`: an allow-list, with an unset `NODE_ENV` treated as `production`.
- `ALLOW_FIXED_TEST_ACCOUNTS=true` would re-open everything, in production too, by setting one variable. That flag must never take effect when `NODE_ENV` (or, for the monolith, `VERCEL_ENV`) is `production`.
- **It would break Davin's production checks.** `waiting-on.md` (the sign-out fix entry) records Davin verifying production with the Free Test User account, and asks for a pass across the other fixed accounts. If the accounts are gated without a replacement, Davin has no way to click through production. This answers the plan's review question 1.

### 2.3 Recommended actions

1. **⚠ Hot-fix decision (Davin), before any plan work.** Minimum change, made in both codebases in one change:
   - Remove the `admin@tradingalerts.com` and `admin-test@…` entries.
   - Hide the "Quick Test Credentials" panel unless the environment is development.
2. **⚠ Replacement for production checks.** Create real, seeded test users in production whose passwords live only in a password manager. They go through the normal bcrypt path, so 2FA and `isActive` apply. Keep the hard-coded map for `development` and `test` only, using the allow-list.
3. **⚠ Incident check (Davin, read-only on production).** For the six emails, look at the `User` rows (role, `isActive`, `updatedAt`), at refresh tokens, sessions and login history, and at any admin action they took. Note that rotating `ADMIN_PASSWORD` does nothing while the hard-coded strings stay in the list.
4. **⚠ Vercel preview deploys.** Previews run with `NODE_ENV=production` (`auth-options.ts:37-42`). If previews should keep the test accounts, gate the monolith on `VERCEL_ENV !== 'production'` rather than on `NODE_ENV`.
5. **⚠ The monolith `CredentialsProvider`.** Either remove it, as 4B-21 intended, or correct its out-of-date comment and record why it stays.
6. **Tests.** Add a unit test in each codebase that the map cannot be reached when `NODE_ENV=production`, and a render test that the panel is absent in production.

The account-deletion token in the logs (plan §3.2) is the other item serious enough to sit next to this one. It stays in Tier 1 (§3).

## 4. Cross-cutting issues

### 4.1 Tier 2's premise is wrong: the money paths are already live

`migration-cutover-table.md` shows these as cut over:

- Slice 1 (8 crons)
- Slice 2 (dLocal webhooks)
- Slice 2W (Wise)
- Slice 3 (reads)
- Slice 4 (Stripe checkout, subscription and cancel, invoices, dLocal create, code distribution, batch execute, plus the Stripe webhook)
- Slice 5 (tier-update events)

No cutover is left to gate. Re-frame Tier 2 as **"live money-path defects"**, escalate every item (non-negotiable 5), and order them by blast radius (§6). Waiting for "scaling beyond 1 replica" is still right for the cron locks, and only for those.

### 4.2 Railway is not Kubernetes

The checklist's examples assume Kubernetes. The plan copies them without translating to the platform this repo runs on. The Railway behaviour below should be **re-confirmed against current Railway docs** before the plan relies on it:

- **Healthcheck.** Railway calls `healthcheckPath` while deploying, to decide when the new deployment can take traffic. It does not keep probing a running deployment. So:
  - The liveness/readiness split (Check 17) has no continuous restart loop to protect.
  - A deep check (database and Redis) is what you want **as the deploy gate**.
  - `restartPolicyType: ON_FAILURE` restarts only when the process exits.
- **Draining.** There is no `preStop` hook. The time between SIGTERM and SIGKILL is a Railway deploy setting (draining seconds, plus an optional overlap). An in-app 5-second drain (§5.3) is cut off by SIGKILL if Railway's draining time is shorter. Configure both, and test with a real redeploy that the shutdown hooks' log lines appear.
- **Which config file is read.** Railway's config-as-code has `build` and `deploy` sections. I found no sign that the `[[services]]` blocks in `railway.toml` are read. The repo's own history agrees:
  - 4B-7 found that `operation-service` deployed with the **root** `railway.json` until it got its own.
  - Lesson L44 says "every sub-service needs its own `railway.json`".
  - 4B-3 found the worker service "initially ran the wrong process".

  `money-service` and `railway-gateway` have no `railway.json`, so their real start command, healthcheck path and replica count live in the dashboard. Any change to start commands (§5.2) or health paths (§5.16) needs a **runtime inventory first** (§6, Tier 0).

- **Deploy method is mixed.** The gateway builds from GitHub (Root Directory, Watch Paths unset). `operation-service` has been deployed with `railway up --path-as-root`. This decides whether `.railwayignore` matters (row 3.2).

### 4.3 Nest 11 shutdown order breaks the drain design

From the published `@nestjs/core@11.2.3`, `NestApplicationContext.listenToShutdownSignals()` runs these steps in order:

1. `onModuleDestroy` for every module
2. `beforeApplicationShutdown`
3. `dispose()`, which closes the HTTP server
4. `onApplicationShutdown`
5. `process.kill(pid, signal)`, or `process.exit(0)` when `useProcessExit: true`

Four consequences:

- All three `PrismaService` classes call `$disconnect()` in `onModuleDestroy`. That runs **while the HTTP server is still accepting requests**. With the `PrismaPg` adapter, the pool is gone, so requests still in flight fail. Move `$disconnect()` to `onApplicationShutdown`. Do this at the same time as §3.4 for the gateway, and as a small fix for the other two services, which already have hooks enabled.
- A drain placed in `beforeApplicationShutdown` (§5.3) runs **after** Prisma has disconnected. To drain, put the wait in an `onModuleDestroy` that runs before Prisma's, or rely on the fix above.
- `otel.ts:63-67` adds its own `SIGTERM` listener. Nest removes only its own listener before re-raising the signal. The OTel listener then catches it, so the process exits only if nothing else keeps it alive; otherwise it waits for SIGKILL. Use `useProcessExit: true`, which 11.2.3 **does** support, and call `sdk.shutdown()` from `onApplicationShutdown`.
- If the start command becomes a bare `node …` and Node ends up as PID 1, a re-raised `SIGTERM` is ignored. `useProcessExit: true` avoids this too. Change §5.2.1 and the hook option together, never one without the other.

`return503OnClosing` (checklist Check 3) is a Nest 12 option. On 11.2.3 it needs either the Nest 12 upgrade or a custom middleware.

### 4.4 Version facts the plan should state

- `@nestjs/core`: `latest` is **12.1.3**. The 11.x line is tagged `legacy` at **11.2.7**. `operation-service` and `money-service` pin exactly 11.2.3; the gateway uses `^11.2.3`.
  - Recommend: a patch bump to 11.2.7 in Tier 1 or 3.
  - Recommend: a separate ⚠ decision on moving to Nest 12, which would also bring `return503OnClosing`.
- **Node 20 reached end-of-life on 2026-04-30.** `engines.node` is `>=20.0.0` in all three services, and several CI workflows pin Node 20 (for example `api-tests.yml`; `environment-gotchas.md` also mentions "CI's Node 20").
  - Pin an active LTS (22 or 24) in `engines` and in the Nixpacks settings.
  - Confirm in a Railway build log which Node major actually runs today.

### 4.5 CI must come first, not last

`money-service` and `operation-service` alone have 650 and 401 tests (baselines in `.claude/protocols/verification-checklist.md`), and none of the three services' tests runs in CI. Every tier in this plan changes these services. Without CI, each change depends on someone remembering to run `npm test` in three folders with three lockfiles.

Add a workflow per service (or a matrix). Each runs `npm ci`, `npx tsc --noEmit` and `npm test`; the gateway also runs `npm run test:e2e` and `npm run check:sensor-kit`. Use Node 22 or 24 (§4.4). This is **Tier 0**.

### 4.6 Stripe dual delivery: dedupe must live in the database both processes share

4A-13 Deviation 8 kept the monolith Stripe endpoint registered as a safety net, and nothing records that it was turned off since. While both endpoints receive every event, both run full handlers against the same database.

`creditAffiliateCommission` checks for an existing commission, then creates one, with no lock. That is exactly the pattern two concurrent deliveries can break into a **double commission**.

Recommendations:

1. **⚠ Davin:** check in the Stripe dashboard whether both endpoints are still active. Then either retire the monolith endpoint, as 4A-13's checklist step 4 allows, or keep it and add (2).
2. A shared `ProcessedWebhookEvent(provider, eventId)` table with a unique constraint. Both handlers insert into it **inside** their transaction, and treat a unique-constraint violation as "already processed".
3. A unique constraint on `Commission (affiliateCodeId, stripeInvoiceId)` for non-clawback rows, so the database itself refuses a second commission. This is a schema change: read `.claude/architecture/database-traps.md`, and the Executor never applies production migrations.

A Redis key in `money-service` alone, as §4.3.4 proposes, does not cover the monolith.

### 4.7 Order shape and governance

To pass CONFIRM, each item of the revised plan needs:

- **Decisions taken.** For example: the gate is an allow-list, not a deny-list; `SkipThrottle` versus a key-based tracker; whether the Bull contract re-processes or acknowledges.
- **`⚠ NEEDS EXPLICIT SIGN-OFF`** on every auth, money, CORS or secrets item. That means §3.1, §3.4's throttling change, §4.x, §5.1, §5.5 and §5.6, not only Tier 2.
- **One verifiable unit per session.** That means one service and one concern at a time. "All of Tier 3" is roughly ten sessions.
- **A failing test first** for every defect fix. This is possible for every Tier 1 and Tier 2 item. §3.5 needs real Bull on Redis (or `ioredis-mock`), because the existing mocks cannot show the drop.
- **Verification** using the repo's real commands (§7), and a **rollback** line.
