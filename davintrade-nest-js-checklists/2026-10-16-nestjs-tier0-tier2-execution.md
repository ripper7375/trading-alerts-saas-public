## 2. Needs from Davin

In the order they bite.

1. **Before money-service is redeployed, make sure `NEXTAUTH_URL` and `DLOCAL_API_KEY` are set on it in
   production (2.5).** The service now refuses instead of guessing: Stripe checkout answers **503
   `CHECKOUT_NOT_CONFIGURED`** without `NEXTAUTH_URL` (it used to send paying customers back to
   `http://localhost:3000`), and dLocal create-payment answers **503 `PAYMENTS_NOT_CONFIGURED`** without either
   (it used to answer with a fake `sandbox.dlocal.com/pay/mock-...` link and a PENDING row). If production relies on
   the fallback today, checkout will stop until the variables exist. The Next.js app is not affected.
2. **Apply the migration, then deploy (2.1).** `prisma/migrations/20261016000000_add_processed_webhook_events_and_commission_uniqueness/migration.sql`
   (a file; I did not apply it).
   - Run the two **pre-flight queries** in its header against production first. Both must return **zero rows**. If
     either returns rows, those are real double credits (the affiliate's counters were incremented twice); the unique
     index will refuse to build and nothing changes. Decide those rows by hand before applying.
   - Order: migration, then money-service, then the monolith. The new code is safe on the old schema (the claim fails
     open and logs, and a unique violation cannot happen before the indexes exist), but the protection starts only
     when the table and the indexes are there.
   - `prisma migrate status` first (steps 2 to 7 may still hold pending migrations), then
     `prisma db execute --file ...` and `prisma migrate resolve --applied 20261016000000_add_processed_webhook_events_and_commission_uniqueness`.
   - The migration grants the new table to `money_svc` **if that role exists** (a guarded `DO` block). Confirm which
     database role money-service and the monolith use in production; with no grant the claim logs an error and the
     deduplication silently stays off.
3. **Stripe Dashboard (4A-13 step 4): is the monolith endpoint `/api/webhooks/stripe` still registered next to
   money-service's `/v1/webhooks/stripe`?** I cannot see it. If both are, every event is delivered twice; the
   migration plus the shared claim now make that safe, but retiring the monolith endpoint is still the cleaner end
   state. Until the claim table exists, the commission uniqueness is the only thing standing between a double
   delivery and a double commission.
4. **Account-deletion e-mail (1.1) is now real.** Confirm `RESEND_API_KEY`, `RESEND_FROM_EMAIL` and `NEXTAUTH_URL` on
   operation-service. Note the links changed: the old code pointed at `/account/confirm-deletion` and
   `/account/cancel-deletion`, which are not pages; the real public pages are
   `/settings/account/delete/confirm` and `/settings/account/delete/cancel`. **Separate gap, not touched:**
   `UsersService.confirmDeletion` still carries `TODO (preserved from SOURCE): queue deletion job`, so confirming a
   deletion does not delete anything.
5. **Gateway deploy (1.6).** Watch Paths are still unset on Railway, so any push to `main` redeploys
   `railway-gateway`; push outside a Stack D certification window. `trust proxy` is `1` (one hop); if the production
   path has two proxies in front of the gateway, the counted address is still the inner one. Check the real
   `X-Forwarded-For` chain once. The process now exits with `process.exit(0)` after draining instead of
   re-sending SIGTERM to itself.
6. **CI (0.1).** First push will show whether the workflow is green on `ubuntu-latest` with Node 22 and Python 3.11.
   The gateway's `npm run lint` step is **left out** (the script matches no files and exits 2; see section 3).
7. **Tier 0 §4.2 (the Railway and Stripe runtime inventory)** is still yours: start commands, replicas, draining,
   Watch Paths, `max_connections`, whether PgBouncer is in front. It is also what 2.9's "CRON_ENABLED on at most one
   instance" depends on.
8. **Commit and push** when you decide. I made no commit. The pre-push hook runs the whole root suite.

## 4. Verification

- Per unit: `npx tsc --noEmit`, the unit's specs, then the whole service's tests and `npm run build`. The full runs are
  in section 1's table. The gateway also ran `npm run test:e2e` and `npm run check:sensor-kit`.
- **Mutation checks** (break the code, see a test fail, restore byte for byte): the stack-promotion guard (1.3, 4
  failures), the Redis give-up (1.4, 3), `@SkipThrottle()` on one controller (1.6, 2), the unique-violation handling
  (2.1, 2), the overlap guard (2.6, 3), the user in the idempotency key (2.8, 5). The shutdown specs first failed on a
  5-second default timeout under load; they now carry an explicit 30-second timeout and poll for the observable
  outcome instead of counting event-loop ticks.
- **Real PostgreSQL 18.0**, scratch cluster, never production: migration refuses on the seeded duplicates and rolls
  back whole; applies once they are gone; no drift against the new Prisma schema (`migrate diff --exit-code` 0); the
  constraints refuse the duplicates; and the concurrency proofs of 2.1, 2.2, 2.3, 2.4 and 2.6. Scripts and how to
  re-run them: [the proofs folder](./2026-10-16-nestjs-tier0-tier2-proofs/README.md).
- Two things the real server caught that unit tests could not: Prisma prints a `prisma:error` block for every
  expected unique violation (so the claim uses `createMany({ skipDuplicates })` and the logs stay clean), and a lease
  comparison against a database default would break if the database session were not on UTC (so `createdAt` is written
  by the service, from the same clock as the cutoff).

## 6. Found, not fixed (out of scope; each is small)

- **`money-service/src/redis/redis.service.ts` has the same `times > 10` give-up** that 1.4 fixed in
  `operation-service`: after a Redis outage over about 27 seconds the cache and idempotency store stay dead until the
  process restarts.
- **`reserveAffiliateCode` has the same race as 2.2** (money-service and the monolith): read the status, then update
  unconditionally. Two checkouts with one code can both reserve it. It is the Stripe path, which `processAffiliateConversion`
  (dLocal) is not.
- The monolith's refund path still cancels a `PENDING` commission non-atomically (money-service's is atomic now). The
  shared claim and the unique indexes cover the dual-delivery case; a single endpoint receiving two refunds at once is the
  residue.
- `operation-service/src/main-worker.ts` calls `enableShutdownHooks()` with its defaults (same as 1.6).
- `operation-service/src/users/users.service.ts` still logs plaintext e-mail addresses (profile change, password
  change, deletion confirmed and cancelled), though no longer a token.
- `ProcessedWebhookEvent` has no purge job (about 90 days is plenty; the SQL is in the migration header), and the dLocal
  and RiseWorks webhooks do not use it (2.3's conditional update covers their completion).
- A crash between the commit and the acknowledgement of an alert-dispatch job can still repeat the notification
  (2.7 removes the Redis-publish cause, not this one; Tier 3 §8.4).
