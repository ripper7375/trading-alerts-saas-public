## 1. Verdict

**The plan works well as a map. It is not ready to be APPROVED as an order.**

What the plan does well:

- It covers every checklist control and maps each one to a unit.
- All four P0 findings are real. Unit 0.1 (`/api/test/seed`) is a genuine live Critical, and its blast radius is larger than the plan says (§2.1).
- Most paths and line numbers are right. Tier 2's `React.cache()`, the admin BI waterfalls, `after()` for the view count and the error sanitising are sound and low-risk.

What blocks approval:

1. **Unit 1.1 rests on a premise the code contradicts.** No proxied route falls back to local Prisma when the proxy throws. The Prisma paths run only when a cutover flag is off, or in admin view-as. A proxy error becomes an HTTP error (`app/api/alerts/route.ts:168-174, 280-289`). So timeouts do not "let the fallback execute". They turn a hang into an error. On **proxied writes** (alerts, 2FA, profile, password) a 5 s timeout can report failure for a write that has already succeeded downstream, and the user's retry then duplicates it (§4.1).
2. **Most of Unit 2.2's Stack D items would break documented contracts and passing tests.** `loadWorld` already uses `Promise.all` (`lib/engine4/server/context.ts:136-166`). `readProfile` must stay first: a test asserts it, and its result feeds the other reads. `readStructureLevels` needs hashes from `readSynthesisDetail`. The intake gate order is a stated architecture rule. Intake trace stages are recorded in the order they _finish_, and tests assert that order. Only the reply orchestrator (and `state-api`'s balance plus profile reads) can be parallelised safely (§5 Q5).
3. **Unit 1.2 needs a guard-test change the plan does not foresee, and does not need the dependency it asks sign-off for.** Next.js 16 handles `server-only` itself, and `next/jest` already maps it. But three Stack D guard suites reject the import, and two of them cannot be fixed by an allow-list entry alone (proved by experiment, §5 Q4). The plan's `lib/dlocal/*.ts` glob would also break the client build, because four Client Components import `lib/dlocal/constants.ts`.
4. **Three remediations would do harm if executed literally.** `safeCallbackUrl(url, '')` in the NextAuth `redirect` callback rejects `/login`, `/register` and `/verify-2fa` (§2.3). `experimental.taint: true` switches the whole `app/` directory onto React's **experimental** channel (`taint.md`). `next/dynamic(..., { ssr: false })` in `app/admin/dashboards/regional/page.tsx` is a build error, because that page is a Server Component (`lazy-loading.md:94-95`).
5. **The headline numbers contradict the plan's own matrix.** The checklist has **45** controls, not 38, and the plan's matrix rows say **12 Pass · 10 Partial · 23 Fail**, not 10 · 8 · 20. RTE-01 counts 108 route handlers; there are **148**.
6. **Governance gaps.** Several units change auth or money paths with no `⚠ NEEDS EXPLICIT SIGN-OFF`: 0.1, 0.4 with 1.6, 1.4, 1.5, and 2.4, whose routes include dLocal, disbursement and the Stripe webhook mirror. Unit 1.1's reply timeouts are decision **D23** (`docs/adr/099-prompt-and-reply-as-built-in-step-7.md:103-105`). The realtime token design is decision **F8 Q4**. The plan would re-open both without saying so. There is no `Decisions taken` section, and each tier is a multi-session batch, not one verifiable unit (non-negotiables 1, 2, 5 and 7).

**Recommendation:** Davin takes the revised P0 in §2 now, as four small orders. The Advisor then revises the rest along §6.

## 2. P0: what holds and what changes

### 2.1 Unit 0.1 `POST /api/test/seed`: confirmed Critical, and wider than written (⚠ auth)

**Confirmed in code.** `app/api/test/seed/route.ts:66-80` computes `process.env['TEST_SECRET'] || 'test-secret'` and lets the request through when the header matches, whatever `NODE_ENV` is. `GET` (`L232-240`) and `DELETE` (`L254-264`) have no such bypass. After `bd67b30c`, `admin-test@trading-alerts.test` is no longer a fixed account (`lib/auth/auth-options.ts:183-221`), so the seeded database row is a working ADMIN login with password `AdminPassword123!`.

**What the plan leaves out:**

- **`NODE_ENV` is inlined as `"production"` by `next build`.** In every built deployment, Vercel production and previews alike, the `ALLOWED_ENVIRONMENTS` branch is never true. The header is therefore the _only_ way the `POST` ever runs in a build. The archived E2E setup sends exactly `'test-secret'` (`e2e/archive/global.setup.ts:32-35`). The fallback is not an edge case: it is the path the route was designed around. (The repo already knows this inlining trap: `lib/auth/auth-options.ts:223` reads `Reflect.get(process.env, 'NODE_ENV')` on purpose.)
- **Money impact, not only an admin login.** The same call also:
  - upserts `pro-test@trading-alerts.test` with an `ACTIVE` PRO subscription and no payment (`L126-145`). Fixed accounts are disabled in production, so this row logs in through the normal database path, as a PRO user;
  - creates an `ACTIVE` affiliate profile with bank details (`L147-171`);
  - creates two live discount codes, `TESTCODE10` and `TESTCODE20` (10 % and 20 % off, 20 % commission, valid 90 days; `L178-213`), which anyone can then use at checkout.
- `L225` and `L284` return `String(error)`, as the plan says.

**Recommended fix:**

1. No live caller exists (§5 Q1), so **delete `app/api/test/seed/route.ts`**, and remove its allow-list line at `__tests__/lib/systemconfig-figures-guard.test.ts:124`.
2. If Davin wants to keep it for local E2E instead, make all three handlers return **404** when `process.env.NODE_ENV === 'production'` (the bundler then drops the body), and remove the header bypass entirely. With no secret, `timingSafeEqual` is not needed.
3. **Runtime check for Davin (read-only):** do `*@trading-alerts.test` users or the codes `TESTCODE10` / `TESTCODE20` exist in production? If they do, find out whether they came from the seed route or from preview sign-ins (see §8), then deactivate them.

### 2.2 Unit 0.2 `'use server'` in the fraud service: real, latent, and still worth the one-line fix

- **Confirmed:** `lib/fraud/fraud-detection.service.ts:1` is `'use server'`. The seven exports sit at the lines the plan gives. None of them checks auth or validates input.
- **Callers are wrong in the plan.** Only `app/api/admin/fraud-alerts/route.ts` and `app/api/admin/fraud-alerts/[id]/route.ts` import the module, and both call `requireAdmin()`. There is no `[id]/block-user/route.ts`. `app/api/payments/dlocal/create/route.ts` does not import it. `runFraudChecks`, `createFraudAlerts` and `detectAndAlertFraud` have **no caller at all**.
- **The severity is overstated.** Next 16 creates encrypted, non-deterministic action IDs and removes unused actions from client bundles (`node_modules/next/dist/docs/01-app/02-guides/data-security.md:283-291`). No Client Component or Server Component imports this module (§5 Q2), so no action ID reaches a browser. The exposure is latent: it becomes a public, unauthenticated `blockUserFromFraudAlert` the day any client file imports the module. Rate it **High (latent)**. Keep it in P0 only because the fix is one line with no risk.
- **Step 2 is already done.** In `app/dev/report2/`, `buildScene()` calls `refuseInProduction()` first (`world.ts:186-195`), and `page.tsx:26` answers 404 in production. Drop this step.

### 2.3 Unit 0.3 NextAuth `redirect`: fix one branch, leave the other alone (⚠, as the plan says)

- **Real:** `targetHost.endsWith('.vercel.app')` (`lib/auth/auth-options.ts:656`) is an open redirect to any Vercel subdomain.
- **Missed:** `L657-658` also accept `localhost` and `127.0.0.1` in production, which redirects a victim to a port on their own machine. It is minor; allow these only outside production.
- **Not exploitable:** the relative branch (`L645-646`). It returns `` `${baseUrl}${url}` ``, so `//evil.com` becomes `https://davintrade.app//evil.com`, and the host stays `davintrade.app`. `/\evil.com` normalises the same way. Hardening it is optional.
- **Do not use `safeCallbackUrl(url, '')` here.** It rejects `/login`, `/register` and `/verify-2fa` (`lib/auth/safe-callback-url.ts:24, 56-63`), because it was built for _post-login_ returns. With an empty fallback, any NextAuth flow whose callback is an auth page would land on the home page.
- Recommended shape: accept a relative URL unless it starts with `//` or contains `\`; otherwise require an exact origin match against `new URL(baseUrl).origin` (keeping today's apex/www equivalence). In previews, also accept `https://${VERCEL_URL}` (and `VERCEL_BRANCH_URL` if branch aliases are used).
- **Testing note:** `vercel.json` `ignoreCommand` skips builds for `claude/*` and `docs/*` branches, so an Executor branch never gets a preview deploy. The preview leg must be tested on a branch Davin pushes.

### 2.4 Unit 0.4 `lib/csrf.ts`: a real bug whose live exploit is login CSRF, not the 45 routes (should be ⚠)

- **Confirmed:** `origin.startsWith(allowed)` (`L26`), and `return true` when Origin is absent (`L22-24`). Also missed: `http://${host}` is accepted in production (`L18`).
- **Where it bites today.** `validateOrigin()` has 12 callers: the ten `app/api/auth/*` routes (`token-*`, forgot / reset / resend) and the two admin view-as routes. Most are **unauthenticated**, so `SameSite=Lax` does not help them. `token-login` calls `validateOrigin()` (`L49`), then `request.json()` with no content-type check (`L56`), then sets the session cookies (`L94-100`). A page on `https://davintrade.app.attacker.com` can therefore POST a `text/plain` JSON body that needs no CORS preflight and passes the prefix test. That logs the victim into the attacker's account (login CSRF). Fixing the comparison closes this.
- **Missing Origin.** Current browsers send `Origin` on every non-GET/HEAD request, same-origin included, so a missing Origin means a non-browser client. Refusing when `Sec-Fetch-Site` is `cross-site` is right. Also refuse `same-site` for routes that need it: in production the cookie domain is `.davintrade.app` (`auth-options.ts:43-44`), so sibling subdomains such as `chat-api.davintrade.app` are same-site. A `Referer` fallback adds little, since `Referrer-Policy` already trims cross-origin referers to the origin. Do not trust `x-forwarded-host` on its own.
- **API shape.** Let `validateOrigin(request?)` read `request.headers` when it is given a `Request`, and fall back to `next/headers` only when it is not. This matters for testing (§5 Q3).
- **No unit test of `lib/csrf.ts` exists.** Every route test mocks the module (`__tests__/api/auth/token-login.test.ts:19`, `__tests__/api/admin-user-view-as.test.ts:28`). The unit must add `__tests__/lib/csrf.test.ts` covering: exact match, suffix spoof, port mismatch, `http` in production, apex vs `www`, a missing Origin with and without `Sec-Fetch-Site`.
- The plan has no ⚠ here. The change alters the login, register and password-reset flows, so it is auth (non-negotiable 5).

## 4. Cross-cutting issues

### 4.1 There is no "Prisma fallback on throw", so timeouts change error behaviour

Take `POST /api/alerts` with the flag on. It forwards, and any throw goes to the outer `catch`: an `OperationServiceError` is mapped to its status, and anything else becomes a 500 (`app/api/alerts/route.ts:168-174, 280-289`). A search of every proxied route for a fallback-on-error pattern found none. What a timeout really buys is a fast error instead of a Vercel function that hangs until its own limit.

That matters most on **writes**. A timeout that fires after `operation-service` (or dLocal, or money-service) has committed returns an error for a successful write. The user retries and gets a duplicate: a second alert, or a second 2FA setup secret. Recommendations:

- Reads: about 5 s, following `lib/active-indicator/gateway-client.ts:288-311`. Map the abort to a typed `TIMEOUT` and a 504 with a code, not a bare 500.
- Writes: a timeout at least as long as the downstream's own budget (≈15 s), no automatic retry, and an idempotency key where the downstream supports one. The Stripe SDK sets idempotency keys on its own retries; its defaults today are 80 s and 1 retry (`stripe@14.25.0`).
- The R2 client: set `requestHandler` timeouts (connection and socket) on the `S3Client` rather than a 5 s `AbortSignal` per call. `getChartImage` streams the body with `transformToByteArray()` (`r2.ts:177`), so a wall-clock abort can cut a large image mid-read.
- Check each route's `maxDuration` and the plan's Vercel limit before choosing numbers. ADR-099 D23 records that "the Vercel plan's limit was not checked".

### 4.2 The CSRF surface is narrower than "45+ routes", and is better closed in one place

- Every session cookie is `SameSite=Lax` (`lib/auth/auth-options.ts:688-771`, `lib/operation-service/cookies.ts:34-48`), so a cross-site POST does not carry the session.
- The Stack D POST bodies must be `application/json` (`lib/engine4/server/request.ts:49-56`, `lib/intake/server/request.ts:44-51`; reply reuses the intake reader). The engine4 file says outright that this is the intended CSRF guard (`L4-6`). PATCH and DELETE are non-simple methods. No route sends `Access-Control-Allow-Origin`. So a cross-site browser cannot reach these routes at all.
- **What is left:** (a) same-site sibling subdomains, since the production cookie domain is `.davintrade.app`; (b) unauthenticated POSTs that parse JSON without checking content type: the login-CSRF case in §2.4.
- **Better than editing ~45 handlers and four Stack D wrappers:** one check in `middleware.ts` (or `proxy.ts`, §4.4) for non-GET `/api/**`. It compares `Origin` exactly with the allowed origins, or accepts `Sec-Fetch-Site: same-origin`, and refuses otherwise. Its exclusions are the machine callers: `/api/webhooks/{stripe,dlocal,riseworks}`, `/api/cron/**`, and any API-key route (e.g. `/api/admin/system/jobs/[jobId]/trigger`). Make that inventory part of the order. A wrapper-level change instead would need a new code in the closed error catalogues (`Engine4ErrorCode` / `ERROR_STATUS`, the intake and reply equivalents) and changes to the Stack D contract docs. The middleware matcher already covers `/api` (`middleware.ts:209-218`); keep the CSRF check _outside_ the fail-open `try`.

### 4.5 The locale dictionaries are the biggest client-bundle item

`lib/context/locale-context.tsx:45-59` statically imports `th.json` (666 KB), `en-GB.json` (374 KB) and `en-US.json` (374 KB). That is about **1.4 MB raw and ≈ 328 KB gzip, on every page**, and it outweighs the chart libraries. Recommended order of work:

1. Load **only the active language** as a per-language chunk. The server knows the language, so the layout can preload it, and the provider can `use()` the import promise so hydration waits for a cached chunk. That keeps the "first paint is already translated" guarantee the comment at `L49-54` protects.
2. Passing the dictionary as an RSC prop is the plan's alternative. It re-sends ~90–145 KB gzip on every `router.refresh()`, and saving a theme triggers one through its Server Action (`app/(marketing)/page.tsx:17-20`). Prefer cacheable chunks.
3. `en-US` and `en-GB` differ by a handful of rows, so ship `en-US` as an overlay.

A language switch must still work without a reload, so the order needs a test for that.

### 4.6 Findings the plan does not have

1. **The realtime endpoint hands the 30-day session token to JavaScript.** `app/api/realtime/token/route.ts:21-28` returns `getOperationServiceToken()`, which is the raw `httpOnly` session cookie value (`lib/operation-service/client.ts:179-187`). 4. **Plain-HTTP `ip-api.com`** (user IPs in cleartext to a third party, no timeout) on the 2FA, password and login-tracking paths (§3.3 STB-01).

### Q3 CSRF in the Stack D wrappers and test headers

**How the tests build requests.**

- `__tests__/api/engine4/helpers/mocks.ts:126-140` and `__tests__/api/intake/helpers/mocks.ts:319-328` build `new Request('http://localhost' + path, { method, headers: { 'content-type': 'application/json' } })`.

That would break the 13 route-level suites that go through a wrapper: `__tests__/api/engine4/*` (5), `__tests__/api/intake/*` (3), `__tests__/api/chat/{message,routes}.test.ts` (2; `threads.test.ts` too if the check goes into the thread handlers), `__tests__/lib/engine4/server/trace-respond.test.ts`, `__tests__/components/report2/api-parity.test.ts` and the PostgreSQL spec `__tests__/engine4/engine4-routes.pg.spec.ts`.

- Yes: `validateOrigin(request)` should read `request.headers` whenever a `Request` is at hand. Every route handler has one, and it is also what makes the check testable.
- Under the policy in §2.4, a request with no `Origin` and no `Sec-Fetch-Site` is allowed. The existing tests therefore keep passing unchanged, and new tests add the cross-site cases.
- `createChatAuth` (`lib/reply/server/threads-api.ts:64`) is a factory that reads `env`, not a per-request wrapper, so it is the wrong place. The thread handlers take the `Request`.
- Better still, do it once in middleware (§4.2) and leave the Stack D wrappers and their closed error catalogues alone.

Why the allow-list alone cannot pass reply, platform and intake: each of those guards has **two** checks. The AST check (`analyse()`) sees the bare import and demands an allow-list entry. The "exactly" checks collect imports with the regex `/from '([^.][^']*)'/g`, which never matches `import 'server-only'` (there is no `from`), so they then fail on the entry the AST check required.

The fix is one of these, in the guard tests (`__tests__/lib/reply/boundaries.test.ts` "exactly" tests and `__tests__/lib/intake/boundaries.test.ts:414-457`):

The second is cleaner: one rule, and the pure folders stay import-free. Either way, each guard's own self-test snippets should gain one case: `server-only` allowed in `server/`, refused in a pure file.

**Jest, tsc, ESLint:** a module carrying the import loads in Jest, because `next/jest` already maps it to an empty module. `npx tsc --noEmit` exits 0 and ESLint exits 0, both **without** installing the package. So `jest.config.js` needs no `moduleNameMapper`, and `package.json` needs no dependency. Two cautions:

- Never put the import in a pure file. Client Components import the intake barrel and `lib/engine4/templates/**`; the guards keep those free of server code today.
- Exclude `lib/dlocal/constants.ts` from the list (§3.4).
