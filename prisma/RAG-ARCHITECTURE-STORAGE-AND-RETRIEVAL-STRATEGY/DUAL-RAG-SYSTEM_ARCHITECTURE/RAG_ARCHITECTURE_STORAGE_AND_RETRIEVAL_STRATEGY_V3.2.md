## 1. Storage Strategy and Architecture

### 1.1 Core Principles

**Principle 1: Right Data, Right Storage**

- Time-series numerical data (OHLCV + Indicators) → PostgreSQL as **native columns** (optimized for range queries and aggregations)
  - **NO conversion needed** — Both OHLCV and indicator values are structured, predictable data from MT5 data pipeline
  - Stored as separate columns with proper data types for SQL performance
- Descriptive market context (JSONB Comments) → PostgreSQL as **single JSONB column** alongside quantitative data
  - Auto-generated by PostgreSQL trigger at insert time
  - Permanently attached to each row — historical context preserved forever
  - Multiple comments per indicator per timestamp (extensible without schema change)
- Static knowledge → Vector DB (optimized for semantic search)
- User profiles → Filesystem (human-readable, versionable)
- Audit trails → Filesystem (append-only, archivable)

**Principle 2: Store What Cannot Be Regenerated Faithfully**

- Market conditions at a specific historical timestamp are **unique and unrepeatable**
- JSONB comments capture the descriptive meaning of conditions _at the moment they occurred_
- Retroactive regeneration from raw numbers loses temporal context (what was "significant" then may not be identifiable now)
- Store descriptive context permanently; it is irreplaceable historical narrative

**Principle 3: Optimize for Access Pattern**

- Hot data (recent 24 hours) → In-memory cache + PostgreSQL indexes
- Warm data (1-90 days) → PostgreSQL with standard indexes (OHLCV + JSONB comments together)
- Cold data (> 90 days) → Compressed archives on filesystem

**Principle 4: Symbol-Timeframe Independence**

- Each symbol-timeframe pair (e.g., XAUUSD-H4, XAUUSD-H1) is an **independent trading instrument**
- Different timeframes have different: OHLCV values, indicator values, JSONB comments, support/resistance levels, market commentary, trading behavior, and user context
- Database schema must support this independence with proper indexing on (symbol, timeframe, timestamp) tuples

### 1.3 Storage Decision Matrix

| Data Type                  | Characteristics                          | Storage                   | Indexed?                                      | Update Frequency         |
| -------------------------- | ---------------------------------------- | ------------------------- | --------------------------------------------- | ------------------------ |
| **(1) OHLCV + Indicators** | Numerical, time-series                   | PostgreSQL                | SQL indexes on (symbol, timeframe, timestamp) | Every 5 min              |
| **(2) JSONB Comments**     | Descriptive text, per-row, per-indicator | PostgreSQL (JSONB column) | GIN index on comments column                  | Auto at insert (trigger) |
| **(3) Trading Knowledge**  | Text, static                             | Vector DB                 | Vector embeddings                             | Rarely (curated)         |
| **(4) User Profiles**      | Text, semi-static                        | Filesystem                | Vector embeddings                             | Weekly/Monthly           |
| **(5) Audit Logs**         | JSON Lines, append-only                  | Filesystem                | No (sequential)                               | Every interaction        |

**Why JSONB Comments in PostgreSQL (not on-demand generation)?**

- Historical descriptive context is **unrepeatable** — conditions at a past timestamp cannot be faithfully reconstructed after the fact
- Each row tells its complete story **permanently** — even months later, retrieve any timestamp and know exactly what the market conditions meant
- Multiple comments per indicator per row — LLM receives multi-dimensional narrative, not just numbers
- Zero schema changes needed when adding more indicators or comment types — JSONB grows freely
- Auto-generated by PostgreSQL trigger — zero manual work, zero latency, zero application overhead

### 2.1 PostgreSQL Schema

#### 2.1.1 Market Data Tables

```sql
-- Table 1: OHLCV + Indicators + JSONB Comments (Core Time-Series)
CREATE TABLE ohlcv_5m (
    id BIGSERIAL PRIMARY KEY,
    symbol VARCHAR(20) NOT NULL,
    timeframe VARCHAR(10) NOT NULL DEFAULT '15m',
    timestamp TIMESTAMP NOT NULL,

    -- Price data
    open DECIMAL(20,5) NOT NULL,
    high DECIMAL(20,5) NOT NULL,
    low DECIMAL(20,5) NOT NULL,
    close DECIMAL(20,5) NOT NULL,
    volume BIGINT NOT NULL,

    -- Technical indicators (calculated)
    atr_value DECIMAL(20,5),
    atr_percentile INT,       -- 0-100
    adx_value DECIMAL(10,2),
    rsi_value DECIMAL(10,2),
    tema_value DECIMAL(20,5),
    hrma_value DECIMAL(20,5),
    smma_value DECIMAL(20,5),

    -- Market regime classification
    trend_direction VARCHAR(10),      -- 'UP', 'DOWN', 'RANGING'
    volatility_regime VARCHAR(20),    -- 'LOW', 'MEDIUM', 'HIGH'
    swing_momentum VARCHAR(20),       -- 'Over-Bought', 'Over-Sold', 'Neutral'

    -- Support/Resistance (JSONB for flexibility)
    support_levels JSONB,
    resistance_levels JSONB,

    -- Reversal signals
    reversal_probability VARCHAR(20), -- 'Likely', 'Possible', '---'

    -- ─────────────────────────────────────────────────────────────────
    -- JSONB COMMENTS: Auto-generated by trigger at insert time.
    -- Stores multi-dimensional descriptive context per indicator.
    -- Single JSONB column = flexible, extensible, no schema changes needed.
    --
    -- Structure example:
    -- {
    --   "tema":     { "comment_1": "...", "comment_2": "..." },
    --   "hrma":     { "comment_1": "...", "comment_2": "..." },
    --   "smma":     { "comment_1": "...", "comment_2": "..." },
    --   "momentum": { "comment_1": "...", "comment_2": "..." },
    --   "atr":      { "comment_1": "...", "comment_2": "..." },
    --   "reversal": { "comment_1": "..." }
    -- }
    -- ─────────────────────────────────────────────────────────────────
    comments JSONB NOT NULL DEFAULT '{}',

    -- Constraints
    CONSTRAINT unique_symbol_timestamp UNIQUE(symbol, timeframe, timestamp)
);

-- Essential indexes for sub-10ms queries
-- CRITICAL: Symbol + Timeframe is the combined key for independent trading instruments
CREATE INDEX idx_ohlcv_symbol_timeframe_time
    ON ohlcv_5m (symbol, timeframe, timestamp DESC);

CREATE INDEX idx_ohlcv_recent
    ON ohlcv_5m (symbol, timeframe, timestamp DESC)
    WHERE timestamp >= NOW() - INTERVAL '24 hours';

-- GIN index for JSONB comments (enables fast JSON key searches)
CREATE INDEX idx_ohlcv_comments
    ON ohlcv_5m USING GIN (comments);

COMMENT ON TABLE ohlcv_5m IS 'Raw market data with calculated indicators and auto-generated JSONB comments';
COMMENT ON COLUMN ohlcv_5m.comments IS 'Auto-generated descriptive context per indicator. Single JSONB column — add new indicators without schema change.';
COMMENT ON INDEX idx_ohlcv_symbol_timeframe_time IS 'Primary index for symbol-timeframe queries (e.g., XAUUSD H4)';
COMMENT ON INDEX idx_ohlcv_comments IS 'GIN index for searching within JSONB comments';
```

#### 2.1.2 Two-Stage Index Strategy

Every query against `ohlcv_5m` follows a two-stage narrowing process. PostgreSQL applies both indexes automatically in this order — no explicit instruction needed.

```
┌─────────────────────────────────────────────────────────────┐
│              TWO-STAGE INDEX STRATEGY                        │
└─────────────────────────────────────────────────────────────┘

Stage 1: Composite + Time Index
         "Where and When"
         ──────────────────────────────────────────
         Answers: Which symbol? Which timeframe?
                  Which time range?
         Index:   idx_ohlcv_symbol_timeframe_time
         Result:  Millions of rows → ~16 target rows
         Speed:   5-20ms

              ↓  (16 rows identified)

Stage 2: GIN Index
         "What Happened"
         ──────────────────────────────────────────
         Answers: Which specific conditions exist
                  inside those 16 rows?
         Index:   idx_ohlcv_comments (GIN)
         Result:  16 rows → rows matching condition
         Speed:   ~1ms (tiny dataset after Stage 1)
```

**Why this order matters:**

- GIN first (wrong) → scan `comments` across millions of rows → very slow
- Composite first (correct) → narrow to ~16 rows → GIN operates on tiny set → near instant

**Example query using both stages:**

```sql
-- Stage 1: Composite index → finds XAUUSD + H4 + last 4 hours
-- Stage 2: GIN index → filters for LIKELY reversal inside those rows

SELECT timestamp, close, comments
FROM ohlcv_5m
WHERE symbol    = 'XAUUSD'                          -- Stage 1 ↓
  AND timeframe = 'H4'                              -- Stage 1 ↓
  AND timestamp >= NOW() - INTERVAL '4 hours'       -- Stage 1 ↓
  AND comments @> '{"reversal": {"comment_1":
      "Reversal probability: LIKELY"}}'             -- Stage 2 ↓
ORDER BY timestamp DESC;
```

**When each index is used:**

| Query Pattern               | Stage 1 | Stage 2 | Example User Query                                |
| --------------------------- | ------- | ------- | ------------------------------------------------- |
| Fetch latest N bars         | ✅ Yes  | ❌ No   | "What is XAUUSD H4 doing now?"                    |
| Fetch + filter by condition | ✅ Yes  | ✅ Yes  | "Any reversal signals on XAUUSD H4 last 4 hours?" |
| Search conceptual knowledge | ❌ No   | ❌ No   | "What is RSI?" (Vector DB only)                   |

**Key rule**: Stage 2 (GIN) is only activated when the query filters by comment content. For standard RAG retrieval (fetch latest rows + return JSONB as part of result), only Stage 1 fires. The JSONB column is simply returned as data — not searched inside.

````
#### 2.1.2 PostgreSQL Trigger: Auto-Generate JSONB Comments

The trigger fires automatically on every INSERT, populating the `comments` column based on the row's quantitative values. No application-level code is needed. No ETL pipeline required.

```sql
-- ─────────────────────────────────────────────────────────────────────────
-- TRIGGER FUNCTION: generate_ohlcv_comments()
-- Purpose: Auto-populate the JSONB comments column at insert time.
-- Fired: BEFORE INSERT on ohlcv_5m, FOR EACH ROW.
-- Result: Every row is self-describing — numbers + meaning, permanently.
-- ─────────────────────────────────────────────────────────────────────────

CREATE OR REPLACE FUNCTION generate_ohlcv_comments()
RETURNS TRIGGER AS $$
DECLARE
  v_comments JSONB := '{}';
  v_tema_c1  TEXT  := NULL;
  v_tema_c2  TEXT  := NULL;
  v_hrma_c1  TEXT  := NULL;
  v_hrma_c2  TEXT  := NULL;
  v_smma_c1  TEXT  := NULL;
  v_smma_c2  TEXT  := NULL;
  v_mom_c1   TEXT  := NULL;
  v_atr_c1   TEXT  := NULL;
  v_atr_c2   TEXT  := NULL;
  v_rev_c1   TEXT  := NULL;
BEGIN

  -- ── TEMA COMMENTS ────────────────────────────────────────────────────
  IF NEW.tema_value IS NOT NULL AND NEW.close IS NOT NULL THEN
    IF NEW.close > NEW.tema_value THEN
      v_tema_c1 := 'Price above TEMA — bullish bias';
    ELSIF NEW.close < NEW.tema_value THEN
      v_tema_c1 := 'Price below TEMA — bearish bias';
    ELSE
      v_tema_c1 := 'Price at TEMA — neutral';
    END IF;

    IF NEW.trend_direction = 'UP' THEN
      v_tema_c2 := 'TEMA slope rising — momentum building';
    ELSIF NEW.trend_direction = 'DOWN' THEN
      v_tema_c2 := 'TEMA slope falling — downward pressure';
    ELSE
      v_tema_c2 := 'TEMA flat — consolidation phase';
    END IF;
  END IF;

  -- ── HRMA COMMENTS ────────────────────────────────────────────────────
  IF NEW.hrma_value IS NOT NULL AND NEW.close IS NOT NULL THEN
    IF NEW.close > NEW.hrma_value THEN
      v_hrma_c1 := 'Price above HRMA — trend support intact';
    ELSE
      v_hrma_c1 := 'Price below HRMA — trend resistance overhead';
    END IF;

    IF NEW.adx_value IS NOT NULL THEN
      IF NEW.adx_value > 35 THEN
        v_hrma_c2 := 'HRMA showing strong directional alignment (ADX > 35)';
      ELSIF NEW.adx_value > 20 THEN
        v_hrma_c2 := 'HRMA showing moderate trend (ADX 20-35)';
      ELSE
        v_hrma_c2 := 'HRMA flat — low directional conviction (ADX < 20)';
      END IF;
    END IF;
  END IF;

  -- ── SMMA COMMENTS ────────────────────────────────────────────────────
  IF NEW.smma_value IS NOT NULL AND NEW.close IS NOT NULL THEN
    IF NEW.close > NEW.smma_value THEN
      v_smma_c1 := 'Price above SMMA — long-term bullish';
    ELSE
      v_smma_c1 := 'Price below SMMA — long-term bearish';
    END IF;

    -- Check proximity to SMMA (within 0.2% = acting as dynamic S/R)
    IF ABS(NEW.close - NEW.smma_value) / NEW.smma_value < 0.002 THEN
      v_smma_c2 := 'Price at SMMA dynamic support/resistance — decision zone';
    ELSE
      v_smma_c2 := 'Price clear of SMMA — no immediate dynamic S/R interaction';
    END IF;
  END IF;

  -- ── MOMENTUM COMMENTS ────────────────────────────────────────────────
  IF NEW.swing_momentum IS NOT NULL THEN
    CASE NEW.swing_momentum
      WHEN 'Over-Bought' THEN
        v_mom_c1 := 'Over-bought — exhaustion risk, watch for reversal signals';
      WHEN 'Over-Sold' THEN
        v_mom_c1 := 'Over-sold — bounce potential, monitor for entry signals';
      ELSE
        v_mom_c1 := 'Neutral momentum — no extreme reading';
    END CASE;
  END IF;

  -- ── ATR / VOLATILITY COMMENTS ────────────────────────────────────────
  IF NEW.atr_percentile IS NOT NULL THEN
    IF NEW.atr_percentile >= 80 THEN
      v_atr_c1 := format('Extremely high volatility (%s percentile) — widen stops', NEW.atr_percentile);
    ELSIF NEW.atr_percentile >= 60 THEN
      v_atr_c1 := format('Elevated volatility (%s percentile) — normal ATR-based stops apply', NEW.atr_percentile);
    ELSIF NEW.atr_percentile <= 20 THEN
      v_atr_c1 := format('Very low volatility (%s percentile) — potential breakout setup forming', NEW.atr_percentile);
    ELSE
      v_atr_c1 := format('Normal volatility (%s percentile)', NEW.atr_percentile);
    END IF;

    CASE NEW.volatility_regime
      WHEN 'HIGH'   THEN v_atr_c2 := 'Volatility regime: HIGH — increased position risk';
      WHEN 'MEDIUM' THEN v_atr_c2 := 'Volatility regime: MEDIUM — standard risk parameters';
      WHEN 'LOW'    THEN v_atr_c2 := 'Volatility regime: LOW — tight ranges, reduced momentum';
      ELSE               v_atr_c2 := NULL;
    END CASE;
  END IF;

  -- ── REVERSAL COMMENTS ────────────────────────────────────────────────
  IF NEW.reversal_probability IS NOT NULL AND NEW.reversal_probability != '---' THEN
    CASE NEW.reversal_probability
      WHEN 'Likely'   THEN v_rev_c1 := 'Reversal probability: LIKELY — high-confluence reversal signal present';
      WHEN 'Possible' THEN v_rev_c1 := 'Reversal probability: POSSIBLE — early reversal signals, confirm before acting';
      ELSE                 v_rev_c1 := NULL;
    END CASE;
  END IF;

  -- ── ASSEMBLE JSONB OBJECT ────────────────────────────────────────────
  IF v_tema_c1 IS NOT NULL THEN
    v_comments := v_comments || jsonb_build_object(
      'tema', jsonb_build_object('comment_1', v_tema_c1, 'comment_2', v_tema_c2)
    );
  END IF;

  IF v_hrma_c1 IS NOT NULL THEN
    v_comments := v_comments || jsonb_build_object(
      'hrma', jsonb_build_object('comment_1', v_hrma_c1, 'comment_2', v_hrma_c2)
    );
  END IF;

  IF v_smma_c1 IS NOT NULL THEN
    v_comments := v_comments || jsonb_build_object(
      'smma', jsonb_build_object('comment_1', v_smma_c1, 'comment_2', v_smma_c2)
    );
  END IF;

  IF v_mom_c1 IS NOT NULL THEN
    v_comments := v_comments || jsonb_build_object(
      'momentum', jsonb_build_object('comment_1', v_mom_c1)
    );
  END IF;

  IF v_atr_c1 IS NOT NULL THEN
    v_comments := v_comments || jsonb_build_object(
      'atr', jsonb_build_object('comment_1', v_atr_c1, 'comment_2', v_atr_c2)
    );
  END IF;

  IF v_rev_c1 IS NOT NULL THEN
    v_comments := v_comments || jsonb_build_object(
      'reversal', jsonb_build_object('comment_1', v_rev_c1)
    );
  END IF;

  NEW.comments := v_comments;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- Attach trigger to table
CREATE TRIGGER auto_generate_comments
  BEFORE INSERT ON ohlcv_5m
  FOR EACH ROW
  EXECUTE FUNCTION generate_ohlcv_comments();
````

#### 2.1.3 JSONB Comments: Extensibility Design

**No schema change required** when extending comment depth or adding indicators:

```sql
-- Today: 2 comments per indicator
-- { "tema": { "comment_1": "...", "comment_2": "..." } }

-- Tomorrow: 5 comments per indicator — just update the trigger function
-- { "tema": { "comment_1": "...", "comment_2": "...", "comment_3": "...",
--             "comment_4": "...", "comment_5": "..." } }

-- Adding a new indicator (e.g., RSI) — just add to trigger function
-- { ..., "rsi": { "comment_1": "RSI at 68 — approaching overbought territory",
--                 "comment_2": "RSI diverging from price — weakening momentum" } }

-- Zero ALTER TABLE operations required in any of the above cases.
```

### 2.4 Storage Rationale

| Storage Type                                | Why This Choice?                                                                                                                                                                                                                            |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **PostgreSQL for OHLCV + Indicator Values** | Both OHLCV and indicator values come from the same MT5 Contabo VPS data pipeline. SQL excels at time-series range queries, built-in aggregation functions, ACID guarantees, efficient indexing. Native columns = optimal query performance. |
| **PostgreSQL JSONB for Comments**           | Single column holds all indicator comments. Extensible without schema change. GIN index for fast JSON searches. Trigger auto-generates at insert. Historical context preserved permanently alongside quantitative data in same row.         |
| **Filesystem for Markdown Profiles**        | Human-readable, easy versioning, Git-friendly, no database overhead for infrequent updates.                                                                                                                                                 |
| **Filesystem for JSONL Logs**               | Append-only writes (O(1) performance), easy compression for archives, standard format, cost-effective for 7-year retention, sequential access ideal for audit logs.                                                                         |
| **Vector DB for Trading Knowledge**         | Optimized for semantic similarity search, efficient nearest-neighbor algorithms (HNSW, IVF), purpose-built for embeddings, scales to millions of vectors.                                                                                   |

#### 2.4.1 Why JSONB Comments Wins Over On-Demand Generation

The critical architectural decision is to **permanently store** descriptive context alongside quantitative data rather than generating it on-demand at query time.

**Superpower 1: Historical Descriptive Data (Permanently Attached)**

```
timestamp 1772025000  →  numbers + comments (permanently attached)
timestamp 1772025300  →  numbers + comments (permanently attached)
timestamp 1772025600  →  numbers + comments (permanently attached)
timestamp 1772025900  →  numbers + comments (permanently attached)
...
timestamp 1772029800  →  numbers + comments (permanently attached)
```

Every row tells its own complete story — **forever**. Even 6 months later, retrieve any historical timestamp and know exactly what the market conditions meant at that moment. On-demand generation cannot reproduce this: the conditions that made a bar significant at the time may not be identifiable retroactively.

**Superpower 2: Multi-Dimensional Narrative Per Timestamp**

```json
// Each row gives LLM numbers + layered meaning simultaneously
{
  "close": 2679.8,
  "tema_value": 2671.2,
  "comments": {
    "tema": {
      "comment_1": "Price above TEMA — bullish bias",
      "comment_2": "TEMA slope rising — momentum building"
    },
    "hrma": {
      "comment_1": "Price above HRMA — trend support intact",
      "comment_2": "HRMA showing moderate trend (ADX 20-35)"
    },
    "smma": {
      "comment_1": "Price above SMMA — long-term bullish",
      "comment_2": "Price clear of SMMA"
    },
    "momentum": { "comment_1": "Over-bought — exhaustion risk" },
    "atr": {
      "comment_1": "Elevated volatility (72 percentile)",
      "comment_2": "Volatility regime: MEDIUM"
    },
    "reversal": { "comment_1": "Reversal probability: LIKELY" }
  }
}
```

LLM receives the complete multi-dimensional context of every row in a time series query — not just what the numbers were, but what each indicator was signaling at that exact moment. This is the architectural foundation for intelligent, precise responses.

**Combined Effect on LLM Response Quality:**

|                        | On-Demand Generation        | JSONB Comments                    |
| ---------------------- | --------------------------- | --------------------------------- |
| Historical row context | Numbers only                | Numbers + meaning at each point   |
| LLM understanding      | What price was              | What each indicator was signaling |
| Time-series narrative  | Absent from history         | Present for every row             |
| Temporal accuracy      | Reconstructed (approximate) | Captured at the moment (exact)    |
| Response quality       | Basic price summary         | Rich, contextually-aware analysis |

**Example: User asks "What happened to gold in the last hour?"**

Without JSONB comments — LLM sees rows of numbers and can only say:

> "Gold declined from 5191 to 5174, a drop of 17 points."

With JSONB comments — LLM sees numbers + meaning at every step:

> "Gold showed flat momentum in a consolidation phase for 10 bars, with TEMA acting as dynamic resistance overhead. ATR entered elevated volatility at bar 8. The final 4 bars saw over-bought momentum shift to neutral as price broke below SMMA dynamic support with reversal probability rising to LIKELY — indicating a momentum shift rather than a simple price pullback."

Same raw data. Completely different quality.

#### 2.4.2 JSONB Comments vs On-Demand: Comparison

| Dimension             | JSONB Comments                              | On-Demand Generation                        |
| --------------------- | ------------------------------------------- | ------------------------------------------- |
| Historical accuracy   | ✅ Exact — captured when it happened        | ❌ Approximate — reconstructed from numbers |
| Time-series narrative | ✅ Present for every row                    | ❌ Only current bar gets commentary         |
| Storage cost          | ~5-15% increase per row                     | Zero additional storage                     |
| Insert performance    | Minimal — trigger adds ~1ms                 | No overhead at insert                       |
| Query performance     | Same SQL query + JSONB in result            | Same SQL query + generation (2-5ms)         |
| Schema flexibility    | ✅ No ALTER TABLE ever needed               | N/A                                         |
| Extensibility         | ✅ Add indicators/comments freely           | Need to update generation code              |
| LLM context richness  | ✅ Full multi-row narrative                 | ❌ Single snapshot only                     |
| Maintenance           | Trigger function to update if logic changes | Generation function to update               |

**When updating comment logic:** Update the trigger function → new inserts get new comments. Historical rows retain their original comments (as captured at the time). This is correct behavior — historical context should reflect what was true then, not be retroactively reinterpreted.

#### 2.4.3 JSONB Storage Considerations and Mitigations

### 1. Storage Growth

**Reality**: JSONB adds ~200-500 bytes per row vs. raw numerical columns alone.

**Estimate**:

- 15 symbols × 9 timeframes × 288 bars/day = 38,880 rows/day
- ~350 bytes JSONB average per row = ~13.2 MB/day additional
- Per year = ~4.8 GB additional storage for JSONB comments

**Mitigation**: Negligible cost at Railway PostgreSQL pricing. Far outweighed by LLM response quality improvement.

### 2. Comment Logic Updates

**Reality**: If you improve comment generation logic, historical rows retain old comments. New rows get new comments.

**Mitigation**: This is by design. Historical rows correctly describe conditions as they were classified at the time. If full retroactive update is needed, run a background migration:

```sql
-- Background migration to regenerate comments for historical rows
-- Run during off-peak hours, batched to avoid lock contention

UPDATE ohlcv_5m
SET comments = generate_comments_v2(
  tema_value, hrma_value, smma_value,
  swing_momentum, atr_percentile, volatility_regime,
  reversal_probability, close, adx_value
)
WHERE timestamp >= '2026-01-01'
  AND timestamp < '2026-02-01';
-- Run in batches by month
```

### 3. JSONB Query Syntax

**Reality**: Accessing nested JSONB requires specific syntax.

```sql

SELECT
  timestamp,
  close,
  comments -> 'tema' ->> 'comment_1' AS tema_signal,
  comments -> 'momentum' ->> 'comment_1' AS momentum_signal,
  comments -> 'reversal' ->> 'comment_1' AS reversal_signal
FROM ohlcv_5m
WHERE symbol = 'XAUUSD'
  AND timeframe = 'H4'
ORDER BY timestamp DESC
LIMIT 16;

-- Find all rows where reversal was LIKELY
SELECT timestamp, close, comments
FROM ohlcv_5m
WHERE symbol = 'XAUUSD'
  AND timeframe = 'H4'
  AND comments @> '{"reversal": {"comment_1": "Reversal probability: LIKELY — high-confluence reversal signal present"}}'
ORDER BY timestamp DESC;
```

**Mitigation**: Use a typed retrieval helper in your application layer:

### 4.2 Query Routing Logic

```typescript
interface QueryAnalysis {
  hasSymbol: boolean;
  hasTimeframe: boolean;
  hasDateRange: boolean;
  isConceptual: boolean;
  needsUserContext: boolean;
}

function analyzeQuery(query: string): QueryAnalysis {
  return {
    hasSymbol: /\b(XAUUSD|EURUSD|BTCUSD|US30)\b/i.test(query),
    hasTimeframe: /\b(M5|M15|M30|H1|H2|H4|H8|H12|D1)\b/i.test(query),
    hasDateRange: /\b(today|yesterday|last|week|month)\b/i.test(query),
    isConceptual: /\b(how|what|why|explain|define)\b/i.test(query),
    needsUserContext: /\b(my|I|should I|for me)\b/i.test(query),
  };
}

async function routeQuery(query: string, userId: string) {
  const analysis = analyzeQuery(query);

  const engines = {
    sql: false, // Returns OHLCV + JSONB comments
    vectorKnowledge: false,
    vectorUser: false,
    markdownLoad: false,
  };

  // Engine 1: SQL (specific symbol + timeframe)
  if (analysis.hasSymbol && analysis.hasTimeframe) {
    engines.sql = true; // JSONB comments included automatically
  } else if (analysis.hasSymbol && !analysis.hasTimeframe) {
    // Triggers fallback — timeframe needed for SQL
  }

  // Engine 2a: Vector DB (conceptual questions)
  if (analysis.isConceptual || !analysis.hasSymbol) {
    engines.vectorKnowledge = true;
  }

  // Engine 2b: Markdown (user-specific context)
  if (analysis.needsUserContext) {
    engines.markdownLoad = true;
  }

  return engines;
}
```

```typescript
class SQLEngine {
  async search(params: {
    symbol: string;
    timeframe: string;
    barsBack?: number;
  }): Promise<MarketContext> {
    const { symbol, timeframe, barsBack = 16 } = params;

    // SQL query — JSONB comments retrieved alongside numerical data
    const result = await db.query<OHLCVRow>(
      `
      SELECT
        timestamp,
        open, high, low, close, volume,
        atr_value, atr_percentile,
        adx_value, rsi_value,
        tema_value, hrma_value, smma_value,
        trend_direction, volatility_regime, swing_momentum,
        support_levels, resistance_levels,
        reversal_probability,
        comments                              -- JSONB comments per row

      WHERE symbol = $1
        AND timeframe = $2
        AND timestamp >= NOW() - INTERVAL '${barsBack * 5} minutes'
      ORDER BY timestamp DESC
      LIMIT $3
    `,
      [symbol, timeframe, barsBack]
    );

    if (result.rows.length === 0) {
      throw new Error(`No data found for ${symbol} ${timeframe}`);
    }

      symbol,
      timeframe,
      timestamp: latest.timestamp,
      price: latest.close,

      // Full time-series with JSONB comments per bar
      bars: bars, // Each bar: numbers + JSONB comments

      // Key levels
      support: latest.support_levels,
      resistance: latest.resistance_levels,

      // Current regime
      regime: {
        trend: latest.trend_direction,
        volatility: latest.volatility_regime,
        momentum: latest.swing_momentum,
      },
    };
  }
}
```

### 4.5 Complete Query Handler

```typescript
async function handleQuery(userId: string, query: string): Promise<string> {
  // 1. Analyze and route query
  const analysis = analyzeQuery(query);
  const routing = await routeQuery(query, userId);

  const contexts: any = {};

  // SQL Engine — returns bars with JSONB comments included
  if (routing.sql) {
    const symbolInfo = extractSymbolAndTimeframe(query);
    if (symbolInfo) {
      contexts.market = await sqlEngine.search({
        symbol: symbolInfo.symbol,
        timeframe: symbolInfo.timeframe,
      });
    }
  }

  // Vector Engine (general knowledge)
  if (routing.vectorKnowledge) {
    contexts.knowledge = await vectorEngine.searchKnowledge(query);
  }

  // Vector Engine (user context)
  if (routing.vectorUser) {
    contexts.userContext = await vectorEngine.searchUserContext(userId, query);
  }

  // 2. Assemble LLM context
  const systemPrompt = buildSystemPrompt();
  const contextText = assembleContext(contexts);

  // 3. LLM generation
  const response = await llm.generate({
    system: systemPrompt,
    context: contextText,
    query: query,
  });

  // 4. Audit log
  await jsonlLogger.log({ type: 'user_query', content: query, routing });
  await jsonlLogger.log({
    type: 'assistant_response',
    content: response,
    model_used: 'claude-opus-4',
  });

  return response;
}

function assembleContext(contexts: any): string {
  const parts: string[] = [];

  // Market data with JSONB comments (rich multi-row narrative)
  if (contexts.market) {
    parts.push('# Current Market Conditions\n');
    parts.push(
      `Symbol: ${contexts.market.symbol} | Timeframe: ${contexts.market.timeframe}\n`
    );
    parts.push(`Current Price: ${contexts.market.price}\n\n`);

    parts.push('## Time-Series Data (newest first)\n');
    contexts.market.bars.forEach((bar: OHLCVRow, i: number) => {
      parts.push(`### Bar ${i + 1}: ${bar.timestamp}\n`);
      parts.push(
        `Price: ${bar.close} | ATR%ile: ${bar.atr_percentile} | Momentum: ${bar.swing_momentum}\n`
      );

      // Include all JSONB comments for this bar
      if (bar.comments && Object.keys(bar.comments).length > 0) {
        parts.push('Indicator Context:\n');
        for (const [indicator, comments] of Object.entries(bar.comments)) {
          for (const [, text] of Object.entries(
            comments as Record<string, string>
          )) {
            parts.push(`  - [${indicator.toUpperCase()}] ${text}\n`);
          }
        }
      }
      parts.push('\n');
    });
  }

  // General knowledge
  if (contexts.knowledge?.length > 0) {
    parts.push('# Trading Concepts\n');
    contexts.knowledge.forEach((chunk: any, i: number) => {
      parts.push(`## Concept ${i + 1}\n${chunk.text}\n`);
    });
  }

  // User context
  if (contexts.userContext?.length > 0) {
    parts.push('# Trader Profile\n');
    contexts.userContext.forEach((chunk: any) => {
      parts.push(`## ${chunk.section}\n${chunk.text}\n`);
    });
  }

  return parts.join('\n');
}
```

## 5. Graceful Fallback

### 5.1 Fallback Scenarios

**Available Timeframes in Database**: M5, M15, M30, H1, H2, H4, H8, H12, D1

```
SCENARIO 1: No Symbol in Query and/or No Timeframe
├── Query: "How's the market today?" or "What's EURUSD doing?"
├── Problem: No specific symbol to query OR missing timeframe specification
├── Sub-cases:
│   ├── 1a: No symbol at all → Query major symbols (XAUUSD, EURUSD, US30, BTCUSD)
│   └── 1b: Has symbol but no timeframe → Ask for timeframe or show multiple
├── Fallback: Query major markets or request clarification
└── Response: Broad market overview or "Which timeframe? (H1, H4, D1)"

SCENARIO 2: Symbol Not in Database / Timeframe Not Available
├── Query: "What's AAPL doing?" or "EURUSD M1 analysis"
├── Problem: Symbol not supported OR timeframe not available
├── Sub-cases:
│   ├── 2a: Symbol missing (e.g., stocks) → Only forex/crypto in DB
│   └── 2b: Symbol exists but timeframe unavailable (M1, W1)
├── Fallback: General knowledge + external API OR suggest available timeframes
└── Response: "I don't have real-time AAPL data, but..." or "M1 not available, try H1"

SCENARIO 3: No Recent Data
├── Query: "XAUUSD H4 analysis"
├── Problem: Last update was 2+ hours ago (data gap)
├── Fallback: Use last available rows with JSONB comments + disclaimer
└── Response: "Based on last update at 14:00 UTC — JSONB context preserved from then..."

SCENARIO 4: Conceptual Query Only
├── Query: "What is RSI?"
├── Problem: No market data needed
├── Fallback: Vector search only (skip SQL)
└── Response: Pure educational content from trading knowledge base

SCENARIO 5: Ambiguous Query
├── Query: "Should I trade?"
├── Problem: Missing context (symbol? timeframe? when?)
├── Fallback: User profile + clarifying question
└── Response: "Based on your profile... Which symbol-timeframe? (e.g., XAUUSD H4)"
```

### 5.2 Implementation: Fallback Logic

```typescript
class FallbackHandler {
  private readonly AVAILABLE_TIMEFRAMES = [
    'M5',
    'M15',
    'M30',
    'H1',
    'H2',
    'H4',
    'H8',
    'H12',
    'D1',
  ];
  private readonly MAJOR_SYMBOLS = ['XAUUSD', 'EURUSD', 'US30', 'BTCUSD'];

  async handleQuery(userId: string, query: string): Promise<QueryResult> {
    try {
      return await primaryQueryHandler(userId, query);
    } catch (error) {
      return await this.selectFallback(userId, query, error as Error);
    }
  }

  private async selectFallback(
    userId: string,
    query: string,
    error: Error
  ): Promise<QueryResult> {
    const analysis = analyzeQuery(query);

    if (!analysis.hasSymbol) return await this.majorMarketsOverview(userId);
    if (analysis.hasSymbol && !analysis.hasTimeframe)
      return await this.requestTimeframeClarity(userId, query);
    if (error.message.includes('No data found for symbol'))
      return await this.externalDataFallback(userId, query);
    if (error.message.includes('Timeframe not available'))
      return await this.suggestAvailableTimeframes(userId, query);
    if (error.message.includes('stale data'))
      return await this.staleDataFallback(userId, query);
    if (analysis.isConceptual) return await this.knowledgeOnlyFallback(query);
    return await this.clarificationFallback(userId, query);
  }

  // Stale data fallback: use last available rows — JSONB comments still present
  private async staleDataFallback(
    userId: string,
    query: string
  ): Promise<QueryResult> {
    const symbolInfo = extractSymbolAndTimeframe(query);

    const staleData = await db.query<OHLCVRow>(
      `
      SELECT *, comments
      FROM ohlcv_5m
      WHERE symbol = $1 AND timeframe = $2
      ORDER BY timestamp DESC
      LIMIT 16
    `,
      [symbolInfo.symbol, symbolInfo.timeframe]
    );

    if (staleData.rows.length === 0) {
      return await this.externalDataFallback(userId, query);
    }

    const lastUpdate = staleData.rows[0].timestamp;
    const ageMinutes = Math.floor(
      (Date.now() - new Date(lastUpdate).getTime()) / 60000
    );

    // Note: JSONB comments are preserved even on stale rows — they accurately
    // describe conditions as they were at the last update time.
    const contextText = assembleContext({
      market: {
        bars: staleData.rows,
        symbol: symbolInfo.symbol,
        timeframe: symbolInfo.timeframe,
      },
    });

    const response = await llm.generate({
      system: 'Provide analysis but clearly note that data is stale.',
      context: contextText,
      query: query,
    });

    return {
      response: `[Data as of ${ageMinutes} minutes ago] ${response}`,
      fallback_used: 'stale_data',
    };
  }

  private async requestTimeframeClarity(
    userId: string,
    query: string
  ): Promise<QueryResult> {
    const symbolMatch = query.match(/\b(XAUUSD|EURUSD|BTCUSD|US30)\b/i);
    const symbol = symbolMatch ? symbolMatch[1].toUpperCase() : 'this symbol';
    return {
      response: `I need to know which timeframe for ${symbol}. Available: ${this.AVAILABLE_TIMEFRAMES.join(', ')}. Example: "${symbol} H4"`,
      fallback_used: 'missing_timeframe',
      needs_clarification: true,
    };
  }

  private async suggestAvailableTimeframes(
    userId: string,
    query: string
  ): Promise<QueryResult> {
    const symbolMatch = query.match(/\b(XAUUSD|EURUSD|BTCUSD|US30)\b/i);
    const timeframeMatch = query.match(/\b(M1|M3|W1|MN)\b/i);
    const symbol = symbolMatch ? symbolMatch[1].toUpperCase() : 'the symbol';
    const requestedTF = timeframeMatch ? timeframeMatch[1] : 'that timeframe';
    return {
      response: `${requestedTF} not available for ${symbol}. Available: ${this.AVAILABLE_TIMEFRAMES.join(', ')}. Try H4 or D1?`,
      fallback_used: 'timeframe_not_available',
      available_timeframes: this.AVAILABLE_TIMEFRAMES,
    };
  }
}
```

## Conclusion

This architecture provides:

✅ **Right storage for right data** — PostgreSQL for time-series + JSONB comments, filesystem for audit/profiles, Vector DB for concepts

✅ **Symbol-Timeframe independence** — Each symbol-timeframe pair (e.g., XAUUSD-H4, XAUUSD-H1) is an independent trading instrument with unique data, indicators, and JSONB comments

✅ **Historical descriptive context preserved** — JSONB comments permanently attached to every row at insert time — historical narrative is irreplaceable and never lost

✅ **Multi-dimensional LLM context** — Every row provides numbers + multi-indicator commentary → LLM receives complete time-series narrative, not just numbers

✅ **Schema flexibility** — Single JSONB column grows freely. Add indicators, add comment types, no ALTER TABLE ever needed

✅ **Zero application overhead** — PostgreSQL trigger handles JSONB generation at insert — no ETL pipeline, no separate service, no cron job

✅ **Intelligent retrieval** — Three-engine approach (SQL+JSONB + Semantic + Markdown) covers all query types

✅ **Robust fallback** — Graceful degradation when primary data unavailable, JSONB context preserved even on stale data

✅ **Scalable design** — Each component scales independently

✅ **Cost-effective** — Minimal redundancy, JSONB storage overhead is negligible vs. LLM response quality gain

**Key Takeaways**:

1. JSONB comments capture **what conditions meant** at the exact moment they occurred — this cannot be reconstructed retroactively
2. Symbol-timeframe combinations are **independent instruments** — EURUSD-H4 ≠ EURUSD-H1
3. Store: source data (PostgreSQL native columns) + descriptive context (JSONB) + static knowledge (Vector DB) + user profiles (Markdown)
4. JSONB **Superpower 1**: Historical descriptive data permanently attached to every timestamp
5. JSONB **Superpower 2**: Multiple comments per indicator per row — no schema changes ever needed
6. Available timeframes: **M5, M15, M30, H1, H2, H4, H8, H12, D1**
